# 반납 화면의 상태·문구·복구 동작 설계

**상세 설계 후보. 제품 화면 구현이나 실기 동작 결과가 아니다.** [반납 프로토콜](return-protocol-contracts.md)을 사용자 앱·NU 기기·운영자 화면에 연결한다. 기존 U24/D01/O01/U04/U05 안의 상태와 동작을 구체화하며 기본 화면 수는 37개로 유지한다.

[상태·행동·검토 사례 JSON](return-screen-design.json) · [기존 전체 화면 흐름](screen-flows.md)

이 문서는 화면에서 확인할 정보와 동작을 정한다. 서버 권한 검증·기기 물리 승인·실제 gate 검증을 버튼 활성화로 대체하지 않는다. 프로토콜 후보를 기존 API/BLE에 병합했다고 표시하지 않는다.

## 1. 세 화면이 공유할 원칙

- 앱: 현재 단계, 다음에 할 수 있는 동작, 연결이 끊기면 무엇을 확인해야 하는지 표시한다.
- 기기: 짧은 상태·필요한 물리적 확인을 표시한다. 서버의 반납 완료나 재대여 준비를 로컬 삭제 사실만으로 추정하지 않는다.
- 운영자: 접수·기기 상태·재대여 가능 여부를 따로 본다. 고객의 초기화 승인권이나 복구 정책 선택권을 대신 행사하지 않는다.

기본 상태는 최신 권한 검사를 통과한 동일 job/epoch의 원천에서 정한다. 연결·인증·호환·epoch 불일치 등 추가 제한이 있으면 가능한 동작을 더 줄인다. 제한을 해제했다는 이유로 다른 권한을 추가하지 않는다.

색상만으로 성공/대기/오류를 구분하지 않는다. 단계명·상태 문구·아이콘 의미를 함께 제공한다. 사용자가 여행자임을 고려해 주요 제목은 한국어/영어를 같이 정의했다. 화면 언어 선택은 앱 설정을 따르며 전체 설명/오류/접근성 문구의 영어 번역은 후속 검수 대상으로 남긴다.

## 2. 단계별 표시와 버튼

| 상태 | 사용자 앱 U24 | NU 기기 D01의 반납 모드 | 운영자 O01 |
|---|---|---|---|
| RU-01 점검 중 | **반납 전 확인이 필요해요**. 필요한 확인 진행 / 반납 신청 취소 | 반납 준비 · 앱에서 확인 | 점검 대기. 상태/진단 조회 |
| RU-02 준비 완료 | **기기에서 반납을 확인해 주세요**. 기기에서 확인 / 반납 신청 취소 | 삭제 범위 확인 후 물리 버튼 승인 | 사용자 확인 대기. 초기화 대신 승인 버튼 없음 |
| RU-03 허가 발급·응답 불명 | **초기화 진행 상태를 확인하고 있어요**. 상태 다시 확인 / 기기 다시 연결 | 처리 상태 확인 중 · 앱 연결 유지 | 허가 발급 · 기기 응답 확인 중. 진단/복구 지원 |
| RU-04 기기 실행 중 | **기기의 지갑 정보를 지우고 있어요**. 상태 확인 | 초기화 진행 중 · 전원 유지 | 기기 초기화 진행 중. 진단 조회 |
| RU-05 증거 확인 중 | **초기화 결과를 확인하고 있어요**. 결과 확인 / 기기 다시 연결 | 결과 확인 중 · 연결 유지 | 삭제 증거 확인 중. 허용된 증거 중계 |
| RU-06 서버 완료·기기 정리 대기 | **반납 접수 완료 · 기기 정리 중**. 기기 정리 다시 확인 / 내 기록 보기 | 지갑 초기화 확인됨 · 기기 정리 확인 중 | 반납 접수 완료 · 재대여 대기. 정리 재확인 |
| RU-07 현재 기기 재대여 준비 완료 | **반납이 완료됐어요**. 내 기록 보기 | 반납 완료 · 새 등록 대기 | 재대여 준비 완료. 새 대여 시작은 최신 gate 재검증 후 |
| RU-08 취소 동기화 완료 | **반납 신청을 취소했어요**. 화면 나가기 | 사용 가능 · 기존 설정 유지 | 반납 신청 취소됨 |
| RU-09 격리 | **반납 상태를 확인해야 해요**. 상태 확인 / 반납 도움 받기 | 확인 필요 · 앱에서 도움 요청 | 기기 격리 · 재대여 불가. 진단/지원 |
| RU-10 과거 반납 조회 | **이전 반납 기록이에요**. 내 기록 보기 | 현재 대여 상태 유지; 과거 화면 동작 전송 없음 | 이전 반납 완료와 현재 배정 분리 |
| RU-11 서버 완료·기기 정리 실패 | **반납 접수 완료 · 기기 확인이 필요해요**. 상태 확인 / 도움 받기 / 내 기록 보기 | 기기 확인 필요 · 도움 요청 | 반납 접수 완료 · 기기 정리 실패 · 재대여 불가. 진단/지원만 |

표의 버튼은 해당 권한·연결·동작 조건을 모두 만족할 때만 제공한다. 상세 행동 ID/guard는 JSON의 RA-01~12에 있다. 운영자 버튼에는 강제 초기화·완료 처리·재대여 허용 같은 수동 우회 동작을 두지 않는다.

모든 단계에서 화면 이탈은 가능하다. **화면 나가기와 반납 신청 취소는 다른 행동**이다. 이탈은 원job을 지우거나 취소하지 않는다. 다음 앱 진입은 원job 조회로 복원한다.

RU-08은 취소 요청을 보낸 순간이 아니라 grant 미발급 및 양측 제한 해제까지 확인한 결과다. 응답 유실이면 사용 가능으로 표시하지 않는다. RU-04의 같은 내구 journal 재개는 새 삭제 승인 재실행이 아니며, 일반 서명 요청의 자동 재실행 금지와 구분한다.

RU-11은 job.phase=completed를 유지하면서 기기 정리 표식 유실/검증 실패로 gate=closed인 조합이다. 서버의 반납 완료를 되돌리지 않으며, 기기 정리 실패를 단순 대기나 재대여 가능으로 표시하지 않는다. 같은 epoch의 이 실패 조건은 RU-06/07보다 우선한다. 이미 새 대여가 존재하는 과거 기록이면 RU-10의 기기 조작 금지를 따른다.

## 3. 화면 구성 스케치

아래는 정보 순서 검토용 텍스트 스케치다. 실제 기기 화면 크기·폰트·버튼 배치·최종 시각 디자인은 미선정이며, 프로토콜 ID는 제품 UI에 노출하지 않는다.

### 사용자 앱: 연결이 끊긴 경우

```text
기기 반납

연결이 끊겼습니다
마지막으로 확인한 상태: 초기화 진행 확인 중
마지막 확인 시각: [확인된 시각]

기기를 가까이 두고 연결해 주세요.
반납 상태를 확인한 뒤 다음 단계를 안내합니다.

[ 기기 다시 연결 ]
[ 상태 다시 확인 ]
  화면 나가기
```

실제 연결 상태에 따라 가능한 버튼만 보인다. 재연결은 새 등록/create/import를 뜻하지 않는다. **처음부터 다시·다시 초기화·반납 취소**를 불명확한 실행 상태에 제공하지 않는다.

### 사용자 앱: 서버 접수 후 기기 정리 대기

```text
기기 반납

반납 접수 완료
기기 정리를 확인하고 있어요

기기를 가까이 두고 연결을 유지해 주세요.
기기 정리가 확인되면 완료를 안내합니다.

[ 기기 정리 다시 확인 ]
[ 내 기록 보기 ]
```

이 단계에서 기록 조회는 현재 ReceiptOwnership/Eligibility를 검증한다. 반납 버튼을 눌렀다는 사실로 기록 소유권을 부여하지 않는다. 사용자 원음·키·개인 증거를 운영자 지원 요청에 자동 첨부하지 않는다.

### 운영자: 접수와 재대여 준비를 따로 표시

```text
기기·대여 관리

반납 접수        완료
기기 정리 확인   대기
새 대여          시작할 수 없음

[ 기기 정리 다시 확인 ]
[ 복구 진단 보기 ]
```

재대여 가능 상태라면 “새 대여 시작” 버튼을 제공할 수 있지만, 실제 API-045/등록 요청 직전 서버에서 gate·current epoch·활성 binding 부재·운영 권한을 재검증한다. 화면의 녹색 표시나 지난 조회 결과를 권한 토큰으로 사용하지 않는다.

## 4. 기본 상태보다 우선하는 제한

| 제한 | 표시와 행동 |
|---|---|
| RO-01 인증/조회권 없음 | 개인 job·기록 감춤. 로그인 또는 허용된 지원 경로만. 존재 여부를 추정하게 하는 상세 오류도 숨김 |
| RO-02 job·기기·epoch 모순 | 상태 확인/지원 안내. 현재 기기에 원job의 승인·증거·정리 동작을 보내지 않음 |
| RO-03 서버 상태 오래됨/오프라인/허가 발급 여부 불명 | 확정 성공 문구 대신 **마지막 확인 상태와 시각** 표시. 새 초기화·취소·회수·증거/정리 재접수·새 대여는 원천 확인 뒤 |
| RO-04 앱/기기 호환 조합 미확인 | 지원 연결 안내·조회/지원만. 예전 reset 명령으로 우회하지 않음 |
| RO-05 기기 미연결 | 서버 조회는 가능할 수 있음. 기기 확인·삭제 증거·정리 증명·새 대여는 연결/증거 확인 전 비활성 |
| RO-06 필요한 복구 확인 미완료 | 현재 지원 정책의 사전 확인만. 새로운 초기화 승인 비활성 |

여러 제한은 모두 적용한다. 위 순서는 대표 안내 문구를 선택하는 우선순위이고 다른 제한을 무시하는 순서가 아니다. 예를 들어 재대여 가능 캐시가 있어도 로그아웃/오프라인이면 해당 정보의 노출과 배정 버튼을 제한한다.

RO-03에서는 RU-07의 “반납이 완료됐어요”나 RU-08의 “기기를 계속 사용할 수 있습니다”를 현재 확정 사실처럼 보여주지 않는다. “마지막 확인: 반납 완료/취소됨 · 상태 재확인 필요”로 바꾸고 확정 동작을 비활성화한다. 로컬 기기의 실제 진행 표시는 서버 캐시와 구분한다.

## 5. 재진입·재연결과 동작의 책임

1. 앱은 민감하지 않은 원job 참조만 복원하고 현재 인증/조회권을 확인한다. 이전 owner token이나 니모닉을 자동 복원하지 않는다.
2. RP-08/API-091 후보로 원job·서버 완료·gate를 조회한다. 같은 deviceId의 새 대여를 과거 반납 건으로 대체하지 않는다.
3. 현재 단계에 맞는 owner 세션 또는 제한된 복구 relay를 확보한다. 역할/epoch가 다르면 명령을 보내지 않는다.
4. commit_issued는 grant 재발급 화면이 아니다. 같은 허가의 조회/기기 상태 확인 절차를 따른다. 기기 준비 시간이 재시작되지 않는다.
5. evidence_pending은 같은 job의 증거 재접수, completed/awaiting_cleanup은 같은 ACK/cleanup 증명 재확인이다. 둘 다 새 초기화를 실행하지 않는다.
6. current epoch와 새 binding이 이미 바뀌었으면 RU-10으로 전환하고 과거 기기 조작 버튼을 없앤다.

U05의 일반 설정·찾기·녹음·FOTA 동작은 반납 제한을 따른다. D01의 범용 request.cancel은 commit이 발급된 reset job을 취소하지 못한다. U04가 미설정 기기를 발견해도 서버의 재대여 gate와 현재 등록 대상 검증 전에는 새 지갑 생성/import로 넘기지 않는다.

기기 물리 버튼 승인 화면에는 **해당 기기에서 삭제할 지갑/자격 범위**를 표시한다. 전체 블록체인 자산이나 외부 서비스의 passkey 등록까지 삭제된다고 표현하지 않는다. 지갑 출처별 영향 안내는 해당 검증 profile과 서버 점검 결과에 따라 제공하며 “모두 안전하게 복구 가능” 같은 문구를 사용하지 않는다.

## 6. 미결정 정책과 제품 문구의 경계

신규 여행 지갑의 개인 암호화 백업 추가 여부는 여전히 사용자 선택 대기다. 답변이 없다는 이유로 백업 메뉴·키 내보내기·복구 없이 초기화 버튼을 설계 확정하지 않는다.

**제품 정책 자체가 미정인 상태는 출시 전 설계 장애 요인**이다. 고객에게 “개발 정책이 미정”이라고 보여주는 정상 사용 화면을 만들지 않는다. 현재 검토에서는 해당 신규 여행 지갑의 파괴적 동작 경로를 미승인으로 표시한다. 정책이 정해진 뒤 실제 고객에게 필요한 “복구 확인 필요” 문구와 동작을 확정한다.

import 지갑처럼 기존에 합의된 외부 접근 확인 경로는 별도로 설계할 수 있다. 그러나 그것을 신규 여행 지갑의 복구 수단으로 자동 간주하지 않는다.

“반납 도움 받기”의 실제 지원 채널·운영 응답 기준도 미선정이다. 출시 전에 실제 경로를 연결하고 오프라인 안내를 준비해야 하며, 존재하지 않는 상담/연락처를 화면에 표시하지 않는다. 여기서는 지원 의도와 공유 가능한 정보만 정의했다.

## 7. 기존 화면 반영과 검토 범위

- U24: 기존의 binding 해제=재대여 가능이라는 성공 문구를 분리한다.
- O01: 반납 접수/기기 정리/gate 표시와 운영자 지원 범위를 연결한다.
- U04: 미설정 상태만으로 새 등록·지갑 생성/import를 시작하지 않는다.
- U05: 반납 중 일반 명령을 제한하고 원job 복구로 연결한다.
- D01: 반납 확인/진행 표시와 일반 승인 흐름을 구분하고 범용 취소의 적용 범위를 제한한다.
