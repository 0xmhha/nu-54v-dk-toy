# 지갑 플랫폼 — 화면·권한·결제 흐름 초안

> 2026-09-18 범위 갱신: [12주 완료 범위 v3](twelve-week-completion-scope-v3.md)가 최신 기준이다. 아래 기존 검토에서 패스키·녹음·스마트 계정 등을 후보/후속으로 둔 부분은 새 범위를 따른다. 초기 EOA 개발 순서와 고객 가스 부담은 유지하며, 새 Cloud Wallet의 MPC는 별도로 설계한다.

작성: 2026-09-17. [확정 요구사항과 미정 항목](payment-platform-scope-v2.md)을 바탕으로 만든 설계안이다. 제품 코드나 최종 Seed가 아니다. 아래 화면 구성·상태·책임 분리는 제안이며, 사용자가 모든 세부 기능을 승인한 것으로 취급하지 않는다.

최신 결정: NU-54V-DK와 Nordic nRF54L15 DK는 보유하고 있다. 실기 검증은 개발 단계에서 수행한다. 지금은 화면과 데이터 흐름을 구체화하며, 하드웨어 실측을 다음 질문의 선행조건으로 두지 않는다.

## 1. 사용자가 만나는 제품

| 제품·모드 | 첫 화면과 탐색 구조 제안 | 핵심 동작 | 결정 상태 |
|---|---|---|---|
| 모바일 · 고객 | 지갑 / 패스포트 / 기록 / 내 기기 | 자산, 받기·보내기, 영수증, 혜택, 설정·대여·반납 | 지갑 활용 앱과 패스포트 방향 확정. 세부 화면은 제안 |
| 모바일 · 사장님 | 매장 선택 → 매장 지갑 / 수취 내역 | 사장님 계정과 연결된 지갑 자산 조회 | 자산 조회 확정. 자금 이동 실행 범위 미정 |
| React Native 태블릿 · 관리자 | 매장 홈 / 메뉴 / 주문 / 매출·정산 / 설정 | 가게 로그인, 메뉴·가격·품절 관리, 주문 처리, 입금 대조 | 앱·주요 관리 기능 확정. 세부 권한·마감 정책은 미정 |
| 같은 태블릿 · 고객 주문 | 메뉴 → 장바구니 → 결제 → 주문 결과 | USDC 결제 요청과 지갑 승인 | 기존 결제 제품 범위. 관리자 모드와 전환 분리 |
| 운영 백오피스 | 가맹점 / 기기·대여 / 거래 확인 / 서비스 상태 | 운영자가 서비스 문제와 대여를 관리 | 포함 확정. 세부 기능은 제안 |
| 지갑 하드웨어 | 상태 / 결제 승인 / 패스포트 반응 | 안전한 지출 승인, 기기 조작 | 기본 지갑과 패스포트 방향 유지 |

모바일 ‘기록’은 구매·영수증과 음성 기록을 구분한다. 음성 기록 화면은 사용자 제안에 대한 확장안이며, 첫 버전 필수 범위는 아직 미정이다. 녹음 목록 → 원음·전사문 → 요약·할 일 → 삭제·내보내기 흐름을 후보로 둔다. 근접 인증과 범용 패스키는 별도 지원 수준으로 표시한다.

가게 ID 로그인 요구는 유지한다. 실제 관리 행동의 수행자를 구분할 수 있도록 사용자 계정과 매장 소속/역할을 연결하는 구조를 제안한다. 하나의 공유 비밀번호를 모든 관리자가 사용한다고 가정하지 않는다.

## 2. 대표 사용자 흐름

### 고객

1. 앱 계정과 대여 기기를 연결하고 기존 키 가져오기 또는 신규 지갑 생성을 선택한다.
2. 자산을 확인한다. 신규 지갑은 원래 지갑에서 필요한 자금을 이체한다. 이 단계는 자동 환전 기능이 아니다.
3. 키오스크에서 메뉴와 USDC 결제를 선택한다.
4. 기기에서 매장·금액·지원 체인/토큰을 확인하고 승인한다. 근접 검증을 적용하는 환경에서는 해당 요청에 연결된 유효 결과가 필요하다.
5. 전송 결과가 아직 불명확하면 ‘확인 중’으로 표시한다. 입금 검증과 선택 체인의 확정 기준을 충족하면 결제 완료·영수증·패스포트 혜택을 반영한다.
6. 반납 전 잔액 회수와 기기 연결 해제를 진행한다. 사용자 계정의 영수증·패스포트 기록은 유지한다.

### 사장님

1. 태블릿에서 가게 계정으로 로그인하고 매장을 선택한다.
2. 메뉴·가격·품절·수취 지갑 설정을 확인한다. 수취 지갑 변경은 일반 메뉴 수정과 다른 승인 절차를 둔다.
3. 고객 주문 모드로 전환한다. 관리 화면 복귀 시 재인증한다.
4. 주문 목록과 결제/입금 상태를 확인하고 주문을 처리한다.
5. 매출·USDC 수취·환불·수수료·미일치 내역을 확인한다. 모바일 앱에서는 동일 계정으로 매장 지갑 자산을 조회한다.

### 운영자

가맹점·등록 단말·대여 상태와 거래 오류를 관리한다. 고객의 개인키나 음성 파일을 보유·열람해야 운영할 수 있는 구조로 만들지 않는다. 거래 재조회는 허용 범위 내에서 가능하지만 임의로 온체인 결제를 성공으로 변경하는 기능은 두지 않는다.

## 3. 권한 초안

| 동작·데이터 | 고객 계정 | 사장님 계정 | 고객용 키오스크 모드 | 서비스 운영자 |
|---|---|---|---|---|
| 지갑 자산 조회 | 자신의 연결 지갑 | 자신의 권한이 있는 매장 지갑 | 해당 주문 결제 결과만 | 장애 분석에 필요한 범위만, 별도 권한 |
| 메뉴·가격 변경 | 불가 | 권한 있는 매장 | 불가 | 지원 업무 범위는 별도 결정 |
| 주문·매출 조회 | 자신의 주문 | 자신의 매장 | 현재 주문에 필요한 정보만 | 업무 범위와 기록을 남기는 접근 |
| 지갑 개인키 | 사용자 선택한 가져오기/기기 설정 경로에서만 취급 | 계정 로그인으로 키 획득 불가 | 불가 | 불가 |
| 실제 자금 전송 | 해당 지갑의 승인·서명 필요 | 서명 방식·실행 기능 미정 | 고객 기기에 요청 전달, 독자 서명 불가 | 고객 자금을 임의 전송하지 않음 |
| 고객 음성·전사문·요약 | 자신의 기록 | 고객 기록 접근 불가 | 접근 불가 | 기본 접근 불가 |
| 패스포트 혜택 | 자신의 혜택 조회·사용 | 자기 매장의 발급·사용 정책 범위 | 해당 주문의 적립·사용 흐름 | 운영 범위만, 임의 발급 정책 미정 |

같은 사람이 고객이면서 사장님일 수 있다. 화면 모드 전환은 계정의 매장 권한을 바꾸거나 키를 복사하는 동작이 아니다. API도 매장별 접근을 검증한다. 지원 로그에는 키·오디오·전사문을 기록하지 않는다.

## 4. 서비스의 책임

추가 제공된 [poc-platform 검토](poc-platform-reuse-plan.md)로 지갑 SDK·Bundler·Paymaster Proxy·웹 화면이 이미 있음을 확인했다. 아래는 새로 모든 코드를 만든다는 의미가 아니라 책임 구분이다. 기존 체인 기능과 웹 UI를 재사용하고, 카페 업무·React Native·NU BLE signer를 추가하는 방향을 제안한다. 구독 가맹점 화면과 PG 시뮬레이터를 카페 매출 원장으로 그대로 대체하지 않는다.

초기에는 아래 책임을 구분한 하나의 공통 백엔드를 제안한다. 책임을 나눈다는 이유로 각각을 별도 서버로 배포할 필요는 없다. 언어·프레임워크·배포환경은 아직 선택하지 않았다.

| 기능 영역 | 맡을 일 | 맡지 않을 일 |
|---|---|---|
| 계정·매장 권한 | 계정, 매장 소속, 세션, 기기 등록 | 로그인만으로 개인키 제공 |
| 메뉴·주문 | 메뉴/가격, 주문 당시 항목·금액 보관, 주문 진행 | 이후 메뉴 가격 변경으로 과거 주문 금액 수정 |
| 결제 조정 | 견적, 결제 시도, 서명 요청, 제출 추적, 검증 결과 반영 | 거리 숫자·클라이언트 성공 응답만으로 결제 완료 |
| 체인/토큰 연결부 | 선택 체인의 거래 구성·조회와 정확한 자산 식별 | 지원하지 않는 체인의 같은 이름 토큰을 USDC로 취급 |
| 기존 Indexer 연결부 | 기존 API·이벤트 형식을 내부 조회 형식으로 변환 | 제품을 확인하기 전에 새 Indexer로 교체 |
| 매출·수취 대조 | 주문과 실제 입금/환불의 연결, 차이 표시 | 지갑 잔액을 그대로 매출로 표시 |
| 패스포트 | 적립·쿠폰·사용 상태 | 결제 확인 전 무조건 적립, 재통지에 중복 적립 |
| 대여·반납 | 대여 세션, 기기 할당·회수, 초기화 결과 | 잔액 회수 확인 없이 무조건 키 삭제 |
| 음성 기록 후보 | 사용자 파일·전사·요약 작업과 상태 | 서비스 운영자나 매장에 자동 공유 |

## 5. 주문·결제·환불 상태

이 세 상태는 따로 관리한다. 예를 들어 ‘주문 취소, 입금 확인, 환불 대기’가 동시에 존재할 수 있어야 한다.

| 대상 | 상태 흐름 제안 |
|---|---|
| 주문 | 작성 중 → 결제 대기 → 주문 접수 → 준비 중 → 제공 완료. 취소는 별도 분기 |
| 결제 시도 | 견적 준비 → 승인 대기 → 제출 → 확인 중 → 결제 확인. 거절·기한 만료·실패·추가 확인 필요 분기 |
| 환불 | 요청 → 업무 승인 → 서명 대기 → 제출 → 확인 중 → 환불 확인. 거절·실패 분기 |

서명이 만들어진 뒤에는 화면 닫기·BLE 해제·견적 만료만으로 해당 지급이 불가능해졌다고 판단하지 않는다. 이미 제출했거나 제출 여부가 불명확한 시도는 추적하고, 재시도 시 기존 시도와의 관계를 유지한다. 새로운 견적은 사용자가 다시 확인한다.

주문 ID와 결제 시도 ID를 구분한다. 같은 거래를 재통지받는 경우와 서로 다른 거래로 두 번 입금된 경우를 구분한다. 만료 후 입금, 중복 입금, 금액 차이는 대사 예외로 표시하며 자동 처리 정책은 미정이다.

환불은 원거래를 지우는 동작이 아니라 별도 지급이다. 부분 환불 지원 여부, 환불 수수료 부담, 실제 서명 주체는 결정해야 한다. 이미 반납한 대여 지갑 주소로 무조건 돌려보내지 않고 고객의 환불 수취 주소와 통제권을 확인하는 절차를 설계한다. 누적 환불액과 승인된 환불 한도를 대조한다.

## 6. Indexer에서 결제 완료까지

```mermaid
flowchart LR
    K[키오스크 주문] --> O[주문·결제 요청]
    O --> D[NU 기기 승인·서명]
    D --> T[체인에 거래 제출]
    T --> I[기존 Indexer 관측]
    I --> V[결제 내용·확정 상태 검증]
    V --> R[주문과 입금 연결]
    R --> S[매출·영수증·패스포트 반영]
```

거래 제출 위치는 폰이 필수인 구조로 고정하지 않는다. 기존 결정인 ‘카페 결제 때 고객 폰의 공동 서명 불필요’를 유지한다. 키오스크 또는 연결 서비스가 서명된 거래를 중계하는 방식을 검토한다. 중계·수수료 후원 역할의 법적 적용은 별도 검토 대상이다.

Indexer 연동에서 확인할 항목:

- 지원 체인·네트워크, 정확한 토큰 주소 또는 mint 식별자.
- 거래 실행 성공 여부와 체인별 확정 상태, 재구성/취소 관측 지원.
- 전송 주체·수취인·최소 단위 정수 금액과 주문의 기대값.
- 이벤트 고유 식별자, 중복·순서 변경·재연결·누락 재조회 방법.
- 진행 높이/커서와 지연 상태, 페이지 조회·구독·인증·호출 제한.
- 실제 거래와 주문/결제 시도를 일대일 또는 명시된 규칙으로 연결하는 방법.

예를 들어 ERC-20의 표준 Transfer 이벤트는 from/to/value를 제공하며 주문 ID를 포함하지 않는다. 따라서 ‘이벤트를 읽을 수 있음’과 ‘어느 주문의 결제인지 알 수 있음’은 별개다. 체인 선택 후 주문 연결 방식을 정한다. [ERC-20 규격](https://eips.ethereum.org/EIPS/eip-20)

Indexer가 늦으면 화면은 확인 중과 데이터 갱신 시점을 보여준다. 다시 처리해도 주문·패스포트가 중복 반영되지 않게 한다. 체인 관측이 되돌아가거나 결과가 달라지면 영향받는 주문과 혜택을 추가 확인 대상으로 표시하고 이미 제공된 상품 처리는 예외 정책으로 남긴다.

## 7. 컨트랙트와 테스트 자산

추가 제공된 [stable-poc-contract](https://github.com/0xmhha/stable-poc-contract)에는 테스트 ERC-20, 스마트 계정·서명 검증·Paymaster 코드가 있다. 더미 토큰과 온체인 기능의 기반으로 검토하며 [재사용 계획](stable-contract-reuse-plan.md)에 실제 배포 의존성과 필요한 추가 작업을 기록했다. 일반 지갑으로 시작하고 스마트 계정·운영자 수수료 후원은 후속 단계이며, 기존 키 가져오기를 새 계정 생성으로 대체하지 않는다. ERC-4337 채택 시 결제 시도에 UserOperation 해시를 추가하고 개별 작업 성공과 전송 이벤트를 연결한다.

사용자는 테스트넷 USDC를 구하기 어려워 **개발·시연용 더미 토큰**을 배포해 사용한다고 확정했다. 실제 서비스 자산은 USDC 우선이라는 기존 결정을 유지한다.

| 구분 | 필요한 설계 |
|---|---|
| 확정: 개발·시연용 더미 토큰 | 개발환경에서 통제 가능한 발행·잔액·전송·이벤트 시험. 실제 USDC와 이름·주소·환경 구분 |
| 유지: 실제 서비스의 USDC | 선택 체인의 공식 토큰과 실제 지원 기능을 별도 검증한 뒤 적용 |

Circle은 체인별 본 USDC와 테스트넷 USDC 주소를 제공한다. 테스트 토큰으로 결제 흐름을 시험하는 것과 자체 토큰을 실제 결제에 쓰는 것은 다른 결정이다. [Circle 공식 주소 목록](https://developers.circle.com/stablecoins/usdc-contract-addresses)

제공받은 기존 Indexer는 EVM 기반이며, 실제 소스에 ERC-20 전송·영수증·로그 조회가 있다. 재사용 비용을 고려해 EVM과 ERC-20 더미 토큰을 우선 제안한다. 특정 체인을 선택한 것으로 간주하지 않는다. [코드 검토·연동 제안](indexer-integration-and-test-token.md)

테스트 토큰이 필요하더라도 실제 USDC 결제에서 쓰려는 서명·수수료 후원 방식까지 자동으로 검증되는 것은 아니다. 선택한 결제 방식에 필요한 동작을 목록화하고 테스트 토큰과 실제 지원 토큰의 차이를 별도 시험한다. 주문 추적용 컨트랙트가 필요한지, 기존 전송 흐름으로 연결할지는 Indexer와 체인 결정 후 검토한다.

## 8. 데이터 소유와 보존

- 앱 계정은 개인 기록과 매장 소속을 연결한다. 지갑 주소 하나를 개인 데이터 전체의 공개 조회 키로 사용하지 않는다.
- 대여 기기 교체 후에도 고객의 패스포트·영수증·선택한 음성 기록은 유지할 수 있어야 한다. 계정 연결 해제·삭제 요청 범위는 따로 정한다.
- 고객 앱과 사장님 앱 모드가 같아도 매장 주문 정보와 개인 녹음을 섞지 않는다.
- 사용자 입력으로 키를 가져오는 기능은 존재하지만 일반 계정 서버나 분석 로그에 니모닉/개인키를 저장하는 구조를 요구하지 않는다.
- 원음의 폰 저장·클라우드 전송·보관 정책은 아직 미정이다. 선택한 처리 방식과 데이터 삭제 범위를 제품 화면에 명시한다.

## 9. 개발 단계에서 검증할 대표 시나리오

1. 정상 주문 한 건이 입금 한 건·영수증 한 건·적립 한 번으로 연결된다.
2. 동일 이벤트 반복·재조회에도 매출/적립이 늘어나지 않는다.
3. 틀린 체인·토큰·수취 주소·금액은 정상 주문 완료로 처리하지 않는다.
4. 결제 확인 지연·앱 재시작 후에도 같은 시도를 추적하고 중복 지급을 유도하지 않는다.
5. 취소 뒤 늦은 입금과 서로 다른 거래의 중복 입금을 예외로 식별한다.
6. 환불은 별도 지급으로 추적하고, 반납된 지갑의 수취 주소 문제와 누적 환불 한도를 확인한다.
7. 다른 매장 계정은 주문·매출을 볼 수 없고, 사장님/운영자는 고객 음성 자료와 키를 볼 수 없다.
8. 반납 후 기기에는 이전 고객의 접근 권한이 남지 않고 앱의 개인 기록은 정책대로 유지된다.
9. 근접·음성 기능을 추가하면 실패/연결 중단을 표시하고 지갑 승인에 혼동을 만들지 않는다.

위는 설계상의 검증 항목이며 테스트 실행 결과가 아니다. 실자산 파일럿의 법률·보안·운영 조건과 12주 필수 완료 기준은 여전히 미정이다.

## 10. 바로 이어서 구체화할 입력

[첫 통합 작업·완료 기준](payment-integration-workplan.md)을 작성했다. 조회 API 차이를 먼저 맞추고 주문·지급 대사와 NU signer를 연결한다. 사용자는 초기 고객 부담, 후속 운영자 후원 순서를 확정했다. 체인은 지정된 StableNet RPC, 가스는 고객의 네이티브 토큰으로 확정했다. 계정 방식은 초기 일반 지갑(EOA), 후속 스마트 계정으로 확정했다.

더미 컨트랙트의 개발·시연 목적과 Indexer 백엔드·프론트엔드 저장소를 확인했다. [소스 검토와 연동 설계](indexer-integration-and-test-token.md)를 바탕으로 사용자 지정 StableNet 테스트 체인(8283)을 사용한다. [RPC 확인 기록](stablenet-testnet-baseline.md). 다음은 사장님 자금 이동·환불 정책과 12주 완료 기준을 구체화한다. 하드웨어 실기 시험은 개발 단계에서 수행한다.
