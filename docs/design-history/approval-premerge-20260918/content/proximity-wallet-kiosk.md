# 근접 확인·제스처 입력을 활용한 코인 결제 지갑과 키오스크

검토일: 2026-09-15. NU-54V DK + 디스플레이 + IMU + 버튼을 사용하는 사용자 제안에 대한 기술·제품 검토다. 실물 구현, 키 생성, 자금 이동, 배포는 수행하지 않았다. 첫 결과물은 실제 가치가 없는 테스트넷 자산으로 주문·결제 흐름을 검증하는 시제품으로 제안한다.

## 판단

이 아이디어는 BLE, Channel Sounding, 센서, 화면과 입력, 암호 기능을 서로 연결한다는 점에서 보드 활용도가 높다. 단, 개발 보드에 서명 기능을 구현하는 것과 실제 자산 보관에 적합한 하드웨어 지갑을 만드는 것은 완료 조건이 다르다.

제품 이름은 우선 ‘근접 확인형 코인 결제 단말’로 기술한다. 기능은 **가까운 키오스크의 주문 내용을 지갑 화면에서 확인하고, 사용자 조작 후 해당 주문에 한정된 서명을 제공하는 것**이다. 가까워졌다는 이유로 자동 결제하지 않는다.

일상 사용성은 지원하는 상점/키오스크의 존재에 달려 있다. 이 프로토콜을 만들었다고 기존 카드 결제기·간편결제 가맹점에서 자동으로 사용할 수 있는 것은 아니다. 개인 책상 콘솔보다 연구·시연 가치가 높지만 일상 사용처 확보는 더 어렵다.

## 사실과 검증이 필요한 부분

| 항목 | 확인된 사실 | 남는 검증 |
|---|---|---|
| 거리 측정 | nRF54L15는 Channel Sounding을 지원하며 Nordic이 initiator/reflector 예제를 제공 | NU 보드 포팅, 양단 지원, 거리 추정 알고리즘, 설치 환경 오차 |
| BLE 거리와 보안 | Bluetooth SIG는 PBR와 RTT의 결합 및 릴레이 공격 완화 기능을 설명 | 실제 사용 모드·SDK 설정이 어떤 보안 특성을 제공하는지 확인 |
| 키 보호 | nRF54L 계열은 TrustZone·CRACEN·KMU·보안 부팅 관련 기능 제공 | 선택 코인의 알고리즘, 키 생성·저장·사용 경로, 디버그와 업데이트 정책 |
| 결제 서명 | 서명으로 특정 데이터에 대한 승인을 표현할 수 있음 | 서명이 실제 자산 이전으로 이어지는 거래/컨트랙트 경로 |
| 제스처 | IMU 데이터로 사전에 정의한 움직임 분류 가능 | 오인식, 흔들림, 사용자 편차, 의도치 않은 실행 |

‘이미 거리 기반 처리가 된다’는 가정은 보정해야 한다. 칩에 기능이 있지만 현재 프로젝트에서 거리를 실측한 적은 없다. 보통의 BLE RSSI로 추정한 거리를 결제 승인 기준으로 대체하지 않는다. [Nordic Channel Sounding](https://www.nordicsemi.com/Products/Wireless/Bluetooth-Low-Energy/Channel-Sounding), [Bluetooth SIG 설명](https://www.bluetooth.com/learn-about-bluetooth/feature-enhancements/channel-sounding/), [BLE primer](https://www.bluetooth.com/bluetooth-le-primer/)

## 구성

### 휴대 지갑

NU-54V DK, 작은 디스플레이, 6축 IMU, 확인·취소·선택 버튼, 전원, 케이스. 지갑에서 거래를 해석·표시하고 승인한다. 비밀키를 BLE나 키오스크로 내보내는 인터페이스를 만들지 않는다. 복구용 비밀을 키오스크에 입력하지 않는다.

### 키오스크

태블릿/PC의 주문 화면과 결제 처리 프로그램. 일반 태블릿의 BLE가 Channel Sounding까지 지원한다고 가정하지 않는다. 초기에는 별도의 nRF54L15 계열 보드를 UART 또는 디버거의 가상 직렬 포트 등 지원되는 호스트 인터페이스로 붙여 무선 전면부로 사용하는 구성이 명확하다. 단순 USB 연결만으로 임의 보드가 범용 Channel Sounding 동글이 되지는 않으며 펌웨어와 중계 프로그램이 필요하다.

단일 지갑·단일 키오스크로 시작한다. 가능하면 지갑 쪽이 initiator 역할로 자기 거리 측정 결과를 계산·검증하고, 키오스크 쪽 보드를 reflector로 둔다. 이 역할 배치는 NU 보드에서 검증할 설계안이다. 지갑이 키오스크가 보낸 `near=true`만 믿고 서명하지 않도록 한다.

키오스크 무선부와 주문 서버의 식별자를 결합하고 첫 버전에서는 신뢰할 판매자·수신 주소·체인·결제 컨트랙트를 미리 등록한다. 화면에 수신된 상점 이름을 그대로 표시했다고 상점이 인증되는 것은 아니다.

## 결제 흐름

1. 사용자가 키오스크에서 상품을 선택한다.
2. 주문 ID, 판매자와 수신 주소, 자산 식별자, 금액, 유효시간, 충분한 길이의 암호학적 난수 nonce를 포함한 요청을 만든다.
3. 지갑과 키오스크가 인증된 BLE 세션을 맺고, 같은 피어에 대해 최신 거리 측정을 수행한다. 첫 연결의 코드 비교/등록과 매 주문의 결제 승인은 별개다.
4. 지갑은 요청 형식·상점·체인·자산을 검증하고, 지갑이 실제 서명할 데이터에서 상품 요약·금액·수신 주소를 표시한다. 테스트 자산 이름/소수점 자릿수도 사전 등록 정보와 일치해야 한다.
5. 필요 시 두 화면의 짧은 확인 코드를 비교한다. 지갑의 잠금 해제 PIN과 이 공개 코드는 다른 목적이다.
6. 사용자가 지갑에서 확인한다. 기본은 버튼 승인, 선택적으로 버튼을 누른 상태에서 지정 제스처를 수행한다.
7. 서명 및 외부 전송 직전에 거리 결과의 유효기간·품질·세션 연속성과 요청 일치를 다시 확인한다. 조건이 실패하면 서명을 내보내지 않는다.
8. 지갑에서 결제 데이터를 서명하고 키오스크에 전달한다. 키오스크/서버는 검증 후 해당 결제 방식에 맞게 체인에 제출한다.
9. `사용자 승인`, `서명 수신`, `네트워크 제출`, `결제 확인`, `주문 완료`를 구분한다. 체인에서 필요한 성공 조건을 확인한 뒤 주문 완료로 바꾼다.

키오스크가 임의의 해시만 보내면 지갑은 내용을 확인할 수 없다. 처음에는 하나의 고정된 결제 요청 형식을 지원하고, 금액과 수신자 등을 장치가 직접 해석해 같은 데이터로 서명한다. [Trezor의 장치 화면 확인 원칙](https://trezor.io/guides/trezor-devices/trezor-fundamentals/trezor-s-trusted-display-verify-every-address-on-your-device)

## 랜덤 번호·버튼·제스처의 역할

| 요소 | 적절한 목적 | 보장하지 않는 것 |
|---|---|---|
| 긴 암호학적 nonce | 요청의 일회성, 재사용 식별 | 검증 측의 재사용 방지 로직 없이 단독으로 이중 결제 방지 |
| 사람이 읽는 짧은 코드 | 의도한 단말·요청을 보고 있는지 비교 | 결제 내용의 완전성이나 강한 비밀 인증 |
| 버튼 입력 | 표시된 내용을 사용자가 확인했다는 조작 | 장치 소유자의 신원 그 자체 |
| 고정된 비밀 제스처 | 사용자 조작 또는 잠금 해제 실험 | 생체인증 수준의 신뢰성, 관찰·모방 방지 |
| 무작위 제스처 지시 | 매번 다른 의도적 동작을 요구하는 UX | 공격자가 지시를 아는 상황에서 독립된 보안 요소 |
| 근접 확인 | 승인 시 단말이 가까이 있다는 추가 조건 | 금액·상점의 정당성이나 장치 소유자의 신원 |

제안 UX는 ‘내용 확인 → 버튼을 누른 상태에서 짧은 지정 동작 → 승인’이다. 자유롭게 흔드는 것만으로 승인하지 않는다. 제스처를 쓰기 어려운 경우에는 명확한 버튼 승인 경로를 남긴다. 버튼·제스처 결과는 지갑에서 처리하며 키오스크의 입력 성공 메시지로 대체하지 않는다.

첫 프로토타입의 실제 제스처는 좌우 기울이기, 앞으로 기울이기 등 2~3개로 제한한다. 성공률뿐 아니라 걷기·집어 들기·책상에 내려놓기에서 오승인되는지를 측정한다. 이 기능 때문에 결제가 지나치게 번거로워지면 제스처를 결제 승인 대신 선택·취소·화면 전환에 사용할 수 있다.

## 거리가 멀어졌을 때의 정확한 의미

서명 전에는 새 서명 생성·전송을 막고, 진행 중 입력과 주문 세션을 폐기한 뒤 해당 BLE 연결을 종료한다. 거리 측정 실패·품질 저하·오래된 결과도 승인 불가로 처리한다. 재접근 시 새 nonce와 세션으로 다시 확인한다.

거리 샘플링·처리·BLE 이벤트에는 지연이 있다. ‘멀어진 순간 0ms 안에 끊김’을 보장하지 않는다. 사용할 거리 기준과 허용 지연은 실측 후 정하고, 진입/이탈 기준을 다르게 두어 경계에서 반복 연결되는 현상을 줄인다. 진입을 안정화하기 위한 필터가 서명 시점의 오래된 근접 결과를 계속 유효하게 만드는 일이 없어야 한다.

**지갑 밖으로 나간 유효 서명은 BLE 단절로 회수할 수 없다.** 아직 체인에 제출되지 않았더라도 상대가 유효기간 안에 제출할 수 있다. 체인에 제출된 거래도 연결 해제로 취소되지 않는다. 따라서 이 제품이 제공하는 것은 ‘승인·서명 방출 시점의 근접 조건’이며 ‘거리를 계속 만족할 때만 자금 이전’이라는 보장이 아니다.

서명 이후 연결이 끊기면 화면을 `결제 취소`로 단정하지 말고 `결과 확인 필요`로 둔다. 주문 ID/거래 식별자로 서버에서 상태를 확인한다. 같은 서명·주문의 재전송이 이중 청구·이중 주문으로 이어지지 않도록 한다. [Ethereum 거래 수명주기](https://ethereum.org/developers/docs/transactions/)

## 서명과 실제 코인 이전

랜덤 번호 하나에 서명하면 키 소유 증명은 될 수 있지만 그것만으로 금액이 이전되지는 않는다. 다음 중 한 경로를 명시적으로 선택해야 한다.

- 실제 거래에 직접 서명: 체인의 수신 주소·금액·수수료·체인 식별·거래 nonce 등을 검증하고 서명한다. 앱의 만료 표시만으로 이미 서명된 거래를 무효화할 수 없다.
- 결제 승인 메시지에 서명: 메시지를 처리하는 토큰 또는 결제 컨트랙트가 필요하다. 컨트랙트가 자산 이전 권한과 잔액을 갖는 경로가 있어야 하며 nonce와 유효시간을 실제로 강제해야 한다.

EVM 시제품이라면 EIP-712 형식의 고정된 결제 승인 메시지를 검토할 수 있다. 서명 도메인에는 chain ID·검증 컨트랙트·프로토콜 버전을, 메시지에는 주문 ID·판매자/수신 주소·자산·금액·nonce·만료·세션 바인딩 정보를 포함한다. 사용자에게 청구되는 수수료가 있다면 그것도 고정·표시한다. JSON 문자열을 임의로 해시하는 대신 표준 인코딩과 테스트 벡터를 검증한다.

EIP-712 자체는 이중 사용 방지나 자산 이전 기능을 제공하지 않는다. 앱과 컨트랙트가 이를 구현해야 한다. ERC-3009는 서명 기반 토큰 전송의 참고 표준이지만 모든 코인·토큰이 지원하지 않으며 주문 ID 같은 필드는 자동으로 포함되지 않는다. [EIP-712](https://eips.ethereum.org/EIPS/eip-712), [ERC-3009](https://eips.ethereum.org/EIPS/eip-3009)

구체적인 데모 경로로는 테스트넷의 테스트 토큰을 미리 예치한 결제 컨트랙트가 서명된 주문에 따라 등록된 판매자에게 해당 금액만 지급하는 방식을 사용할 수 있다. 이 경우 예치 잔액·출금·nonce 소비·주문 ID 중복·실패 처리를 구현해야 하며 일반 지갑 잔액을 임의로 가져오는 구조가 아니다. 실제 자산을 이 시제품 컨트랙트에 예치하는 것은 범위에 포함하지 않는다.

거리·BLE·제스처 결과를 메시지에 적었다고 온체인에서 물리적 사실이 증명되는 것은 아니다. 정직하게 구현된 지갑의 로컬 정책과 인증된 세션을 신뢰하는 모델이다. 외부 검증 가능한 거리 증명을 주장하려면 별도 신뢰·증명 설계가 필요하다.

## 하드웨어 지갑으로서의 범위

Nordic의 보안 기능은 유용한 구성요소다. 그러나 ‘KMU가 있으므로 모든 코인의 개인키가 외부에 노출되지 않고 하드웨어 내부에서 서명된다’고 단정할 수 없다. 체인별 서명 곡선, SDK 드라이버, 키 생성·저장·서명 중 메모리 경로를 확인해야 한다. 예컨대 EVM 계열에서 일반적으로 사용하는 secp256k1과 P-256은 서로 다르다. 이번 조사만으로 NU 보드에서 secp256k1의 비추출 키 서명 경로를 확인하지는 못했다.

처음 2주에 실제 SDK를 고정하고 서명 벡터와 키 저장 경로를 검증한다. 부족한 경우 필요한 곡선을 지원하는 보안 소자를 추가할 수 있으나 소자만 추가하면 전체 지갑의 보안이 완성되는 것은 아니다. 개발용 키는 테스트 전용으로 한정한다.

실자산을 다루는 단계에는 키 생성의 난수 품질, 복구와 분실 대응, PIN·시도 제한, 펌웨어 인증과 업데이트, 디버그 접근, 물리적 공격, 표시 데이터와 서명 데이터 일치, BLE 파서와 요청 제한에 대한 검토가 추가된다. 현재는 OTP·디버그 잠금 등의 비가역 설정을 실행하지 않았다. ## 12주 시제품 범위

| 기간 | 결과 |
|---|---|
| 1~2주 | NU 보드·SDK 확인, 양단 거리 측정, 테스트 키 서명 검증. 불확실성이 큰 두 축을 먼저 확인 |
| 3~4주 | 키오스크 상품 선택·주문 ID, 인증 세션, 고정 요청 형식 |
| 5~6주 | 지갑 화면에서 내용 확인, 버튼 승인·취소, nonce·만료·요청 변경 차단 |
| 7~8주 | 단일 테스트넷·단일 자산의 결제 경로, 결제 확인 후 주문 완료 |
| 9~10주 | IMU 입력, 거리 이탈·데이터 노후·단절·재접속 상태 처리 |
| 11~12주 | 중복 결제·금액 변조·다른 상점·오래된 요청·제스처 오승인 시험, 케이스·시연·문서화 |

필수 데모는 ‘주문 선택 → 가까이 가져옴 → 지갑에 정확한 금액 표시 → 사용자 승인 → 테스트넷 결제 확인 → 주문 완료’다. 서명 전 멀어지면 승인되지 않는 데모와, 서명 후 끊겼을 때 결과를 다시 조회하는 데모를 함께 보여준다.

첫 2주 검증이 통과해야 12주 완성 가능성을 판단할 수 있다. 멀티체인, 실제 결제 가맹점 연동, 범용 스마트컨트랙트 서명, 키 복구 제품화, 양산 보안 검증은 기본 시제품 범위에 넣지 않는다.
