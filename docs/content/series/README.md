# NU-54V-DK 구현 전 핵심 정리 시리즈: 포맷과 10편 아웃라인

구현을 시작하기 전에 결정한 핵심 내용을 Medium 시리즈 10편으로 남기기 위한 기준 문서다.
모든 편은 아래 **공통 포맷**과 **작성 규칙**을 따르고, 편별 내용은 **아웃라인**에서 시작한다.

## 1. 참고한 글과 공통점

| 참고 글 | 도입 | 본문 전개 | 마무리 |
|---|---|---|---|
| 멀티-에이전트 LLM 코인 투자 팀 만들기 | 분야의 흐름 → 계기 → "이 글에서는 ~ 공유하고자 합니다" → INDEX 목록 | 기존 한계 ①②③ → 내 구조 → 구현(예산·API·언어) → 논문과의 차이점 → 평가 지표 | 가장 어려웠던 점, 다음에 할 일, 번호 붙은 레퍼런스 |
| BOLT | 서지 정보 → 한 문단 요약 → 기존 기법의 한계 | 핵심 아이디어 → 구조(그림) → 단계 목록·표 → 실제 명령과 출력 | 실측 결과로 효과 확인, 권장 옵션 |
| 언제까지 블룸 필터만 쓸 것인가 | 질문 → 가장 단순한 답 → 한계 → 수치로 대안 제시 → 글의 범위 | 사용 맥락 → 배경 이론 → 핵심 구조 → 최적화 → 변형 비교 | 성능 그래프, 참고 문헌. 본문 중간에 "의문점이 들었던 부분"을 솔직하게 적음 |

세 글의 공통 패턴은 다음과 같다.

1. **질문이나 한계로 시작한다.** "무엇을 만들었다"가 아니라 "왜 기존 방식으로는 부족한가"부터 쓴다.
2. **첫 화면에 숫자가 있다.** 27% 메모리 절감, 월 10만 원 예산, 최대 7% 성능 향상처럼 독자가 기억할 값을 도입부에 둔다.
3. **범위를 먼저 밝힌다.** "이번 글에서는 A와 B를 살펴보겠습니다"로 다루는 것과 다루지 않는 것을 정한다.
4. **배경 → 핵심 구조 → 실제 적용 → 결과 순서로 간다.** 이론만 쓰거나 결과만 쓰지 않는다.
5. **그림마다 캡션과 출처가 붙는다.**
6. **한계와 의문을 숨기지 않는다.** "학술적 가치가 높다고 보기는 어렵지만", "그 부분에 대한 언급은 없었습니다"처럼 쓴다.
7. **번호가 붙은 레퍼런스로 끝난다.** 본문에서는 [1], [2]로 인용한다.

## 2. 시리즈 공통 포맷

### 제목·부제

- 제목: `[시리즈 번호] 질문형 또는 대비형 한 문장`
  - 예: `[NU-54V-DK 02] 결제 기기 하나에 왜 제품이 10개나 필요할까`
- 부제(Medium 부제 칸): 이 글이 답하는 내용을 한 문장으로
- 시리즈 표기: 제목 앞에 `[NU-54V-DK NN]`을 붙이고, 본문 맨 위에 시리즈 안내 한 줄

### 본문 뼈대

```markdown
> NU-54V-DK 여행자 결제 기기 시리즈 NN/10 · 이전 글: <제목> (<Medium URL>)

(도입 3~5문단)
- 1문단: 독자가 공감할 질문이나 장면
- 2문단: 가장 단순한 답과 그 한계
- 3문단: 이 프로젝트의 선택과 핵심 숫자 1~2개
- 4문단: "이번 글에서는 ~을 살펴보겠습니다" (다루지 않는 것도 한 줄)

### INDEX
- 섹션 1 ~ 섹션 N (4~6개)

## 1. 배경: 왜 이 문제가 생기는가
기존 방식, 제약 조건, 실패 사례. 한계가 여러 개면 ①②③ 대신 "첫째, 둘째"나 번호 목록을 쓴다.

## 2. 핵심 구조: 우리가 고른 방식
다이어그램 1장(직접 작성) + 캡션. 구성 요소별로 짧은 목록.

## 3. 동작 흐름 또는 상세 설계
정상 흐름을 순서대로 쓰고, 실패·복구 흐름을 따로 쓴다. 표는 나란히 비교할 때만 쓴다.

## 4. 실제 적용 / 실험
명령, 설정, 로그, 사진, 트랜잭션 화면. 아직 하지 않은 것은 "미실행"으로 쓴다.

## 5. 고민했던 점과 남은 한계
대안과 그 대안을 고르지 않은 이유, 아직 모르는 것, 다음 편에서 확인할 것.

## 마무리
3~4문장: 이번 편의 결론 한 줄, 가장 어려웠던 점, 다음 편 예고.
```

### 분량과 구성 요소

| 요소 | 기준 |
|---|---|
| 분량 | 본문 2,500~4,000자 (읽는 시간 7~10분) |
| 그림 | 2~4장. 대표 그림 1장은 도입부 바로 뒤에 둔다 |
| 캡션 | 모든 그림에 붙인다. 직접 작성, AI 생성, 제조사 자료 중 무엇인지와 출처를 적는다 |
| 코드·명령 | 실행한 것만 넣고, 출력은 핵심 줄만 남긴다 |
| 표 | 한 편에 최대 2개. 비교할 때만 쓴다 |
| 인용 블록 | 본문 흐름에서 벗어나는 보충 설명에만 쓴다 (참고 글 1의 ReAct 설명 방식) |

### 문체

- **존댓말 `~습니다`로 통일한다.** 참고 글 3편 중 2편이 이 문체이고, 입문자도 읽기 편하다.
  - 트레이드오프: 기존 1주차 원고(`medium-*.md`)는 `~다` 문체라서 시리즈 안에서 문체가 바뀐다. 기존 원고와 맞추려면 `~다`로 통일해도 되지만, 10편 전체에서는 한 가지만 쓴다.
- 1인칭 "저는/저희 팀은"을 쓴다. 판단의 주체를 드러낸다.
- 기술 용어는 처음 나올 때 `한국어(English)`로 한 번 풀고, 그다음부터는 한 가지 표기만 쓴다.

### 공개 글 안전 규칙

- 키 생성·보관·서명 내부 구현, 실제 주소·키·토큰·계정·RPC 비밀값은 넣지 않는다. 캡처 이미지도 같은 기준으로 확인한다.
- 테스트넷과 대체 USDC를 쓰는 PoC라는 점을 매 편 한 번 이상 밝힌다. 실자산 결제 서비스로 오해받지 않게 한다.
- 실행하지 않은 결과를 성공으로 쓰지 않는다.

## 3. 10편 아웃라인

시리즈 흐름: **문제(1) → 전체 구조(2~3) → 기기(4~5) → 지갑·결제(6~8) → 운영 수명주기(9) → 구현 착수(10)**

### 01. 외국인 여행자는 카페에서 왜 코인으로 결제하기 어려울까

- 한 문장: 카페 키오스크 주문을 손 안의 기기에서 확인하고 버튼으로 승인하는 테스트넷 결제 기기
- 배경: 여행자의 현지 결제 불편, 휴대폰 지갑 앱의 확인 경험 한계
- 핵심: 물리 버튼 승인을 고른 이유, 첫 성공 경로 한 줄(키오스크 → BLE → 기기 승인 → StableNet → Indexer → 영수증)
- 한계: PoC 범위, 법률·규제 검토 제외
- 출처 문서: `medium-three-month-team-project.md` 1장, `proximity-wallet-kiosk.md`

### 02. 결제 기기 하나에 왜 제품이 10개나 필요할까

- 배경: 기기와 키오스크만 만들면 된다고 생각했지만 실제 사용 장면을 따라가 보니 부족했던 이유
- 핵심: Local·Cloud·Blockchain 3영역, P01~P10 역할, C1~C9 통신 경계 (통합 다이어그램)
- 흐름: 한 주문이 각 제품을 지나는 순서, 상태를 소유하는 제품
- 한계: 범위가 3명·12주에 비해 넓다는 점을 솔직하게 적음
- 출처 문서: `planning/product-wbs-overview.md`, `assets/diagrams/product-architecture-one-page.*`

### 03. 중요한 순서가 아니라 막히는 순서로: 12주 WBS

- 배경: 기능 중요도로 정한 일정이 통합 시점에 무너지는 이유
- 핵심: C0~C3 우선순위, M0~M7 관문, 57개 작업 패키지 (간트 차트)
- 상세: 완료 기준 = 같은 주문 ID가 전 구간을 통과하고 실패 후에도 결과를 다시 찾을 수 있음
- 한계: 3주차 기준 실제 진척과 계획의 차이, 재조정 결과
- 출처 문서: `planning/product-worklist-and-12week-wbs.*`, `assets/diagrams/product-wbs-gantt.png`

### 04. Zephyr를 처음 쓰는 사람의 NU-54V-DK bring-up 기록

- 배경: 보드 리비전, 보드 타깃, 핀을 추정하지 않고 확인해야 하는 이유
- 실험: 빌드·플래시, LED·버튼, 부팅 로그, 타이머, S25 BLE 광고·연결·GATT 쓰기·알림 (BR-01~09)
- 결과: 성공/실패 표, Flash·RAM 사용량, 막힌 점과 해결
- **실험을 마친 뒤 작성한다.** 결과가 없으면 발행 순서를 뒤로 미룬다
- 출처 문서: `nu54v-basic-peripheral-bringup-log.md`

### 05. 키오스크와 기기는 BLE로 무엇을 주고받아야 할까

- 배경: BLE 연결이 끊겨도 체인에 제출된 결제는 취소되지 않는다는 점
- 핵심: 결제 세션 메시지(주문 ID·매장·금액·만료·요청 버전), 인증된 세션, 중복 요청 처리
- 흐름: 정상 흐름과 실패 흐름(끊김, 만료, 같은 요청 두 번 도착)
- 한계: 실측 전송 크기와 연결 안정성은 04편 결과에 의존
- 출처 문서: `specifications/interface-contracts.md`, `specifications/design-baseline-contract.md`

### 06. 하드웨어 지갑과 Cloud Wallet, 지갑을 왜 두 개로 나눴나

- 배경: 하나의 지갑이 편의성과 물리 확인을 동시에 맡기 어려운 이유
- 핵심: 기기 = 눈으로 확인하고 직접 승인하는 지갑, MPC 2-of-3 Cloud Wallet = 앱 편의와 복구
- 상세: 어떤 요청을 어느 지갑이 서명했는지 영수증과 운영 기록에서 추적하는 방법
- 공개 범위: 키 처리 내부 구현은 쓰지 않고 역할 경계만 설명
- 출처 문서: `specifications/wallet-control-recovery-design.md`, `specifications/social-wallet-recovery-design.md`

### 07. 결제 한 건의 수명: 주문 ID가 영수증이 되기까지

- 배경: 트랜잭션은 제출됐는데 키오스크 응답이 끊기면 다시 결제시켜야 하는가
- 핵심: 주문 ID, 멱등 처리, 제출·미확정·확정·실패 상태 구분
- 흐름: 응답 유실 뒤 Indexer와 주문 ID로 기존 결과를 찾는 과정
- 한계: 확정으로 볼 블록 수와 만료 시간 같은 정책 수치
- 출처 문서: `specifications/commerce-lifecycle-design.md`, `specifications/commerce-reconciliation-integration.md`

### 08. StableNet 테스트넷, 대체 USDC, 그리고 Indexer 재사용

- 배경: 체인 이벤트를 그대로 믿기 어려운 이유(중복, 재시작, reorg)
- 핵심: dummy USDC·WKRC 배포 정보, 기존 Go Indexer 재사용 범위와 수정점
- 실험: 테스트넷 전송 1건과 Indexer 수집 결과
- 한계: 기존 코드에서 부족한 부분과 새로 만들 부분
- 출처 문서: `stablenet-testnet-baseline.md`, `indexer-integration-and-test-token.md`, `stable-contract-reuse-plan.md`

### 09. 빌려준 기기를 돌려받을 때: 반납, 잔액 이전, 초기화

- 배경: 대여 기기에는 개인 키와 잔액이 남는다는 점
- 핵심: 반납 흐름(잔액 이전 → 권한 해제 → 초기화 증거 → 재대여 조건)
- 흐름: 반납 도중 실패하면 어디서 다시 시작하는지
- 한계: 실기기 검증 전의 설계라는 점
- 출처 문서: `specifications/return-recovery-design.md`, `specifications/lifecycle-journey-acceptance.md`

### 10. 설계를 멈추고 구현을 시작하는 기준

- 배경: 설계 문서가 계속 늘어나는 것이 오히려 위험한 이유
- 핵심: 설계 동결 `DF-20260920-01`의 결정 20개, 계약 8묶음, 환경 준비 7개
- 상세: "완료"의 정의(실제 대상에서 정상과 실패를 실행하고 증거를 남김), 3인 역할과 교차 검토
- 마무리: 시리즈 회고, 이후 구현기 시리즈 예고
- 출처 문서: `planning/design-freeze-checkpoint.md`, `REPOSITORY-CHECKPOINT.md`

## 4. 발행 전 체크리스트

- [ ] 제목이 `[NU-54V-DK NN]` 형식이고 질문형 또는 대비형이다
- [ ] 도입 4문단 안에 핵심 숫자와 글의 범위가 있다
- [ ] INDEX와 본문 섹션 제목이 일치한다
- [ ] 모든 그림에 캡션과 출처가 있다
- [ ] 실행하지 않은 결과를 성공으로 쓰지 않았다
- [ ] 키·주소·토큰·계정 같은 민감정보가 본문과 캡처에 없다
- [ ] PoC·테스트넷 범위를 밝혔다
- [ ] 이전 편과 다음 편 링크를 넣었다
- [ ] 레퍼런스 번호가 본문 인용과 일치한다
