# 가맹점을 확인하는 결제 기기, 12주 제작기: 포맷과 10편 목차

NU-54V-DK로 가맹점을 검증하는 결제 서명 기기를 만드는 과정을 Medium 시리즈 10편으로 남기기 위한 기준 문서다.
W3부터 W12까지 한 주에 한 편씩, 그 주의 작업과 게이트 결과를 쓴다. 모든 편은 아래 **공통 포맷**과 **작성 규칙**을 따르고, 편별 내용은 **목차**에서 시작한다.

## 1. 참고한 글과 공통점

| 참고 글 | 도입 | 본문 전개 | 마무리 |
|---|---|---|---|
| 멀티-에이전트 LLM 코인 투자 팀 만들기 | 분야의 흐름 → 계기 → "이 글에서는 ~ 공유하고자 합니다" → INDEX 목록 | 기존 한계 ①②③ → 내 구조 → 구현(예산·API·언어) → 논문과의 차이점 → 평가 지표 | 가장 어려웠던 점, 다음에 할 일, 번호 붙은 레퍼런스 |
| BOLT | 서지 정보 → 한 문단 요약 → 기존 기법의 한계 | 핵심 아이디어 → 구조(그림) → 단계 목록·표 → 실제 명령과 출력 | 실측 결과로 효과 확인, 권장 옵션 |
| 언제까지 블룸 필터만 쓸 것인가 | 질문 → 가장 단순한 답 → 한계 → 수치로 대안 제시 → 글의 범위 | 사용 맥락 → 배경 이론 → 핵심 구조 → 최적화 → 변형 비교 | 성능 그래프, 참고 문헌. 본문 중간에 "의문점이 들었던 부분"을 솔직하게 적음 |

세 글의 공통 패턴은 다음과 같다.

1. **질문이나 한계로 시작한다.** "무엇을 만들었다"가 아니라 "왜 기존 방식으로는 부족한가"부터 쓴다.
2. **첫 화면에 숫자가 있다.** 27% 메모리 절감, 월 10만 원 예산, 최대 7% 성능 향상처럼 독자가 기억할 값을 도입부에 둔다.
3. **범위를 먼저 밝힌다.** "이번 글에서는 A와 B를 살펴보겠습니다"로 다루는 것과 다루지 않는 것을 정한다.
4. **배경 → 핵심 구조 → 실제 적용 → 결과 순서로 간다.** 이론만 쓰거나 결과만 쓰지 않는다.
5. **그림마다 캡션과 출처가 붙는다.**
6. **한계와 의문을 숨기지 않는다.** "학술적 가치가 높다고 보기는 어렵지만", "그 부분에 대한 언급은 없었습니다"처럼 쓴다.
7. **번호가 붙은 레퍼런스로 끝난다.** 본문에서는 [1], [2]로 인용한다.

### 문체

- **존댓말 `~습니다`로 통일한다.** 참고 글 3편 중 2편이 이 문체이고, 입문자도 읽기 편하다.
  - 트레이드오프: 기존 1주차 원고(`medium-*.md`)는 `~다` 문체라서 시리즈 안에서 문체가 바뀐다. 기존 원고와 맞추려면 `~다`로 통일해도 되지만, 10편 전체에서는 한 가지만 쓴다.
- 1인칭 "저는/저희 팀은"을 쓴다. 판단의 주체를 드러낸다.
- 기술 용어는 처음 나올 때 `한국어(English)`로 한 번 풀고, 그다음부터는 한 가지 표기만 쓴다.

### 공개 글 안전 규칙

- 키 생성·보관·서명 내부 구현, 실제 주소·키·토큰·계정·RPC 비밀값은 넣지 않는다. 캡처 이미지도 같은 기준으로 확인한다.
- 테스트넷과 대체 USDC를 쓰는 PoC라는 점을 매 편 한 번 이상 밝힌다. 실자산 결제 서비스로 오해받지 않게 한다.
- 실행하지 않은 결과를 성공으로 쓰지 않는다.

### 1부. 무엇을 만들까

#### 01. 10개 제품을 설계하고 6개만 만들기로 한 이유 (W3)

- 도입 질문: 외국인 여행자는 카페에서 왜 코인으로 결제하기 어려울까, 휴대폰 QR 지갑으로는 무엇이 부족한가
- 배경: 처음 설계한 10개 제품(앱, MPC, DeFi, 여행 AI 포함)이 3명·12주에 비해 넓었던 이유
- 핵심: 가맹점을 검증하는 결제 서명 기기라는 방향, X-bar 이론으로 137개 문서를 분류한 그래프에서 드러난 두 기준선의 충돌(F1~F3), 만드는 6개와 설계만 하는 4개
- 흐름: 한 주문이 P04 → P01 → P06 → P07을 지나는 순서
- 한계: 줄인 범위에서 빠진 기능(소셜 로그인, Cloud Wallet, 환불), 사전 예치의 custodial 성격, 법률·규제 검토 제외
- 사진·증거: 보드 실물, 제품 구조 다이어그램, X-bar 문서 그래프 캡처
- 출처 문서: `research/payment-hw-wallet-direction/README.md`, `analysis/xbar/README.md`, `planning/design-freeze-checkpoint-02.md`

### 2부. 기반 다지기

#### 02. 보드를 처음 연결한 날: 이 보드는 무엇인가 (W4)

- 도입 질문: 처음 받은 보드가 어떤 칩과 디버거를 쓰는지 추정하지 않고 어떻게 확인할까
- 핵심: USB 정보와 DAPLink `DETAILS.TXT`로 보드 식별(nRF54L15, CMSIS-DAP), NCS v3.4.1 설치와 CLI·VS Code 병행, 플래시 전 백업, 제조사 board package(`nu54v_dk`) 활용
- 실험: 예제 빌드·플래시, BR-01~BR-08(부팅 로그, LED, 버튼, 타이머, BLE 광고·연결·GATT 쓰기·알림), 외부 SE 데이터시트 확인
- 결과: W4 게이트 통과 여부, Flash·RAM 사용량, 막힌 점과 해결
- 사진·증거: 보드 앞뒷면, USB 연결 상태, `DETAILS.TXT`, 빌드·플래시 터미널, 부팅 로그, LED·버튼 동작, nRF Connect 앱 BLE 화면
- 출처 문서: `nu54v-basic-peripheral-bringup-log.md`, `products/p01/plan.md`

#### 03. 키는 기기 밖으로 나가지 않는다 (W5)

- 도입 질문: 대여 기기의 키를 어떻게 만들고, 누가 서명을 허락하는가
- 핵심: TRNG 키 생성, TF-M secure partition 봉인과 SE 전까지의 waiver, PIN과 잠금, 버튼 토큰을 digest 한 건에 묶는 서명 권한 경계
- 병행 작업: 키오스크 앱 골격과 BLE central
- 한계: 표시와 서명의 일치는 non-secure 코드가 무결하다는 가정 아래의 주장
- 공개 범위: 키 처리 내부 구현은 쓰지 않고 경계만 설명
- 사진·증거: 신뢰 경계 다이어그램, 키 생성·초기화 시험 로그(값 제거)
- 출처 문서: `products/p01/srs.md`, `products/p01/design.md`

#### 04. 개인 키가 새도 잔액이 다 빠지지 않게: 사전 예치 정산 컨트랙트 (W6)

- 도입 질문: 일반 지갑은 키가 새면 자산이 모두 빠진다. 결제 전용 컨트랙트로 무엇을 막을 수 있나
- 핵심: depositFor 사전 예치, settle 검사 순서, 건당·일일 한도, unordered nonce, 가맹점 registry, 지연 출금
- 실험: Foundry 시험, 8283 테스트넷 배포와 소프트웨어 서명 결제 1건(W6 게이트)
- 한계: 감사받지 않은 컨트랙트, 운영자 키 단일 장애점
- 사진·증거: 컨트랙트 구조 다이어그램, Foundry 시험 결과, explorer의 PaymentSettled(주소·해시 축약)
- 출처 문서: `products/p06/srs.md`, `products/p06/design.md`

### 3부. 결제를 통과시키기

#### 05. 버튼을 누르자 블록에 결제가 찍혔다 (W7)

- 도입 질문: 키오스크, 기기, 운영 도구, 체인이 처음으로 한 흐름에 모이면 무엇이 필요한가
- 핵심: BLE 프로토콜(LE Secure Connections, 조각 처리, session.open부터 payment.result까지), 대여 셋업과 TimeAnchor, 가맹점 attestation과 기기 표시
- 실험: 보드 내장 키로 첫 실기 end-to-end 결제(W7 게이트)
- 결과: 게이트 결과와 걸린 시간, 실패했다면 컷 순서 적용
- 사진·증거: 메시지 순서 다이어그램, 페어링 화면, 기기 화면의 가맹점·금액 표시, 영상 캡처
- 출처 문서: `specifications/protocol/payment-protocol.md`, `products/p05/design.md`

#### 06. 결제는 됐는데 화면은 실패라고 한다 (W8)

- 도입 질문: 트랜잭션은 제출됐는데 응답이 끊기면 다시 결제시켜야 하는가
- 핵심: eth_call 시뮬레이션, finalized PaymentSettled로 판정하는 이유, approved·refused·failed·Checking, 거절 코드와 층
- 이야기: 설계 검토에서 찾은 결함(같은 서명 재전송이 NONCE_REPLAYED로 끝나 이중 결제를 부르는 문제)과 검사 순서를 바꾼 과정
- 한계: p95 지연 목표는 W7 이후 실측으로 정한다
- 사진·증거: 결제 상태 기계 다이어그램, 재전송 시험 로그
- 출처 문서: `specifications/protocol/payment-protocol.md` 7·8절, `products/p04/design.md`

#### 07. 키를 secure element로 옮기거나, 옮기지 못하거나 (W9)

- 도입 질문: nRF54L15만으로는 왜 키 보호가 충분하지 않은가
- 핵심: 외부 SE로 키를 감싸는 통합, 또는 W7 게이트 결과에 따른 컷과 TF-M waiver 판단, NFC 핸드오버
- 결과: W9 게이트 결과
- 사진·증거: SE 연결 사진, 서명 로그, NFC 태그 읽기 화면
- 출처 문서: `products/p01/plan.md`, `planning/product-worklist-and-12week-wbs-02.md` 2절

### 4부. 운영과 증명

#### 08. 빌려준 기기를 돌려받는 법 (W10)

- 도입 질문: 대여 기기에는 키와 예치 잔액이 남는다. 반납은 어떤 순서여야 안전한가
- 핵심: closeAccount → finalized 확인 → 운영자 서명 DeviceReset, 지연 출금, MCUboot 서명 이미지와 AP-Protect, 영수증용 최소 indexer
- 흐름: 반납 도중 실패하거나 전원이 끊겼을 때(재-anchor, PIN 잠금)
- 사진·증거: 대여·반납 흐름 다이어그램, 운영 스크립트 로그, 서명 안 된 이미지 거부 로그

#### 09. 20번 연속 성공과 8가지 거절 (W11)

## 4. 발행 전 체크리스트

- [ ] 레퍼런스 번호가 본문 인용과 일치한다
