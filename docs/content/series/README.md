# 가맹점을 확인하는 결제 기기, 12주 제작기: 포맷과 연재 목차

NU-54V-DK로 가맹점을 검증하는 결제 서명 기기를 만드는 과정을 Medium 시리즈로 남기기 위한 기준 문서다.
01편에 초기 계획과 첫 펌웨어를 합쳤다. 이후 편은 주차별 작업과 게이트 결과를 따라가되, 실제 확인한 증거에 맞춰 제목과 편수를 조정한다. 모든 편은 아래 **공통 포맷**과 **작성 규칙**을 따르고, 편별 내용은 **목차**에서 시작한다.

## 1. 참고한 글과 공통점

| 참고 글 | 도입 | 본문 전개 | 마무리 |
|---|---|---|---|
| 멀티-에이전트 LLM 코인 투자 팀 만들기 | 분야의 흐름 → 계기 → "이 글에서는 ~ 공유하고자 합니다" → INDEX 목록 | 기존 한계 ①②③ → 내 구조 → 구현(예산·API·언어) → 논문과의 차이점 → 평가 지표 | 가장 어려웠던 점, 다음에 할 일, 번호 붙은 레퍼런스 |
| BOLT | 서지 정보 → 한 문단 요약 → 기존 기법의 한계 | 핵심 아이디어 → 구조(그림) → 단계 목록·표 → 실제 명령과 출력 | 실측 결과로 효과 확인, 권장 옵션 |
| 언제까지 블룸 필터만 쓸 것인가 | 질문 → 가장 단순한 답 → 한계 → 수치로 대안 제시 → 글의 범위 | 사용 맥락 → 배경 이론 → 핵심 구조 → 최적화 → 변형 비교 | 성능 그래프, 참고 문헌. 본문 중간에 "의문점이 들었던 부분"을 솔직하게 적음 |

세 글의 공통 패턴은 다음과 같다.

1. **질문이나 한계로 시작한다.** "무엇을 만들었다"가 아니라 "왜 기존 방식으로는 부족한가"부터 쓴다.
2. **첫 화면에 숫자가 있다.** 27% 메모리 절감, 월 10만 원 예산, 최대 7% 성능 향상처럼 독자가 기억할 값을 도입부에 둔다.
3. **범위를 먼저 밝힌다.** "이번 글에서는 A와 B를 살펴보겠습니다"로 다루는 것과 다루지 않는 것을 정한다.
4. **배경 → 핵심 구조 → 실제 적용 → 결과 순서로 간다.** 이론만 쓰거나 결과만 쓰지 않는다.
5. **그림마다 캡션과 출처가 붙는다.**
6. **한계와 의문을 숨기지 않는다.** "학술적 가치가 높다고 보기는 어렵지만", "그 부분에 대한 언급은 없었습니다"처럼 쓴다.
7. **번호가 붙은 레퍼런스로 끝난다.** 본문에서는 [1], [2]로 인용한다.

## 2. 시리즈 공통 포맷

### 제목·부제

- 제목: `[시리즈 번호] 질문형 또는 대비형 한 문장`
  - 예: `[NU-54V-DK 02] 보드를 처음 연결한 날: 이 보드는 무엇인가`
- 부제(Medium 부제 칸): 이 글이 답하는 내용을 한 문장으로
- 시리즈 표기: 제목 앞에 `[NU-54V-DK NN]`을 붙이고, 본문 맨 위에 시리즈 안내 한 줄

### 본문 뼈대

```markdown
> 스테이블코인 결제 기기 제작기 NN · 이전 글: <제목> (<Medium URL>)

(도입 3~5문단)
- 1문단: 독자가 공감할 질문이나 장면
- 2문단: 가장 단순한 답과 그 한계
- 3문단: 이 프로젝트의 선택과 핵심 숫자 1~2개
- 4문단: "이번 글에서는 ~을 살펴보겠습니다" (다루지 않는 것도 한 줄)

### INDEX
- 섹션 1 ~ 섹션 N (4~6개)

## 1. 배경: 왜 이 문제가 생기는가
기존 방식, 제약 조건, 실패 사례. 한계가 여러 개면 ①②③ 대신 "첫째, 둘째"나 번호 목록을 쓴다.

## 2. 핵심 구조: 우리가 고른 방식
다이어그램 1장(직접 작성) + 캡션. 구성 요소별로 짧은 목록.

## 3. 동작 흐름 또는 상세 설계
정상 흐름을 순서대로 쓰고, 실패·복구 흐름을 따로 쓴다. 표는 나란히 비교할 때만 쓴다.

## 4. 실제 적용 / 실험
명령, 설정, 로그, 사진, 트랜잭션 화면. 아직 하지 않은 것은 "미실행"으로 쓴다.

## 5. 고민했던 점과 남은 한계
대안과 그 대안을 고르지 않은 이유, 아직 모르는 것, 다음 편에서 확인할 것.

## 마무리
3~4문장: 이번 편의 결론 한 줄, 가장 어려웠던 점, 다음 편 예고.

### 레퍼런스
- [1] 제목 — 링크
- [2] ...

`#NUCODE` `#누코드` `#NU54VDK` `#누코더스` `#Nucoders`
```

### 분량과 구성 요소

| 요소 | 기준 |
|---|---|
| 분량 | 본문 2,500~4,000자 (읽는 시간 7~10분) |
| 그림 | 2~4장. 대표 그림 1장은 도입부 바로 뒤에 둔다 |
| 캡션 | 모든 그림에 붙인다. 직접 작성, AI 생성, 제조사 자료 중 무엇인지와 출처를 적는다 |
| 코드·명령 | 실행한 것만 넣고, 출력은 핵심 줄만 남긴다 |
| 표 | 한 편에 최대 2개. 비교할 때만 쓴다 |
| 인용 블록 | 본문 흐름에서 벗어나는 보충 설명에만 쓴다 (참고 글 1의 ReAct 설명 방식) |

### 문체

- **존댓말 `~습니다`로 통일한다.** 참고 글 3편 중 2편이 이 문체이고, 입문자도 읽기 편하다.
  - 트레이드오프: 기존 1주차 원고(`medium-*.md`)는 `~다` 문체라서 시리즈 안에서 문체가 바뀐다. 기존 원고와 맞추려면 `~다`로 통일해도 되지만, 시리즈 전체에서는 한 가지만 쓴다.
- 1인칭 "저는/저희 팀은"을 쓴다. 판단의 주체를 드러낸다.
- 기술 용어는 처음 나올 때 `한국어(English)`로 한 번 풀고, 그다음부터는 한 가지 표기만 쓴다.

### 공개 글 안전 규칙

- 키 생성·보관·서명 내부 구현, 실제 주소·키·토큰·계정·RPC 비밀값은 넣지 않는다. 캡처 이미지도 같은 기준으로 확인한다.
- 테스트넷과 대체 USDC를 쓰는 PoC라는 점을 매 편 한 번 이상 밝힌다. 실자산 결제 서비스로 오해받지 않게 한다.
- 실행하지 않은 결과를 성공으로 쓰지 않는다.
