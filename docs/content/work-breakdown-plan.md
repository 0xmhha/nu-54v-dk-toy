# 실행 작업 목록과 정리 순서

**최신 인계(2026-09-19):** [구현 전 설계 인계서](planning/preimplementation-handoff.md)에 DS01~08과 15요구·104작업·320단계를 연결했다. [작업별 카드](planning/preimplementation-task-handoffs.md), [계약 보완안20개](specifications/preimplementation-contract-overlay.md), DID/STO/x402·녹음/여행/AI·운영/릴리스 상세를 추가했다. 논리 초안은 작성되었으나 선택 의존 프로필/wire/물리 설계 고정과 기준 계약 채택은 남아 있으며, 아래 과거 경과의 “다음 설계”는 작성 시점 기준이다. 제품 구현·실제 검증은 미수행, 역할·공수는 미배정이다.

작성: 2026-09-18. 사용자의 지시에 따라 **15개 요구사항 전부를 앱 연동까지 12주 안에 완료**하는 것을 고정 계획 전제로 둔다. 총 3명이며, 개인별 역할 배정과 작업량 산정보다 작업 목록 구체화를 먼저 진행한다. 기존 A/B/C 배정·주차별 표는 참고 초안으로 보류한다. [전체 범위](twelve-week-completion-scope-v3.md).

## 1. 이번에 만든 작업 목록

**최신은 [승인 기준 통합](specifications/approval-baseline.md)이다.** 병합 전 파일 174개를 보존해 기존 검증 10개를 재현하고, 승인 HTTP·BLE·권한·화면·논리 저장을 현재 기준에 반영했다. 현재 API110개/권한60개/논리저장28개이며 BLE34개/화면37개는 유지했다. [물리 저장 상세](specifications/approval-physical-storage-design.md)에 테이블 후보 16개·이행 8단계·장애 복구 사례 17개를 추가했다. [결제·환불 대사 연결안](specifications/commerce-reconciliation-integration.md)에 현재 호환 HTTP5개·이벤트2개·저장4개·원자처리4개를 정리했다. 기준 병합과 정책 선택은 대기하며 [소비자 보정·재처리 계약](specifications/commerce-consumer-repair-design.md)에 5개 소비자/6개 논리자원/7단계 재구축/22개 실행 수용 사례를 정리했다. [매출·정산/운영 명령 계약](specifications/settlement-ops-contracts.md)에 기존경로5개와 미등록후보2개를 상세화했다. [미병합 설계 통합표](planning/integration-adoption-matrix.md)에 DI8개·수용24개·15요구/19결정을 연결했다. [반납 호출 계약](specifications/return-route-contracts.md)에 HTTP 10개/BLE 6쌍과 같은 작업·세대의 재대여 조건 조회를 연결했다. [대여 등록·반납 취소 계약](specifications/rental-admission-cancel.md)에 API045 예약/활성화와 초기화 허가 발급 전 양측 제한 해제를 연결했다. HTTP9개·BLE4쌍의 후보이며 [반납·등록·취소 저장 설계](specifications/lifecycle-storage-design.md)에 테이블 후보14개·원자 경계12개·펌웨어 영속영역4개·이행8단계·미실행 복구26사례를 연결했다. [등록 인증·동의·반납 분기·대기 응답](specifications/lifecycle-bootstrap-contracts.md)에 HTTP후보9개/BLE후보3개와 대기 응답17경로를 연결했다. [등록 세션 복구·동의 철회·공동 채택 기준](specifications/enrollment-continuity-adoption.md)에 원 holder의 세션 복구, 등록 전용 철회, 저장 매핑7개·원자 매핑8개·채택 기준12개를 정리했다. [등록·반납 종단 수용 명세](specifications/lifecycle-journey-acceptance.md)에 사용자흐름16개/원사례107개/공동채택5묶음/열린항목5개를 연결했다. 실제 실행0회이며 [전체15요구 설계 점검](planning/full-scope-design-review.md)에서 104개 작업·320개 세부작업을 보존하고 다음 설계를 8묶음으로 정리했다. [DS-01 기기 동시동작·FOTA 공존 후보](specifications/device-coexistence-design.md)에 작업10개·방향별공존100쌍·FOTA전이10개·미실행수용28사례를 연결했다. [DS-02 소셜 로그인·두 지갑·MPC 복구 연결 후보](specifications/social-wallet-recovery-design.md)에 인증전이11개·MPC전이11개·권한영향8개·미실행수용32사례를 정리했다. [DS-03 키오스크 종단 연결 후보](specifications/kiosk-commerce-journey-design.md)에 12여정·표시상태10개·정책입력/계약보강 각7개·미실행수용34사례를 연결했다. [DS-04 StableNet 호환 후보](specifications/stablenet-compatibility-design.md)에 manifest8경계·자산4종·온체인9영역·Indexer8단계·미실행34사례를 연결했다. [DS-05 상품별 처리 후보](specifications/market-product-design.md)에 상품4영역·가격행위10종·keeper6단계·합성산술4개·미실행32사례를 연결했다. 다음은 DS-06 DID·STO·x402 자격/지급 계약이다. 아래 후보/계획의 미병합 표기는 작성 당시 상태이며, 제품 구현과 새 SQL 실행 검증은 계속 미수행이다.

최신 [승인 기준 반영 순서·호환 수용표](specifications/approval-adoption-plan.md)는 이력/validator 책임 보존과 기준 반영 6단계, profile 11영역, 승인 수용 시나리오 24개를 기존 COMP 26개에 연결했다. 문서 채택·실제 tuple 호환·현재 거래 권한을 별도로 판정하며 모든 실행 pins/evidence는 미기입이다. 다음은 재현 가능한 checkpoint 보존과 설계 기준 통합이다. 이력 생성·기준 병합·제품 구현은 이번에 수행하지 않았다.

최신 [승인 HTTP·권한·화면·저장 연결](specifications/approval-integration-contracts.md)은 기존 API 10개+제안 AC 3개의 전체 논리 요청/응답, 권한 매핑, 화면 17개의 변경/회귀 범위, 저장 자원 5개와 원자 처리 5개를 연결한다. 부모/자식 operation과 결과 공개, 환불의 실제 signer 앱 경로, 자격 교체/철회 경쟁을 구분했다. 기준 명세 병합과 구현은 미수행이며 다음은 반영 순서·버전/profile 호환 수용표다.

최신 [공통 승인 schema·권한 자격 계약](specifications/approval-access-contracts.md)은 개인/guest/환불 타입, 개인 BLE·Cloud 결과 조회, AC-01~03 발급·교체·철회를 설계 후보로 연결했다. 응답 유실 시 원 발급 요청을 통한 교체와 병렬 교체의 단일 successor 조건을 포함한다. 22개 실제 동작 사례는 미실행이며 전체 HTTP envelope·권한/화면·저장 통합 및 기준 병합은 후속 설계다.

현재 [승인 계약 병합 계획](specifications/approval-contract-merge-plan.md)은 개인·guest·환불의 차이 8개를 대조하고 API 10개·BLE 5개·직접 참조 화면 17개를 반영/회귀 범위로 지정했다. 5개 설계 병합 묶음과 미완성인 개인 BLE·개인 Cloud 결과 조회·권한 자격 발급 경계를 명시했다. 현재는 병합 범위 정리 완료이며 공통 schema 작성과 기준 명세 실제 병합은 다음 설계 작업이다.

후속 [키오스크 결제·점주 환불 승인 계약](specifications/source-approval-contracts.md)은 5개 HTTP·5개 BLE 메시지 쌍에 주소 소유 증명, 최종 승인, 원천별 서명 결과를 연결한다. guest 기기 단독 경로를 유지하고 환불 승인자와 실제 signer의 권한을 구분했다. 후보의 형태·필드 대조를 검증했으며 16개 실제 동작 검토 사례는 미실행이다. 기준 계약·권한·DB 병합과 구현은 미수행이다.

후속 [승인·제출 저장 경계와 원천 연결](specifications/signing-submission-storage-design.md)은 개인 송금·guest 키오스크 결제·점주 환불을 논리 자원 8개와 원자 변경 6개에 연결했다. outbox 접수와 전송 허가를 구분하고, 철회 경쟁·lease 만료·중복 거래·환불 확정 철회 등 20개 미실행 사례를 정리했다. 신규 SQL이나 제품 구현을 추가하지 않았다.

후속 [지갑 선택·승인 API 계약 후보](specifications/wallet-api-contracts.md)는 8개 기존 endpoint의 전체 논리 HTTP 요청/응답을 연결한다. 개인 EOA 송금부터 승인 문맥과 실제 서명 출처를 결합하며, guest NU→키오스크와 환불의 원천별 권한을 유지한다. 18개 허용·11개 거절 shape와 16개 미실행 검토 사례를 작성했다. 기존 카탈로그 병합·프로파일 선정·제품 구현은 미수행이다.

후속 [HW·Cloud 지갑 사용·키 통제·복구 설계](specifications/wallet-control-recovery-design.md)는 지갑 선택·승인·생성/import·MPC 참여자 교체·분실/반납을 연결했다. 원칙 11개, 미선택 정책 4개, 명세 반영 대상 7개, 미실행 검토 사례 21개를 기존 작업에 매핑했다. HW/Cloud 별도 주소와 MPC 구성은 제안이며, 기존 복구 백업 질문은 답변 대기다. 기준 API/BLE/DB/화면은 아직 변경하지 않았다.

현재 진입점은 [설계 통합 현황과 남은 결정](planning/design-integration-register.md)이다. 기준 명세와 후보의 차이 5곳을 설계 반영 묶음 8개에 연결하고, 기존 결정 19개를 정책 입력·기술 설계·개발 단계 검증으로 구분했다. 전체 15개 요구사항과 기존 작업 수를 유지한다. 반납 화면 서술이 반영된 상태와 API/BLE/저장 후보의 병합 대기 상태를 구분한다.

현재 [반납 화면 설계](specifications/return-screen-design.md)는 기본 상태 11개·추가 제한 6개·행동 12개·검토 사례 13개를 U24/D01/O01/U04/U05에 연결했다. 반납 접수와 재대여 가능, 화면 이탈과 초기화 취소를 구분하며 기본 화면 수 37개를 유지한다. 실제 UI 구현·렌더링·접근성 시험 결과는 아니다.

최신 상세 설계는 [제품별 책임·결제/환불/반납 상태 전이](specifications/commerce-lifecycle-design.md)다. 12개 설계 사례를 기존 작업에 연결하고, DTO·이벤트·저장 계약에 반영할 5개 항목을 미결정/미반영 상태로 추적한다.

LC-GAP-01~03의 후속 [API·이벤트·저장 계약 변경안](specifications/commerce-contract-changes.md)을 작성했다. 기존 계약 병합 전 검토 후보이며, 5개 API·2개 이벤트·4개 논리 자원을 다룬다. LC-GAP-04~05와 운영 정책은 추가 설계 대상으로 남긴다.

LC-GAP-04~05도 [초기화 후 반납 복구·권한·재대여 조건](specifications/return-recovery-design.md)의 설계 후보로 구체화했다. 16개 검토 사례와 기존 계약 변경 지점 6개를 연결했다. 신규 여행 지갑의 늦은 자산 복구 정책은 사용자 선택 대기이며, 장치 신뢰·프로토콜 profile·실기 검증은 아직 미확정이다.

후속 [반납 프로토콜 요청·응답 계약 후보](specifications/return-protocol-contracts.md)에 8개 메시지 묶음과 실행/중계/조회 권한 분리, 허가 재전달 불변성, 정리 증명 유실 복구를 연결했다. 신규 여행 지갑 복구 정책을 자동 선택하지 않았으며 기존 카탈로그 병합과 제품 구현도 수행하지 않았다.

**현재는 상세 설계 단계이며 구현은 보류한다.** 사용자의 구현 착수 지시 전까지 다음 작업은 미결정 사항·설계 간 불일치·상태/복구·제품별 책임 경계를 구체화하는 설계 작업이다. 아래 구현 순서와 착수 조건은 향후 실행 계획이다.

향후 실행을 위한 [구현 순서·착수 조건·완료 증거 연결](planning/implementation-sequence.md)도 작성했다. 기존 272개 완료 의존 관계를 유지하면서, 초기 결제 조회·계약군별 조회·FOTA 적용 전 정책을 10개 부분 산출물로 구분했다. 104개 작업과 320개 세부 산출물의 [착수/증거 카드](planning/execution-readiness.md)를 연결했다. 모든 구현 준비 상태는 미평가이고, 이 계획 검증을 실기·앱 연동 완료로 표시하지 않았다.

펌웨어 기반은 사용자 결정에 따라 **Zephyr로 확정**했다. SDK 배포판(NCS 포함 여부)·정확한 Zephyr 버전·NU board target은 별도 선정이다. [구현 인터페이스 14개와 호환 판정 26개](specifications/implementation-interfaces.md)를 작업에 연결했다. 실제 호환 시험은 개발 단계에 수행한다.

15개 목표를 **26개 작업군 → 104개 작업 패키지 → 320개 세부 작업**으로 분해했다. 각 패키지는 산출물·완료 기준·선행 작업·결정 입력·검증 환경을 가지고, 각 세부 작업은 실행할 내용과 검토할 산출물을 가진다. **19개 종단 시나리오**로 사용자 동작·입출력·실패/복구·증거를 연결했다. 담당자·공수·마감일은 비워 두었다. 작업 수는 일정이나 난이도의 단위가 아니다.

기존 코드가 있어도 실행 검증을 하지 않은 작업은 완료로 표시하지 않았다. 이번 산출물은 구현 코드나 배포 결과가 아니다. 계약/API만으로 끝내지 않고 각 기능의 앱 연결과 최종 검증 작업을 포함한다.

## 3. 작업 카드의 기준

| 필드 | 기록할 내용 |
|---|---|
| ID·원문 연결 | 어떤 사용자 요구를 충족하는지 |
| 작업·산출물 | 구현 또는 결정이 끝났을 때 남는 하나의 검토 가능한 결과 |
| 완료 기준 | 정상 동작과 관련 실패/복구 조건 |
| 선행 작업 | 이 결과를 실제로 연결·검증하기 위해 먼저 필요한 결과 |
| 결정 입력 | 구현 경로를 바꾸는 선택, 예: MPC 복구 주체·패스키 대상 |
| 앱 연결 지점 | 사용자가 시작하고 결과를 확인하는 화면/서비스 |
| 재사용 기준 | 사용할 기존 코드와 아직 검증되지 않은 경계 |
| 검증 환경·증거 | 실제 기기/테스트넷/계정/버전과 실행 기록 |
| 세부 작업 | 고정 ID, 실행할 동작, 검토할 산출물 |
| 연결 시나리오 | J01~J19의 정상/실패/복구 및 증거 |
| 담당자·공수·마감일 | 작업 범위가 산정 가능한 상태가 된 뒤 입력 |

예를 들어 **OTA-03: 앱 FOTA 진행·재연결·실기 복구 구현**은 다음과 같이 정리했다.

- 산출물: 앱 업데이트 화면과 기기 전송 경로.
- 선행 결과: OTA-02의 서명된 이미지와 버전 정보, HW-03의 인증된 연결, HW-04의 설정/키 상태.
- 완료: 실제 기기를 업데이트한 뒤 버전 확인, 전원/통신 중단 시험, 합의한 키·설정 복구 정책 검증.
- 별도 작업: 이미지/부트 경로는 OTA-01~02, 버전 호환/철회는 OTA-04, 다른 기능과 자원 경합은 HW-07.

이렇게 하면 ‘FOTA 구현’이라는 큰 항목에 앱·펌웨어·운영·복구가 숨지 않는다.

## 4. 달력 대신 완료 결과에 따른 순서

현재는 몇 주차에 누가 끝낼지 지정하지 않는다. 먼저 아래 통합 관문을 기준으로 의존성을 확인한다. 서로 독립적인 분기는 병행할 수 있다.

| 관문 | 주요 작업 | 통과 증거 |
|---|---|---|
| G0 — 설계/실행 기반 | BASE-01~05, APP-01, AUTH-01, TOKEN-01, INDEX-01~02, RELEASE-01 | 앱·기기·서비스 연결 계약, 시험 환경, 실제 조회 경로·오류 처리 |
| G1 — 실제 EOA 카페 결제 | HW-01~06, TOKEN-02, PAY-01~05, SHOP-01~03, INDEX-03 | 실제 NU 승인→StableNet 전송→입금 검증→주문 결과 |
| G2 — 기기/계정/매장 수명주기 | OTA, KEY, REC, FIND, MPC, STAMP, SHOP-04~06, OPS | 업데이트·기기 기능, MPC 서명/복구, 환불·정산·대여 흐름 각각 앱 연결 |
| G3 — 전체 영역 앱 실행 | SMART, DEX, FX, PERP, STO, DID, X402, INDEX-04~06, TRIP, AI | 9개 온체인 영역, DEX 3영역, 여행 추천·챌린지의 실제 실행 |
| G4 — 실패·복구·인수 | VERIFY-01~05, RELEASE-02~03 | 전 항목 정상/실패/복구 증거, 실제 기기·카페 환경, 배포/운영 문서 |

G2·G3는 전체가 순차 대기하는 단계가 아니다. 예를 들어 패스키 경로 검증과 MPC 구조 결정은 EOA 결제가 완성되기 전에도 진행할 수 있다. 반면 스마트 계정의 완료 증거는 기존 EOA 경로와 전환 관계까지 확인해야 한다.

의존성 목록은 **최종 통합 완료에 필요한 관계**다. 디자인·스파이크·mock 기반 화면 작업을 막는 전면 착수 금지 목록은 아니다. mock은 개발 보조로 표시하며 최종 앱 연동 완료 증거로 사용하지 않는다. 일정 추정 전에는 설계 선행/구현 선행/통합 선행을 더 나눌 수 있다.

## 6. 결정을 처리하는 순서

19개 묶음을 한 번에 질문하지 않는다. 다음 작업을 산정할 수 있게 만드는 결정부터 묶어서 진행한다.

1. **제품 공통 경계:** D01~03. 대상 앱/OS와 핵심 사용자 흐름, 두 지갑·계정·기기 관계.
2. **구현 경로가 크게 갈리는 기기/키 기능:** D04~07. MPC 신뢰·복구, FOTA, 패스키 대상, 녹음/찾기 기준.
3. **결제와 운영의 동작:** D08~11. 환불/정산·대여/혜택·시험 환경·스마트 계정 전환.
4. **상품별 지원 범위:** D12~16. DeFi/FX·Perpetual·STO·DID·x402의 실제 사용자 행위와 프로토콜.
5. **데이터·추천·인수:** D17~19. 출처/동의·챌린지 조건·운영/복구/성능 기준. 이 항목도 관련 설계를 시작할 때 먼저 다루며 마지막까지 미루지 않는다.

각 결정에는 선택값, 이유, 바뀌는 작업과 완료 기준을 기록한다. 합의된 체인·고객 가스·EOA 우선·스마트 계정 12주 내·전 항목 앱 연동·3명이라는 사실은 다시 선택할 대상으로 두지 않는다.

## 7. 산정 가능한 작업으로 만드는 점검표

아래 조건을 충족하기 전에는 작업에 확정 공수를 넣지 않는다.

- 결과와 실제 앱 동작이 명확하고 다른 작업과 경계가 겹치지 않는다.
- 사용할 기존 코드·새 구현·외부 의존성을 구분했다.
- 구현을 바꾸는 미결정 항목을 해결했거나 비교/검증 작업으로 따로 분리했다.
- 입출력·오류·상태·권한과 선행 결과가 정해져 있다.
- 실제 검증 환경과 정상/실패/복구의 판정 기준이 있다.
- 큰 상품 단위라면 독립적으로 검증 가능한 하위 작업으로 한 번 더 나눴다.

현재 104개 패키지 아래 320개 세부 작업을 두었다. Perpetual·MPC·STO·DID·x402의 상품/프로토콜 선택은 해당 세부 작업의 설계 산출물로 처리한다. 선택 결과에 따라 작업을 분리/병합하되 전체 12주 완료 범위는 유지한다.

## 8. 범위 유지와 변경 관리

추가/분리/병합 시 원문 번호·산출물·앱 검증 연결을 유지한다. 15번 ‘기타 도구’는 기존 기능의 실행/운영에 필요한 도구로 한정해 연결하며 새로운 제품 영역을 자동 추가하지 않는다.

초기 결제는 일반 EOA와 고객 네이티브 가스다. 스마트 계정 지원은 12주 범위 안의 다음 단계다. 운영자 가스 후원은 여전히 후속 범위이며 이번 104개 작업의 필수 결과로 끼워 넣지 않았다. 실제 자산 운영/실제 USDC 조달 여부는 기존 미결정 상태를 유지한다.

현재 다음 순서는 **작업 목록 검토 → 연결/정책 결정 → 큰 작업 추가 분해 → 공수 산정 → 개인별 배정 → 주차별 일정**이다. 개인별 역량·시간 답변은 작업 목록 검토를 진행하는 선행조건으로 요구하지 않는다.

## 9. 문서 동기화

기술 선정은 [19개 선택 카드](planning/technology-selection.md)와 [23개 구현 단계 검증](planning/technology-validation-plan.md)에 구체화했다. D01~D19와 기존 작업에 연결하며 제안을 사용자 확정이나 구현 완료로 취급하지 않는다. `python3 content/planning/render_technology_plan.py --check`로 선택·출처·검증·작업 참조를 검사한다.

작업·세부 작업·결정 제안은 `planning/work-breakdown.json`이 기준이다. `python3 content/planning/render_worklist.py`로 카드/CSV/결정 목록을 갱신하고 `--check`로 생성본 일치·의존성·원문 범위 연결을 검사한다. 실행 명세는 사람이 검토하는 별도 문서이며, 요구 변경 시 연결된 시나리오도 함께 갱신한다. 이 검사는 기획 데이터 검증이며 실제 제품 시험은 아니다.
