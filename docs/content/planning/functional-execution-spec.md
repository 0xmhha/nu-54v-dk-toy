# 기능 실행 명세 — 사용자 흐름·입출력·실패 처리

기준: **15개 요구사항 전부를 앱 연동까지 12주 안에 완료**한다. 인원 배정·공수 산정은 하지 않는다. 이 문서는 구현 작업을 구체화한 설계 초안이며, 실제 실행 결과가 아니다. 기술/상품 선택을 새로 제안하는 부분은 ‘제안’으로 표시한다. 기존에 정한 기능을 제외하거나 후속으로 미루지 않는다.

[작업 계획](../work-breakdown-plan.md) · [104개 작업 카드와 320개 세부 작업](work-cards.md) · [결정 목록](decisions.md)

후속 구체화: [API·BLE·데이터 연결 명세](../specifications/interface-contracts.md). 요청·권한·메시지와 저장 무결성의 제안은 해당 문서를 함께 따른다.

## 1. 제품별 화면과 책임

화면 이름은 경로를 정하기 위한 초안이다. 별도 앱/서비스의 수를 늘리라는 의미가 아니며, 백엔드 배포 단위는 아직 정하지 않았다.

| 제품 | 화면/기능 | 상태의 기준 |
|---|---|---|
| 유저 앱 | 로그인·계정 연결·탈퇴, 지갑 선택·자산·송금·거래 내역 | 계정 서비스, 지갑 signer, 체인/Indexer |
| 유저 앱 | 기기 등록·신규/import·상태·찾기·FOTA·패스키·반납 | 실제 기기 응답과 대여 원장 |
| 유저 앱 | 녹음 목록·재생·전사·요약·내보내기 | 모바일 파일과 동의한 처리 작업 |
| 유저 앱 | 카페 패스포트·맛집·후기·발자취·코스·챌린지 | 혜택 원장, 장소/결제 출처, 여행 기록 |
| 유저 앱 | 스마트 계정, DeFi/FX/Perp, STO, DID, 유료 HTTP 자원 | 승인 대상·실제 실행 결과·상품별 조회 모델 |
| 유저 앱 점주 컨텍스트 | 소속 매장 선택·매장 수취 지갑 자산·권한 있는 자금 행위 | 매장 소속과 지갑 통제 권한을 별도로 검사 |
| RN 키오스크 | 가입/로그인·매장 설정·메뉴 관리·고객 주문·결제 | 매장/메뉴/주문 원장 |
| RN 키오스크 관리 모드 | 매출·환불 요청/승인·정산 대조/마감 | 주문·입금·환불·마감 기록 |
| 백오피스 | 가맹점·운영 권한·기기 대여/반납·FOTA 배포·거래 예외 | 각 서비스 원천 기록과 변경 감사 |
| Indexer/탐색 화면 | 블록/receipt/log·진행점·계약 이벤트·재처리 | 지정 RPC의 정규 체인 관측 |

점주가 로그인했다고 수취 지갑의 개인키를 보유한 것은 아니다. 키오스크는 고객의 키를 받지 않으며, 점주 앱의 읽기 권한과 환불 서명 권한을 구분한다.

### 기기 접근 권한과 연결 전환

| 연결 주체 | 허용 범위 | 종료 조건 |
|---|---|---|
| 등록된 소유 앱 | 승인 정책에 따른 설정·import·FOTA·찾기·지갑 이용 | 등록 해제·반납·계정/세션 철회 |
| 일시적인 키오스크 | 확인한 가게/주문에 한정한 결제 요청과 결과 확인 | 주문 세션 만료·거절·완료·연결 해제 |
| 운영 도구 | 대여/릴리스 원장 및 공개 상태 관리 | 운영 권한 철회 |

키오스크가 결제를 요청할 때 소유 등록을 바꾸지 않는다. 가게·기기를 확인하고 주문에 결합한 임시 세션을 만든다. 설정/import 명령은 이 세션에서 거절한다. 폰 연결과 키오스크 연결의 동시 유지 또는 일시 전환·복귀는 HW-07에서 실기 검증 후 고정한다. 근접 측정만으로 신원 확인을 대신하지 않는다.

## 2. 업무 데이터와 연결 계약 초안

아래 필드명은 제안이다. BASE-02/03에서 실제 API/BLE 스키마로 고정한다. 금액은 서버/앱 간 기본 단위 정수 문자열과 decimals로 주고받고, 표시 문자열을 서명 금액으로 다시 해석하지 않는다.

| 객체 | 필요한 식별자/입력 | 결과·연결 | 제약 |
|---|---|---|---|
| Account / Membership | accountId, providerSubject, storeId, role | 소셜 연결, 매장 소속 | 이메일만 같다는 이유로 계정 자동 병합하지 않음 |
| Wallet | walletId, kind, chainId, address, signerRef | HW/Cloud/스마트 계정 구분 | 로그인·주소·서명 권한을 같은 값으로 취급하지 않음 |
| Device / Rental | deviceId, rentalId, accountId, firmwareVersion | 등록·대여·반납·재사용 | 과거 대여와 현재 접근 권한 분리 |
| Order | orderId, storeId, lineItemsSnapshot, price, recipientSnapshot | 주문 내용과 결제 요구 | 이후 메뉴/주소 변경이 기존 주문을 바꾸지 않음 |
| Quote / PaymentAttempt | quoteId, attemptId, orderId, asset, amount, expiresAt | 승인 payload, txHash | 요청 재시도와 새 결제 시도 구분 |
| SigningRequest | requestId, walletId, chainId, payloadDigest, displayData, expiresAt | approved/rejected/expired + signature | 화면 표시와 실제 서명 payload 결합; 비밀키 미포함 |
| ChainObservation | chainId, txHash, blockHash, logIndex, receiptStatus, canonicality, revision | 지급 관측과 보정 | 고유 지급 식별은 chain/tx/log; 블록 소속·버전은 별도 관리 |
| Refund | refundId, orderId, originalPaymentId, destination, amount | 별도 서명·별도 체인 거래 | 원지급 삭제 금지; 동시 환불 요청도 누적 한도 적용 |
| SettlementRecord | storeId, period, expectedReceipts, observedReceipts, refunds, revision | 대조·차이·마감 | 초기 정산은 코인 수취 대조; 원화 자동 환전 아님 |
| BenefitEntry | benefitId, accountId, sourcePaymentId, ruleVersion | 스탬프 발급/사용/보정 | 중복 지급·사용 차단, 수정 대신 보정 이력 |
| Recording | recordingId, ownerId, format, sequenceRange, completeness | 파일·전사·요약 | 단절로 빠진 원음 구간을 복원됐다고 표시하지 않음 |
| TravelEvidence | evidenceId, sourceType, sourceId, placeId, observedAt, consent, validity | 발자취·추천·챌린지 입력 | 위치 방문, 테스트 결제, 실제 구매를 구별 |
| Operation | operationId, idempotencyKey, status, retryability, resultRef | 앱 재시작 후 진행 작업 조회 | timeout을 성공/실패로 단정하지 않음 |

BLE 비밀 import payload는 일반 요청 로그·진단 이벤트·백오피스 조회 모델로 복제하지 않는다. 앱 입력 단계의 노출 위험과 암호화 전송의 보호 범위도 구분해 구현 명세에 남긴다.

## 3. 상태 전이와 실패 처리

상태 이름과 정책은 작업을 연결하기 위한 초안이다. 업무 취소와 체인 지급 취소는 별개다.

| 대상 | 정상 경로 | 예외·복구 |
|---|---|---|
| 결제 시도 | created → awaiting_approval → signed → submitted → observed → accepted | rejected/expired; 제출 응답 유실은 submission_unknown으로 조회; 체인 실패는 failed; 관측 철회는 재평가 |
| 주문 | draft → awaiting_payment → paid → fulfilled | 지급 전 cancelled/expired; 그 뒤 입금은 예외 대사; 이미 제공한 상품은 체인 재구성으로 자동 미제공 처리하지 않음 |
| 환불 | requested → authorized → signing → submitted → confirmed | 거절/서명 중단/제출 불명확/체인 실패; confirmed 전 예약한 환불 한도를 어떻게 해제할지 명시 |
| MPC 생성/서명 | creating/signing → completed | 부분 생성·참여자 거절·timeout; 세션별 복구/폐기; 프로토콜에 맞는 새 세션 사용 |
| FOTA | offered → verified → transferring → applying → boot_confirmed | busy/blocked/interrupted/recovery_required; 이전 상태를 근거로 재개·재시작 선택 |
| 녹음 | starting → recording → stopping → saved | partial/lost/failed; 전사 작업 상태는 파일 상태와 분리 |
| 대여 | available → assigned → active → return_requested → checks → cleared → available | 잔액/미확정 거래/권한 정리 실패 시 return_pending; 초기화 확인 전 재대여 불가 |
| 혜택·여행 증거 | pending → valid → consumed/completed | invalidated/corrected; 원본과 보정 이력 연결, 과거 사용 혜택의 처리 정책 별도 |

공통 오류 형식 제안: `code`, `retryable`, `operationId`, `safeMessage`, `nextAction`. BLE/서명 요청의 만료는 향후 승인을 막지만, 이미 유효하게 서명·제출된 일반 전송을 온체인에서 취소하지는 않는다.

## 4. 제품을 연결하는 실행 시나리오

각 시나리오는 입력 → 수행 → 관측할 결과 → 실패 시험으로 구성한다. 하위 작업은 [작업 카드](work-cards.md)의 고정 ID로 추적한다.

### J01 · 소셜 가입과 두 지갑 사용

- 연결: AUTH-01~04, APP-01~03, MPC-01~05, HW-02~04, BASE-06.
- 입력: Google 또는 Apple 계정, 소유/대여한 기기, 선택한 신규/import 경로.
- 수행: 실제 제공자 인증 → 계정 생성/연결 → Cloud Wallet 생성/연결 → 기기 등록 → HW 지갑 생성 또는 import → 사용할 지갑 선택.
- 결과: 계정은 하나로 관리하되 지갑 종류·주소·잔액·승인 방법을 화면에서 구분한다. 제안 기본값은 HW와 Cloud를 독립 지갑으로 두고 계정에 연결하는 방식이다.
- 실패 시험: 중복 로그인 콜백, 생성 도중 앱 종료, 이미 연결된 제공자, 계정 전환 후 타 계정 지갑 조회/서명 시도.
- 증거: 제공자별 가입/재로그인 기록, 두 지갑 주소와 실제 송금 hash, 재실행 후 지갑 중복 생성 여부.

### J02 · 기기 등록·import·설정

- 연결: HW-01~04, APP-02, STAMP-03.
- 입력: 장비 식별자, 대여자, 인증된 연결, 신규 생성 또는 사용자가 입력한 복구 정보.
- 수행: 기기 확인 → 사용자 등록 → 보호된 세션 수립 → 선택 지갑 설정 → 예상 주소 확인 → 화면/잠금/연결 설정 저장.
- 결과: 기기 재부팅 후 올바른 주소를 다시 읽고, 새 요청에 사용자의 승인 정책을 적용한다.
- 실패 시험: 다른 기기에 연결, 전송 중단, 잘못된 입력, 재전송, 이전 대여자의 설정 요청.
- 증거: 실기 주소 비교, 설정 전후 상태, 민감값 없는 진단 기록. 전송 암호화만으로 감염된 폰의 입력 노출까지 해결했다고 판정하지 않는다.

### J03 · 카페 주문과 하드웨어 결제

- 연결: PAY-01~05, SHOP-02~03, HW-05~06, INDEX-01~03, APP-04.
- 입력: 확정 메뉴 가격, 가게 수취 주소, 결제 토큰, 고객 네이티브 가스, 연결된 기기/거리 모듈.
- 수행: 주문 snapshot → 견적/attempt 생성 → 기기에 가게·금액 표시 → 근접 상태 확인 → 버튼 승인 → 기기 서명 → 제출 → 실제 입금 검증 → 주문/영수증 갱신.
- 결과: 사전에 승인한 거래·지급 주체·attempt 귀속을 확인한 지급 증거 1개가 주문 1개에 배정되고 매출/스탬프에 한 번 반영된다. 스마트 계정에서는 외부 tx.from을 실제 고객 지급 주체와 동일시하지 않는다.
- 실패 시험: 이중 탭, 기기 거절, 가스 부족, 견적 만료, 다른 고객의 같은 금액 거래 제시, 동일 거래 재제출, 서명 전 거리 이탈, 제출 직후 BLE 단절, 만료된 주문에 뒤늦은 입금, 키오스크의 설정/import 명령 시도.
- 증거: orderId/attemptId/requestId/txHash/logIndex 연결, 기기 표시·키오스크·사용자 내역·원장 대조.

### J04 · 점주 가입·메뉴·자금 권한

- 연결: SHOP-01~03/06, AUTH-01~04, APP-02, OPS-01~02.
- 입력: 점주 소셜 계정, 매장, 메뉴, 수취 지갑 주소.
- 수행: 매장 생성/소속 → 메뉴/품절 설정 → 수취 주소 확인 → 고객 모드 전환 → 점주 앱에서 매장 지갑 조회.
- 결과: 같은 점주 계정으로 키오스크 운영과 모바일 자산 조회가 연결된다. 주소 변경은 기존 주문 snapshot에 소급되지 않는다.
- 실패 시험: 다른 가게 자원 접근, 고객 모드에서 관리자 진입, 메뉴 관리 권한만 가진 계정의 수취 주소 변경/환불 서명.
- 증거: 매장별 접근 결과, 주소 변경 감사, 점주 앱의 선택 매장/자산 대조.

### J05 · 환불과 정산 처리

- 연결: SHOP-04~06, PAY-04, INDEX-05~06, OPS-03, STAMP-01.
- 입력: 원주문/확정 지급, 환불 가능액, 검증한 환불 수취인, 점주의 서명 권한.
- 수행: 환불 요청 → 한도 예약 → 업무 승인 → 실제 signer 승인 → 별도 지급 → 확정 → 원장/혜택 보정 → 일자별 대조·마감.
- 결과: 부분/전액 환불 이력을 원지급과 함께 보존한다. 대조 차이가 있는 건은 원인을 표시한다.
- 실패 시험: 동시 환불 두 건, 반납된 기기의 예전 주소 선택, 서명 거절, 제출 응답 유실, 가게 지갑의 주문 외 입금.
- 증거: 환불 전후 잔여 한도, refundId/txHash, 매출·환불·실수취 비교, 마감 후 보정 이력.

### J06 · 반납·회수·재대여

- 연결: STAMP-03~04, KEY-03, SMART-03, HW-02~03, MPC-04.
- 입력: 대여 기기와 계정, 남은 자산, 미확정 거래, 복구/반환 주소, 등록 자격/권한.
- 수행: 지갑 생성 출처와 외부 접근 수단 검사 → 신규 여행 지갑은 필요한 가스를 고려한 자산 회수, import 지갑은 외부 접근 확인 후 기기 사본 삭제 준비 → 미확정 거래 확인 → 이 기기로 만든 패스키/위임과 기존 권한을 구분해 정리 → 키·설정 초기화 → BLE 등록 철회 → 재대여 점검. import한 기존 지갑의 자산 전액 이전이나 무관한 기존 권한 철회를 자동 수행하지 않는다.
- 결과: 이전 사용자의 계정 기록은 유지하되 반환 기기를 통해 이전 키/자격을 사용할 수 없다. Cloud Wallet이 별도 지갑이면 그 지갑까지 자동 삭제하지 않는다.
- 실패 시험: 가스 부족, 아직 처리 중인 거래, 자격 정리 실패, 초기화 응답 유실, 이전 앱으로 재접속.
- 증거: 검사 항목별 완료/보류 기록과 새로운 사용자로 재등록한 결과.

### J07 · 실제 기기 FOTA

- 연결: OTA-01~04, HW-07, OPS-02.
- 입력: 호환 버전의 서명된 이미지, 대상 기기, 유지할 키/설정, 업데이트 허용 상태.
- 수행: 앱에서 업데이트 확인 → 모델/버전/패키지 검증 → 무선 전송 → 적용/재부팅 → 새 버전·키 주소·설정 확인.
- 결과: 앱·운영 화면이 실제 부팅한 버전을 표시하고 실패 기기를 완료로 표시하지 않는다.
- 실패 시험: 변조 이미지, 다른 모델, 구버전 앱, 전송 중 전원/통신 중단, 부팅 실패, 녹음/서명 진행 중 업데이트 요청.
- 증거: 이미지 manifest, 단계별 실기 로그, 정상/복구 후 주소·설정 비교. 상세 메모리 경로는 보드 검증 작업에서 확정한다.

### J08 · 패스키 등록·로그인·해제

- 연결: KEY-01~03, HW-07, STAMP-04.
- 입력: 명시한 대상 서비스/OS/브라우저, 지원 전송 경로, 등록할 자격.
- 수행: 서비스 등록 요청 → 실제 인증기의 사용자 확인 → 등록 완료 → 새 challenge로 로그인 → 앱/서비스의 해제 흐름 실행.
- 결과: 표준 호환 경로의 실기 인증을 증명한다. 근접 승인용 자체 서명과 패스키 성공은 별도 결과로 기록한다.
- 실패 시험: 다른 RP, 만료/재사용 요청, 사용자 거절, 삭제된 자격, 분실 후 대체 로그인.
- 증거: 호환성 표의 각 대상에서 등록/인증 결과. 특정 전송/서비스 지원은 조사·실기 검증 전 확정하지 않는다.

### J09 · 녹음·모바일 저장·AI 정리

- 연결: REC-01~03, HW-07, TRIP-04.
- 입력: 마이크·버튼·연결된 폰, 사용 가능한 저장공간, 사용자가 선택한 AI 처리.
- 수행: 버튼 시작 → 기기에 녹음 표시 → BLE 프레임 수신 → 종료/파일 마감 → 재생 → 전사 → 원문에 연결된 요약·할 일 → 내보내기/삭제.
- 결과: 녹음 파일·전사·요약이 같은 recordingId로 연결된다.
- 실패 시험: 앱 백그라운드, 연결 끊김, 버퍼 초과, 저장공간 부족, 전사 실패, 처리 도중 삭제.
- 증거: 실제 재생 파일, 프레임 누락/부분 녹음 표시, 전사/요약 비교, 삭제 후 접근 결과. 보관할 공간이 없는 기기에서 단절 구간을 완전 복구한다고 가정하지 않는다.

### J10 · 기기 찾기와 근접 안내

- 연결: FIND-01~02, HW-06, STAMP-04.
- 입력: 등록된 기기, 현재 연결/거리 모듈 상태.
- 수행: 앱 찾기 → 대상 확인 → 실제 LED/부저 반응 → 중지 → 유효한 거리 결과가 있으면 안내.
- 결과: 현재 연결 가능성과 측정 유효성을 구분해 보여준다.
- 실패 시험: 연결 안 됨, 오래된 거리 관측, 모듈 없음, 반납 후 이전 사용자 요청.
- 증거: 앱과 실제 기기 반응, 측정 시각/대상, 권한 거절 결과.

### J11 · 스탬프와 카페 패스포트

- 연결: STAMP-01~02, INDEX-06, APP-04.
- 입력: 확정 결제, 카페별 혜택 규칙/버전.
- 수행: 지급 증거 검증 → 적립 → 앱/기기 표시 → 사용 요청 → 원장 갱신 → 환불/관측 보정 반영.
- 결과: 재조회·중복 이벤트에도 같은 혜택이 한 번만 지급·사용된다.
- 실패 시험: 두 화면 동시 사용, 오프라인 기기, 부분 환불, 이미 사용한 혜택의 원결제 철회.
- 증거: 혜택 원장과 앱/기기 표시 비교, 보정 이력.

### J12 · Cloud Wallet 복구와 스마트 계정

- 연결: MPC-01~05, SMART-01~03, BASE-06.
- 입력: 소셜 계정과 추가 복구 증명, 참여자 상태, EOA/스마트 계정 모델.
- 수행: 실제 분산 생성/서명 → 새 폰/참여자 교체 → 복구/철회 → 선택한 스마트 계정 연결 → 앱에서 승인·실행.
- 결과: EOA 경로와 스마트 계정 경로를 모두 남기고 주소·자산·권한 변화를 표시한다. 고객 가스 정책을 유지한다.
- 실패 시험: 임계값 부족, 오래된 참여자 응답, 소셜 계정만 탈취, SDK/EntryPoint 해시 불일치, UserOperation 개별 실패.
- 증거: 참여자 경계·복구 결과, EOA txHash, UserOperation 식별자와 실제 실행 receipt/event. MPC 방식·계정 전환 모델은 제안 비교 후 결정한다.

### J13 · 테스트 자산·Indexer·운영 복구

- 연결: TOKEN-01~03, INDEX-01~06, OPS-03, RELEASE-01~02.
- 입력: 8283 RPC, 배포 주소/ABI/시작 블록, 네이티브 가스와 더미 토큰.
- 수행: 환경 일치 확인 → 토큰 준비 → 블록/이벤트 수집 → 실제 앱 조회 → 수집 중단 → backfill/재처리 → 업무 데이터 대조.
- 결과: 앱·원장·탐색 결과가 같은 지급을 가리키며 재처리로 중복 매출이 생기지 않는다.
- 실패 시험: 주소/체인 불일치, RPC 지연, 중복 log, 블록 변경, 오래된 ABI. 체인 재구성은 재현 가능한 시험 환경에서도 검증한다.
- 증거: 높이/해시·cursor·이벤트 고유키, 전후 집계, 보정 이벤트의 혜택/여행 반영.

### J14 · DeFi와 FX

- 연결: DEX-01~03, FX-01~03, INDEX-04, APP-03.
- 입력: 선택한 토큰/통화 쌍, 실제 pool/유동성, 가격/수수료/유효기한.
- 수행: 견적 → 금액/최소 수취 확인 → 필요한 allowance → signer 승인 → swap 또는 유동성 입출금 → 이벤트/잔액 확인. FX는 통화 표시·가격 출처를 함께 보여준다.
- 결과: 앱의 체결 금액이 실제 receipt/event와 일치한다.
- 실패 시험: 유동성 부족, 견적 이후 가격 변동, allowance 부족, 만료, 단위 오류, 승인 후 실행 실패.
- 증거: quoteId와 실제 체결/LP 변동 비교. FX 현물 모델과 사용할 쌍은 제안 단계이며 확정 전 계약 구조를 고정하지 않는다.

### J15 · Perpetual

- 연결: PERP-01~06, INDEX-04, OPS-03.
- 입력: 시장·담보·가격 소스·위험 파라미터·실행 서비스.
- 수행: 증거금 입금 → 포지션 개설 → 손익/펀딩 반영 → 축소/종료 또는 청산 → 담보/이력 조회.
- 결과: 계약·서비스·앱의 포지션/잔액이 일치하고 keeper 실제 실행을 확인한다.
- 실패 시험: 가격 stale, 잘못된 가격 단위, 최대 허용량 초과, 경계 청산 가격, 반복 펀딩 실행, keeper 중단/복구.
- 증거: 가격 시점, 전후 담보/포지션, 펀딩/청산 event와 앱 표시. 기존 고정 가격/stub을 실행 증거로 쓰지 않는다.

### J16 · STO와 DID

- 연결: STO-01~03, DID-01~03, INDEX-04, BASE-06.
- 입력: 테스트 발행물·발행자·보유/전송 조건, 선택 표준의 자격과 검증자.
- 수행: 자격 발급 → 앱 보관/제시 → 검증 → 허용된 발행물 보유/전송 → 자격 철회/만료 후 재검증.
- 결과: 지갑 통제 증명과 별도 자격 조건을 구분한다. DID를 STO 자격 입력으로 재사용하는 연결은 제안이며 각각 독립 기능으로도 검증한다.
- 실패 시험: 무권한 발행, 다른 주체의 자격, 만료/철회 자격, 허용하지 않은 전송 대상.
- 증거: 자격 검증 결과, 계약 전송 결과, 공개/개인 데이터 경계. 테스트 발행물을 실제 권리가 있는 자산으로 표시하지 않는다.

### J17 · x402 유료 자원 사용

- 연결: X402-01~03, APP-03, INDEX-04.
- 입력: 유료 HTTP 자원, 지원할 프로토콜 버전/네트워크/자산, 검증/지급 서비스.
- 수행: 자원 요청 → 지불 요구 확인 → 사용자 가격 승인 → 선택 방식의 지급 증명 → 검증/지급 → 자원 응답 → 이용 이력.
- 결과: 지급과 응답 전달 상태를 구별하고 지불 후 응답 실패를 복구한다.
- 실패 시험: 위조/다른 요청의 증명, 허용하지 않은 자산, 승인 거절, 같은 요청 재전송, 지불 후 서버 timeout.
- 증거: request/payment/resource 식별 연결과 중복 과금 없는 복구. StableNet 지원 경로는 구현 조사에서 확인하며 임의 헤더만 붙여 호환 완료로 간주하지 않는다.

### J18 · 맛집·여행·AI 코스·챌린지

- 연결: TRIP-01~04, AI-01~03, STAMP-01, INDEX-06.
- 입력: 동의한 위치, 장소 정보, 출처가 표시된 결제/후기, 일정·이동·예산 조건.
- 수행: 지역 검색 → 장소 상세/후기 → 여행 시작 → 결제/방문 발자취 → AI 코스 생성·수정·저장 → 따라하기 → 조건별 발도장.
- 결과: 추천 장소의 근거와 이동/영업 제약을 보여주고 방문·구매·챌린지 완료를 구분한다.
- 실패 시험: 위치 거절, 데이터 부족, 없는 장소 생성, 영업 종료, 같은 증거 반복 사용, 환불/결제 관측 보정, 후기/위치 삭제.
- 증거: 추천 입력 출처/시점, 검증된 코스, 챌린지 원장, 삭제/보정 후 결과. 테스트 결제는 실제 구매로 표시하지 않는다.

### J19 · 전체 운영과 인수

- 연결: OPS-01~03, VERIFY-01~05, RELEASE-01~03.
- 입력: 모든 제품의 버전·환경·배포 기록과 시나리오별 실행 증거.
- 수행: 설치 → 운영자/점주/사용자 흐름 실행 → 장애 재현 → 백업 복구 → 원장/체인 대조 → 요구사항별 판정.
- 결과: 15개 항목 모두 앱에서 시작해 실제 기기/서비스/체인 결과까지 확인 가능한 릴리스 묶음.
- 실패 시험: 운영 권한 부족, 백업 복구 후 재수집, 배포 중지, 서비스 부분 장애, 오래된 앱/기기 조합.
- 증거: 재현 명령, 버전, 테스트 데이터 ID, 기대/실제 결과, 실패 원인과 재검증 기록. 고객 키·원음·정밀 위치는 인수 로그에 기본 첨부하지 않는다.

## 5. 실행 증거 양식

각 J 시나리오의 정상·거절·실패·복구 사례마다 다음 필드를 채운다.

```text
scenarioId / caseId / linkedTaskIds
buildVersions / environment / deviceModel / OS
preconditions / fixtureIds / input
steps
expectedResult / actualResult
safeEvidenceRefs / transactionRefs / operationRefs
verdict: not_run | pass | fail | blocked
issueRef / retestEvidence
```

현재 모든 사례는 `not_run`이다. 계획에서 수량이나 품질 목표를 제시할 때는 제안값으로 기록하고, 구현을 시작할 때 선택한 수치와 측정 방법을 고정한다.

## 6. 구체화된 작업의 적용 순서

1. BASE-02/03에서 위 식별자·상태·메시지를 스키마와 예제로 만든다.
2. 제품별 작업을 J 시나리오의 입력/결과에 맞춰 구현할 수 있도록 카드의 하위 산출물을 검토한다.
3. 선택이 필요한 항목은 [결정 목록](decisions.md)의 제안값을 비교하고, 해당 작업에 실제 선택을 기록한다.
4. 구현과 함께 정상·거절·실패·복구 증거를 쌓고 VERIFY에서 제품 간 결과를 대조한다.

이는 주차 배치나 담당 배정이 아니다. 독립 작업은 병행 가능하며 전체 12주 완료 범위를 유지한다.
