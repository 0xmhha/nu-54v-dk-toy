# 구현 전 선택을 위한 결정 자료

기존 19개 결정과 신규 여행 EOA 복구 질문 1개를 선택 카드로 정리했다. 권장안은 검토를 위한 제안이며 선택값은 모두 비워 두었다. 전체 15개 기능·12주·3명·앱 연동 범위를 유지한다.

## 먼저 볼 내용

- 사용자 경험·비용·복구 권한을 바꾸는 선택과 기술 검증으로 좁힐 수 있는 선택을 구분했다. 기술 항목마다 새 사용자 승인을 요구하는 목록이 아니다.
- D02(연결 규칙), D10(시험 환경)은 기존 분류상 새 사용자 질문 없이 기술 검토를 이어갈 수 있다. 미확인 실배포값이나 하드웨어 능력은 임의로 확정하지 않는다.
- RR-DEC-01은 이미 열린 복구 정책 질문이다. 이 문서에서 재질문하거나 답변을 추정하지 않는다.
- 제공자·SDK 버전·보드 저장 용량·법적 운영 가능 여부는 이 자료로 확인 완료되지 않는다. 운영자 후원은 기존 후속 범위를 유지한다.

## 검토 묶음

| 묶음 | 포함 선택 |
|---|---|
| 공통 제품·환경 | D01, D02, D10, D19 |
| 기기·키·복구 | D03, D04, D05, D06, D07, RR-DEC-01 |
| 매장·자산·혜택 | D08, D09, D11 |
| 체인 상품·자격 | D12, D13, D14, D15, D16 |
| 여행·데이터·AI | D17, D18 |

그룹은 검토 묶음이며 전체 선행 순서가 아니다. coordinateWith는 공동 검토 관계로 완료 의존성을 의미하지 않는다.

## 선택이 설계로 반영되는 과정

```mermaid
flowchart LR
 A["제품 선호·통제 권한"] --> C["선택 기록 + 적용 범위"]
 B["기술 비교·보드/제공자 근거"] --> C
 C --> D["profile·wire·ABI·저장 배치 고정"]
 D --> E["계약 묶음 채택 검증"]
 E --> F["구현 전환 지시 이후 개발"]
 F --> G["실기·앱·체인 수용 증거"]
```

다른 독립 설계는 미선택 항목 때문에 멈출 필요가 없다. 선택이나 문서 검증은 실행 검증을 대신하지 않는다.

## 결정별 비교 카드

### D01 · 앱·인증 대상

**권장 검토안** — 유저 앱과 RN 키오스크를 별도 앱으로 두고 계정·금액·거래 상태 모듈만 공유한다. Android/S25 실증과 한국어·영어 UX를 우선 검토한다.

**대안** — 유저 앱의 UI/native 계층을 별도 플랫폼 구현으로 분리하고 업무 계약만 공유한다. 키오스크 RN 조건은 유지한다.

**차이와 조건** — A는 공통 기능 변경을 함께 검토하기 쉽지만 BLE·MPC·녹음 native bridge의 플랫폼별 검증은 남는다. B는 OS 대응 자유도가 커지는 대신 중복 화면/테스트 관리가 늘어난다.

**입력할 선택값**

- 추가 지원 OS와 최소 버전
- 키오스크 태블릿 모델·공유 기기 잠금
- 설치/배포 경로
- 언어와 번역 범위

**선택을 뒷받침할 근거**

- 지원 행렬에 Google·Apple 로그인 경로를 각각 기입
- 선정 native bridge가 해당 OS에서 빌드·권한·백그라운드 요구를 충족하는 증거 확보

**결정 후 고정할 설계** — 앱 경계·공유 패키지 목록 / OS별 인증 redirect/복구 profile / 플랫폼 수용 행렬

**판단 경계** — 사용자·운영 정책: 추가 OS·태블릿·배포 경로·언어 우선순위 · 기술 설계: 유저 앱 RN 채택안·native bridge 공유 경계 · 실제 확인: 플랫폼별 설치/Google·Apple 인증

**연결** — 작업 BASE-01, AUTH-02, AUTH-03, APP-01, SHOP-01, TRIP-03; 기술 TECH-01, TECH-02; 검증 계획 VAL-01, VAL-02; 함께 검토 D04, D06, D07.

**상태** — 선택 없음 · 원본 `content/planning/work-breakdown.json#/decisions/0` · queued_not_asked

### D02 · 연결 규칙·데이터 경계

**권장 검토안** — 기존 식별자·공통 봉투·원천/업무 상태 분리를 유지하고, 요청/결과/권한 변경을 한 계약 버전으로 고정한다. 보호 상태와 outbox의 단일 원자 경계를 우선 설계한다.

**대안** — 분리 저장 서비스를 사용하되 불명 결과의 재조회·중복 제거·보상 책임을 추가 계약으로 명시한다.

**차이와 조건** — A는 원장과 권한의 경합을 한 저장 경계에서 다루기 쉽다. B는 배포를 분리할 수 있으나 네트워크 장애 때 단일 원자성을 가정할 수 없다.

**입력할 선택값**

- wire encoding과 정규화
- API/BLE/profile 버전 정책
- 권한 변경·원장·outbox의 저장 배치
- 수명/만료 시계와 재시도 규칙

**선택을 뒷받침할 근거**

- OC26개와 기존 API/BLE/권한/저장 매핑의 변경표 대조
- 동일 요청·응답 유실·현재 권한 변경에 관한 golden fixture 확정

**결정 후 고정할 설계** — versioned HTTP/BLE schema / 거절 사유/재조회 표 / 원자 경계와 migration 채택 묶음

**판단 경계** — 사용자·운영 정책: 새 사용자 질문 없음; 기술 근거로 진행 · 기술 설계: API/BLE/proof 버전·인증 envelope·역할별 projection·정규화·원자 저장 경계 · 실제 확인: 실제 profile 호환·권한/동시성

**연결** — 작업 BASE-01, BASE-02, BASE-03, AUTH-01, HW-03, INDEX-02; 기술 TECH-03, TECH-04, TECH-09, TECH-19; 검증 계획 VAL-03, VAL-04, VAL-09, VAL-19; 함께 검토 D03, D08, D19.

**상태** — 선택 없음 · 원본 `content/planning/work-breakdown.json#/decisions/1` · no_new_user_question_required

### D03 · 지갑 키·복구

**권장 검토안** — HW와 Cloud 지갑은 별도 주소·서명자로 표시한다. HW 신규 생성/import를 모두 제공하고 import는 물리 확인을 포함한 인증된 암호화 채널로 전송한다.

**대안** — 같은 두 지갑을 유지하면서 계정 연결을 자동 진행하지 않고 사용자가 필요할 때 개별 연결한다. 생성/import 기능은 삭제하지 않는다.

**차이와 조건** — A는 지갑 전환과 결제 기록 연결이 쉽고 B는 연결 시점을 사용자가 제어한다. 두 방식 모두 앱 로그·분석·클립보드·저장소에 원시 키가 남지 않도록 설계해야 하며 감염된 입력 단말의 탈취까지 전송 암호화만으로 막을 수는 없다.

**입력할 선택값**

- 파생 경로·가져오기 지원 형식
- 기기 잠금/재인증·표시 확인
- 보호 키 backend·장치 신원/epoch
- 신규 여행 EOA 백업은 RR-DEC-01에서 별도 결정

**선택을 뒷받침할 근거**

- 입력부터 앱/기기 정리까지 민감정보 수명 표 작성
- 개인 복구 경로와 대여 운영자 권한을 분리
- 주소를 바꾸거나 자산을 옮기는 행위를 자동 연결과 구분

**결정 후 고정할 설계** — 키 lifecycle·import 암호 profile / 계정-지갑 연결/해제 UX / 복구/반납 상태표

**판단 경계** — 사용자·운영 정책: 신규 여행 지갑의 개인 복구 백업 추가 여부 또는 복구 없을 때 초기화 보류 / HW/Cloud 지갑의 주소·복구 관계 · 기술 설계: 키 파생·격리·import·장치 신원/epoch/journal 보호·늦은 증거 검증 · 실제 확인: 원시 키 비노출·서명·삭제·초기화 후 복구

**연결** — 작업 BASE-03, AUTH-04, APP-02, HW-02, HW-03, HW-04, HW-05, MPC-01, STAMP-03, VERIFY-01, BASE-06, STAMP-04; 기술 TECH-02, TECH-07, TECH-12; 검증 계획 VAL-02, VAL-07, VAL-12, VAL-20, VAL-22; 함께 검토 D04, D09, RR-DEC-01.

**상태** — 선택 없음 · 원본 `content/planning/work-breakdown.json#/decisions/2` · existing_question_pending

### D04 · MPC 신뢰 구조

**권장 검토안** — 독립 통제 주체를 둔 2-of-3를 우선 비교안으로 평가한다. 평상시 폰 참여자+서버, 복구 시 별도 사용자 복구 참여자의 개입을 요구하는 정책을 검토한다.

**대안** — 폰+서버 2-of-2에 별도의 참여자 교체/백업 절차를 둔다. 한 참여자 부재 때 서명할 수 없다는 조건을 명시한다.

**차이와 조건** — A의 사용자 경험은 세 번째 참여자의 실제 보관·인증·복구 방식에 달렸다. 같은 운영자가 두 조각을 통제하면 독립 통제 취지가 무너진다. threshold 숫자만으로 서버 단독 통제나 서비스 중단 복구가 해결되지 않는다.

**입력할 선택값**

- 각 참여자의 실제 통제 주체
- 분산 ECDSA/DKG·refresh·복구 지원 revision
- 소셜 계정 탈취/폰 분실/운영 중단의 허용 quorum
- 조각 저장·복구 인증·회전 방식

**선택을 뒷받침할 근거**

- 전체 키를 한 곳에서 합치는 백업 복원과 임계 서명을 구분
- 제공자 feature matrix에 DKG/서명/중단/재개/교체를 증거별 기입
- 폰+복구 경로가 서버 부재에도 실제 가능한지 별도 입증

**결정 후 고정할 설계** — 참여자·장애·공모 행렬 / quorum/키조각 lifecycle / provider adapter와 실패/재개 profile

**판단 경계** — 사용자·운영 정책: MPC 참여 주체·복구 권한·서비스 중단 시 접근 정책 · 기술 설계: 제공자/라이브러리·임계값·조각 보관 경계·세션 중단 규칙 · 실제 확인: 실제 DKG/임계 서명·참여자 변경·복구

**연결** — 작업 AUTH-04, MPC-01, MPC-02, MPC-03, MPC-04, VERIFY-01, BASE-06, MPC-05; 기술 TECH-12; 검증 계획 VAL-12, VAL-22; 함께 검토 D03, D11, D19.

**상태** — 선택 없음 · 원본 `content/planning/work-breakdown.json#/decisions/3` · queued_not_asked

근거: [NIST Multi-Party Threshold Cryptography](https://csrc.nist.gov/projects/threshold-cryptography) — 전체 키를 재조립하지 않는 분산 임계 연산. 이 근거만으로 2-of-3 또는 특정 제공자 채택·제품 보안 인증을 확인했다고 보지 않는다.

### D05 · FOTA 운영

**권장 검토안** — Zephyr의 MCUboot·MCUmgr/SMP를 우선 후보로 삼아 앱 전달→기기 검증→시험 부팅→확정 흐름을 설계한다. 진행 중인 서명·녹음을 정리한 뒤 업데이트한다.

**대안** — 기능은 유지하고 외부 update bank 또는 별도 복구 저장 배치를 검토한다. 보드 용량을 확인하기 전에 내부 dual-slot 가능성을 확정하지 않는다.

**차이와 조건** — A/B의 차이는 실제 flash·RAM·이미지 크기로 판단한다. 업데이트 UI 선택과 부트 검증 정책은 별개이며 긴급 업데이트도 키 무단 삭제·서명 중단을 정당화하지 않는다.

**입력할 선택값**

- 실제 보드 revision/target·Zephyr SDK revision
- bootloader·slot·보호 키/설정 영역
- rollback 허용 범위·이미지 확인 조건
- 업데이트 요청/강제/유예 UX와 릴리스 서명키 운영

**선택을 뒷받침할 근거**

- 핀/메모리 지도와 이미지 상한으로 저장 배치 검토
- 전원 차단·잘못된 서명·실패 부팅·저장 호환 테스트 계획 확정

**결정 후 고정할 설계** — partition/devicetree 후보 / 서명 manifest·부팅 상태표 / FOTA 앱 복구 UX

**판단 경계** — 사용자·운영 정책: 업데이트 시 사용자 중단/강제 여부와 운영 배포·복귀 정책 · 기술 설계: Zephyr SDK/board target·부트로더/슬롯·서명 키 운영·저장 호환 · 실제 확인: 서명 이미지·전원 차단·부팅 복귀·키 보존

**연결** — 작업 HW-01, OTA-01, OTA-02, OTA-03, OPS-02, VERIFY-02, HW-07, OTA-04; 기술 TECH-06, TECH-08; 검증 계획 VAL-06, VAL-08; 함께 검토 D03, D07, D19.

**상태** — 선택 없음 · 원본 `content/planning/work-breakdown.json#/decisions/4` · queued_not_asked

근거: [Zephyr MCUmgr](https://docs.zephyrproject.org/latest/services/device_mgmt/mcumgr.html) — SMP 기반 관리·Bluetooth 전송·MCUboot 연결. 이 근거만으로 NU 보드 slot 용량·선정 SDK 호환·실기 업데이트 성공을 확인했다고 보지 않는다.

### D06 · 패스키 호환 범위

**권장 검토안** — 통제 가능한 시험 RP의 표준 등록/인증부터 검증하고 대상 외부 서비스 행렬로 확장한다. USB HID 경로가 필요하면 companion transport 후보를 비교한다.

**대안** — 목표 폰/OS가 지원하는 다른 표준 CTAP 전송을 우선 검토한다. 일반 BLE GATT 서명을 표준 패스키로 대체 표기하지 않는다.

**차이와 조건** — 지원 RP/OS/전송 조합을 고정해야 수용 판정이 가능하다. 시험 RP 성공은 모든 서비스 호환을 뜻하지 않으며 자체 근접 승인과 RP의 WebAuthn 검증은 별도 기능이다.

**입력할 선택값**

- 대상 서비스·OS·브라우저·전송 조합
- user presence와 user verification 방식
- discoverable credential·동기화/백업 표시 정책
- 분실/반납 시 대체 로그인과 RP 자격 해제

**선택을 뒷받침할 근거**

- RP ID·challenge·origin·사용자 확인 검증을 포함한 등록/인증 시험 정의

- 백업 검증 실패 또는 선택 없음은 초기화 진행 금지

**결정 후 고정할 설계** — 신규 EOA 복구/반납 profile / 선택 시 필요한 backup 형식/UX / 초기화 전 검사와 보류 운영표

**판단 경계** — 사용자·운영 정책: 기존 질문의 사용자 선택 · 기술 설계: 선택한 복구 방식의 키 수명/반납 경계 · 실제 확인: 독립 복구·초기화·재대여 시험

**연결** — 작업 HW-03, STAMP-03, STAMP-04; 기술 TECH-07; 검증 계획 기존 복구/반납 수용 사례; 함께 검토 D03, D09.

**상태** — 선택 없음 · 원본 `content/specifications/return-recovery-contract.json#/openDecisions/0` · existing_question_pending_do_not_reask

## 시험 목표의 비교 출발점

아래 숫자는 성능 실측이나 채택된 운영 약속이 아니다. 기존 목표가 비어 있어 선택할 수 있도록 만든 제안값이다. 모두 실제 개발 단계에서 측정한다.

### TARGET-01 · 회의 녹음

- 제안: 30분 mono 16kHz/16bit; 정상 종료 exact coverage, 유실은 partial 표시
- 조건: 제품 검토용 목표 제안; 기기 측정값 아님
- 측정: 실기+S25, 화면 켜짐/잠금 각각; 시작/종료/단절 이벤트와 durable chunk manifest
- 미달 때: codec/품질/버퍼 후보 재검토; 누락 숨김·complete 승격 금지

### TARGET-02 · 앱/키오스크 업무 요청 응답

- 제안: 비체인 조회/접수 p95 1초 이내를 초기 시험 목표로 제안
- 조건: 5개 단말·10개 동시 사용자·15분·최소1000요청의 합성 부하 가정; 실측/운영 약속 아님
- 측정: 오류율·timeout·cold start 따로 보고; 체인 확정/AI 생성/큰파일 업로드 제외
- 미달 때: DB/네트워크/원천 조회를 분리 측정; 지급 확정 조기 표시 금지

### TARGET-03 · 시험 업무 서비스 장애 복구

- 제안: DB/객체 참조 일치 기준 RPO 15분·RTO 60분을 비교 출발점으로 제안
- 조건: 운영 SLO 채택 아님. 키 복구·온체인 자산·Indexer 전체 복구 시간을 이 값으로 대신하지 않음
- 측정: DB 시점 복원+object inventory+Indexer replay+outbox 중복 제거+체인 대사 각각 검증
- 미달 때: 해당 업무 mutation 제한·원 지급 상태 재대사, 관측 전 결제완료 처리 금지

## 선택 기록 양식

| 필드 | 남길 내용 |
|---|---|
| 선택 ID·옵션 | D번호 또는 RR-DEC-01, 권장/대안/수정안 |
| 적용 범위 | 제품·환경·기능·자산·사용자 범위 |
| 근거 | 선택 이유와 기술 자료/사용자 결정 기록 |
| 고정할 버전 | profile/계약 및 변경 전 기록 |
| 실제 검증 | 미실행/실행 구분, 증거·기종·배포 identity |
| 변경 관계 | 시행 조건과 대체하는 이전 선택 |

선택이 확정되면 원 decision ledger, 기술 선택, 영향 계약·화면·저장 설계를 같은 변경 묶음으로 갱신한다. 현재는 어떤 원본 선택도 변경하지 않았다.
