# P10 유즈케이스 — 공유 EIP-712 타입·벡터와 수용 기준

행위자는 각 제품의 개발자(role A, role B, user)와 시험 담당이다. 요구 번호는 [SRS](srs.md)를 가리킨다.

## 1. UC-P10-01 타입 변경

| 항목 | 내용 |
|---|---|
| 행위자 | user |
| 사전 조건 | 서명 타입 필드를 바꿔야 하는 결정이 register에 기록됨 [N04] |
| 기본 흐름 | 1. 스키마의 타입을 고친다. 2. `build_eip712_vectors.py`로 벡터를 다시 만든다. 3. `--check protocol+vectors`를 돌린다. 4. 세 제품 담당에게 벡터 변경을 알린다 |
| 예외 흐름 | 2a. cast 서명이 계산한 digest로 검증되지 않음 → 생성기가 실패하고 벡터 파일을 쓰지 않는다 |
| 요구 | P10-FR-01..P10-FR-04 |

## 2. UC-P10-02 구현 적합성 확인

| 항목 | 내용 |
|---|---|
| 행위자 | role A(펌웨어), role B(키오스크), user(컨트랙트) |
| 사전 조건 | 벡터 파일이 커밋됨 [N21] |
| 기본 흐름 | 1. harness가 벡터를 각 구현의 시험에 넘긴다. 2. 각 구현이 digest를 계산한다. 3. harness가 벡터 digest와 비교하고, 서명에서 복원한 signer가 벡터의 signerRole(device, operator, merchant) 주소와 같은지 확인한다. 4. 결과를 로그로 남긴다 |
| 예외 흐름 | 3a. 한 구현만 다름 → 그 구현의 인코딩 버그로 보고 벡터는 바꾸지 않는다. 3b. signer 역할이 다름 → 그 구현이 서명자 역할을 뒤섞은 버그로 보고한다 |
| 요구 | P10-FR-05 |

## 3. UC-P10-03 12주차 수용 기록

| 항목 | 내용 |
|---|---|
| 행위자 | 시험 담당 |
| 사전 조건 | W12 리허설 완료 |
| 기본 흐름 | 1. 항목별 시험을 수행한다. 2. 원본 로그·영상을 git 밖에 저장한다. 3. 기록지에 결과, 줄인 주소·tx hash, 원본 파일의 64자리 전체 `sha256:` checksum을 적는다 [N16]. 4. `--check acceptance`와 `--check redaction`을 돌린다 |
| 예외 흐름 | 1a. P07이 컷됨 → W12-06은 키오스크의 PaymentSettled 직접 조회 기록으로 적는다 [N18] |
| 요구 | P10-FR-06, P10-FR-07 |
