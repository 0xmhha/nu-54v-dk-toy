# 12주 완료 범위 v3 — 기기·지갑·매장·여행·온체인 서비스

작성: 2026-09-18. 사용자 확정에 따라 **15개 항목 전부를 앱 연동까지 12주 안에 완료**하는 것을 고정 계획 전제로 기록한다. 아래 상세 수용 기준과 개별 설계 선택은 검토용 제안이다. 현재 단계는 작업 구체화이며, 최종 Seed 또는 구현 완료 상태가 아니다.

이 문서는 이전 문서의 좁은 결제 시연 범위와 상충하는 부분을 대체한다. 사용자의 항목을 임의로 후속 버전으로 제외하지 않는다. **사용자 후속 확정: 모든 항목은 앱 연동까지 완료하고 참여 인원은 총 3명이다.** 역할·작업량 배정은 보류하고 [상세 작업 목록과 의존성](work-breakdown-plan.md)을 먼저 정리한다. 이전 3인 배치는 참고 초안이다.

## 1. 변경 및 유지되는 결정

- 패스키·녹음기·디바이스 찾기·결제 스탬프는 후보에서 **12주 필수 범위**로 바뀐다. FOTA도 필수다.
- 유저 앱은 Google·Apple 로그인, **MPC 키 관리를 사용하는 Cloud Wallet**, 여행자 기능을 포함한다.
- 스마트 계정은 **일반 지갑(EOA)부터 개발한 뒤 12주 범위 안에서 지원**한다. 지원은 앱 연동까지이며, 실제 전환 방식은 미정이다. 운영자 가스 후원은 기존 결정대로 후속이며, 이번 목록만으로 12주 필수가 된 것으로 보지 않는다.
- 초기 EOA 결제는 고객의 StableNet 네이티브 토큰으로 가스를 지불한다. 하드웨어 지갑의 고객 서명은 NU 기기가 맡고 매번 폰 공동 서명을 요구하지 않는 기존 결정을 유지한다.
- 새 MPC 요구는 우선 **Cloud Wallet의 별도 키 관리 요구**로 분류한다. NU 지갑의 키를 서버에 복제하거나 모든 지갑을 같은 MPC 정책으로 바꾸는 결정으로 해석하지 않는다.
- StableNet 테스트 체인 8283, 지정 RPC/탐색기, 기존 네 저장소 재사용, NU 보드와 거리 측정 모듈 보유, 실제 기기 검증은 개발 단계에서 수행한다는 결정을 유지한다.
- 테스트넷 USDC 확보 문제로 더미 토큰을 쓰는 기존 결정을 유지한다. 이번 USDC ‘지원’이 실제 USDC 조달·실자산 파일럿 필수까지 의미하는지는 미정이다.
- FX·Perpetual·STO 등은 테스트넷 기능 지원 범위로 기록한다. 기존의 원화 자동 환전/정산 제외 결정을 실제 외환 서비스 도입으로 자동 변경하지 않는다.

## 4. 11번 컨트랙트 지원을 검증할 최소 단위 — 제안

사용자의 모든 항목을 유지하고 **각 영역은 앱 연동까지 지원**한다. 아래 대표 시나리오는 기준 초안이며, 개별 상품 설계·실물 자산 운영을 이미 합의했다는 뜻은 아니다.

| 영역 | 대표 시나리오 | 추가 결정 |
|---|---|---|
| USDC | 표준 토큰 잔액·승인·전송·환불과 이벤트 관측. 시연은 기존 결정대로 더미 토큰 | 실제 USDC 지원 확인/조달과 더미 토큰 호환 시험 범위 |
| WKRC | 네이티브 잔액·가스 납부·송금 | wrapped ERC-20 입출금도 포함할지 별도 결정. 네이티브 토큰과 wrapped 계약을 같은 자산 모델로 혼동하지 않음 |
| DeFi | 지정한 프로토콜에서 입출금 또는 유동성 제공/회수 등 합의한 대표 사용 사례 | DeFi의 필수 상품 목록. ‘모든 DeFi’로 확대하지 않음 |

| 사용자 요구 | 기존 키 가져오기/신규 생성, 실제 NU 승인·서명 | 소셜 로그인에 연결된 클라우드 지갑, MPC 키 관리 |
| 기본 책임 | 고객 지출의 키·서명은 NU에 둠 | 선택한 참여자들이 임계 서명에 참여 |
| 아직 미정 | 지원 키 파생 경로·보드 보호 영역 세부·복구 정책 | MPC 제공자/구현·참여자 수·임계값·각 조각의 소유자·복구 |
| 명시해야 할 UX | 현재 선택한 주소·기기·지불 자산 | 현재 선택한 주소·서명 승인·복구 수단 |

소셜 로그인 성공, 매장 운영 권한, 지갑 서명 권한은 따로 설계한다. 소셜 계정 탈취만으로 모든 서명 조각과 복구 권한을 얻도록 만들지 않는 것을 목표로 한다. 두 지갑의 잔액/주소/수수료를 구분하고 사용자 승인 없는 자동 합산·키 복제를 하지 않는다. 기기 반납/초기화가 Cloud Wallet의 접근·복구까지 지우는 동작인지도 구분한다.

‘MPC 지원’은 단어만으로 검증할 수 없다. 실제 선택한 알고리즘·라이브러리/서비스와 위협 범위에 대해 분산 서명, 참여자 장애, 복구·회전·철회, 로그/백업의 민감정보 취급을 시험한다. 지금 임의로 2-of-3 또는 특정 벤더를 확정하지 않는다.

## 6. 실제 데이터와 시험 데이터

14번의 ‘실제 결제 데이터’는 **테스트넷에서 실제 발생한 주문·전송 데이터**와 **고객의 실제 구매/실자산 결제 데이터** 중 무엇까지 요구하는지 구분이 필요하다. 현재 전자만으로 후자의 요구를 충족했다고 판단하지 않는다.

추천 데이터에는 결제 이벤트, 실제 구매 확인, 위치 방문, 사용자 후기, 합성 시험 데이터를 구별하는 출처/시점을 둔다. 추천 엔진에 전체 블록체인 주소 이력을 무조건 사람의 이동·선호로 연결하지 않는다. 위치·후기·녹음의 수집/활용 범위를 사용자 설정으로 드러내고 삭제·내보내기·권한 거절 흐름도 수용 기준에 넣는다.

## 7. 기존 자산의 활용 원칙

- `poc-platform`: 웹/확장 지갑·SDK·Bundler·Paymaster·일부 DApp 화면을 재사용. 모바일/보드/MPC 구현 여부는 별도 증거 필요.
- `stable-poc-contract`: 테스트 토큰·스마트 계정·DeFi 등 실제 소스가 있는 모듈을 재사용. 코드 존재와 지원 영역 전체의 완성을 구분.
- `indexer-go`, `indexer-frontend`: 거래/이벤트 수집과 탐색기 재사용. 이번 신규 계약과 앱의 스키마·API 계약까지 연결.
- 기존에 발견한 SDK–Indexer 요청/응답 불일치와 Paymaster 형식 차이는 유지한다. 스마트 계정이 12주 범위에 들어왔으므로 AA 호환성도 12주 일정에서 검증한다. 운영자 후원 자체를 필수로 확대하지 않는다.

추가 영역의 소스 근거와 미확인 항목은 [확장 범위 재사용 조사](expanded-scope-reuse-inventory.md)에 정리한다. 배포·연동·실기 시험 결과는 아직 없다.

## 8. 12주 배치 초안과 인력 조건

| 기간 | 병행 작업의 목표 | 종료 시 확인할 증거 |
|---|---|---|
| 1~2주 | 3인 역할·투입 시간·작업 추정, 기기/패스키/FOTA/MPC 위험 경로의 개발 검증, 계약/데이터 목록 확정 | 빌드 가능한 환경, 실기/플랫폼 호환 경로, 담당자·API·키 소유 경계 |
| 3~4주 | EOA 결제·기기 설정, Google/Apple 로그인, Cloud Wallet 기본 서명, 메뉴/주문/대사 골격 | 기기 승인 거래·소셜별 로그인·MPC 서명·주문 연결 증거 |
| 5~6주 | FOTA·패스키·녹음/찾기·스탬프, 매장 환불/정산·백오피스, 스마트 계정과 계약군 통합 | 실제 기기 기능, 계정별 권한, 계약별 대표 호출·이벤트 |
| 7~8주 | DEX/FX/Perpetual 서비스, STO/DID/x402 대표 흐름, Indexer 확장, 여행 장소/후기/발자취 | 서비스와 체인 결과의 연결·개인 데이터 권한 |
| 9~10주 | 여행 추천·챌린지/발도장, 전체 제품 통합, 대여/반납·복구·단절/중복/오입금 처리 | 정상·실패·복구 시나리오와 실제 데이터 출처 |
| 11~12주 | 실제 기기·카페 환경 수용 시험, 성능/배터리/업데이트/권한 회귀 시험, 운영/사용 문서 | 항목별 결과·실패 내역·잔여 이슈·재현 방법 |

이 배치는 **3인의 병행 개발을 전제로 한 초안**이다. 역할별 상세 배치는 현재 보류하며 [작업 목록](work-breakdown-plan.md)을 구체화한 뒤 다시 계획한다. 개인별 숙련도·주당 시간은 아직 확인하지 않았으며 작업량 검증이 끝난 일정은 아니다. 기존 코드의 완성도·장비 자원·MPC/패스키 연동 수준을 확인하기 전에는 전 항목의 12주 달성을 보장할 수 없다. 지연이 발생하면 범위 제외로 조용히 처리하지 않고, 검증 깊이·인력·일정 변경을 명시적으로 결정한다.

## 9. 15번 지원 도구의 경계 — 제안

필수 항목의 동작/운영에 필요한 배포·주소/ABI 등록, 테스트 토큰 공급, FOTA 릴리스 관리, 환경/비밀 설정, CI와 재현 가능한 빌드, 테스트 데이터, 관측/알림, Indexer backfill, 데이터 백업/복구, 계정/권한·감사 이력, 사용/운영 문서를 우선 후보로 둔다. 각 작업은 위 요구사항 ID와 연결하며 새 독립 제품은 별도로 범위를 결정한다.
