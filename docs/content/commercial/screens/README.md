# 앱 화면 설계와 예상 화면

고객은 **얼마를 누구에게 보내는지**, 점원은 **어떤 주문을 준비해도 되는지**, 점주는 **어느 주소에 얼마가 들어왔는지**를 각자의 첫 화면에서 확인한다. 같은 주문을 모바일·키오스크·백오피스·영수증 탐색기에서 추적하도록 구성했다. 화면 안의 ‘여울 커피 성수점’, 잔액, 주문, 블록과 시각은 설계 검토용 예시다. [기준 PRD·유즈케이스·IA](../products/README.md)

## 페이지별 상용 화면 설계

[전체 페이지를 여는 화면 설계서](book.html)에서 사용자·메뉴명·상태명이나 `P09.UC4`와 같은 원문 ID로 찾을 수 있다. 화면의 버튼은 사용자 행동이다. 오른쪽 ‘설계 검토’의 사건은 보드 버튼 승인, 다른 직원의 승인, 원장 커밋, 체인 확정 등을 재현한다. 브라우저의 뒤로 가기와 페이지별 주소로 검토 위치를 공유할 수 있다. [기능과 유즈케이스 대조표](coverage.md) · [독립 감사와 반영 기록](audit.md)

## 하드월렛 진행 단계

보드에는 화면이 없어서 사용자는 보드만 보고 지금 무엇을 눌러야 하는지 알 수 없다. 그래서 보드를 기다리는 모든 모바일 앱 상태는 [board.json](board.json)의 단계 하나를 가리키고, 앱은 진행 순서·지금 할 일·누를 버튼·표시등과, 이어지는 단계에서 누를 버튼을 함께 보여 준다. 설계서 빌드는 모바일 앱 상태가 보드 버튼·PIN·물리 확인·기기 승인을 요구하면서 단계를 가리키지 않거나, 독립 표시를 요구하면서 대조 단계가 없는 흐름을 가리키거나, "맞으면 승인"처럼 대조 기준을 밝히지 않은 승인 문구를 쓰면 실패한다. 보드 단계가 아닌 예외는 사유와 함께 [board.json](board.json)의 `notBoardSteps`에 적는다.

| 흐름 | 단계 | 쓰는 화면 |
|---|---|---|
| 보드 등록 | 연결 창(SW4 길게) → 보드 승인(SW1/SW2) → PIN → 완료 | W04 |
| 내용 대조 후 서명 | 독립 표시 대조 → 보드 승인 → PIN → 완료 | W08, W10, W14, W15, W16, W17, W19, W27, W28, T04–T06, L02–L05 |
| 휴대전화 교체 | 복구 창(SW3 길게) → 독립 복구 장치 승인 → 보드 승인 → PIN → 완료 | W06 |
| 백업·복원 | 물리 확인(SW3 길게) → PIN → 보드 처리 → 완료 | W05, W06 새 보드 |
| 이미지 기록·펌웨어 적용·찾기·삭제 | 보드 처리, 유선 정비 창(SW1+SW2), 찾기 신호, 물리 확인 | W03, W12 |

PIN은 4자리이며 SW1이 현재 자리 숫자를 올리고, SW3이 다음 자리로, SW2가 모두 지운다. 처음 등록할 때는 같은 PIN을 한 번 더 입력한다. PIN의 숫자와 입력 위치는 휴대전화로 전송되지 않으므로, 앱은 PIN 단계라는 것과 버튼 사용법만 안내한다. 버튼과 표시등 동작은 펌웨어(`main.c`, `status_led.c`, `device_recovery_pin.c`, `device_update.c`, `device_hd.c`, `device_pilot.c`)에서 확인한 값이다. 독립 표시가 필요한 요청은 보드가 독립 표시의 서명을 받은 뒤에만 버튼 입력을 기다린다. 개인 슬롯 삭제의 물리 확인은 펌웨어에 아직 없어서 설계서에 미구현으로 표시한다.

휴대전화는 보드의 진행 상태를 알려 주는 화면이고, 승인할 내용(금액·받는 곳·권한)을 대조하는 기준이 아니다. 감염된 휴대전화가 잘못된 내용을 보여 줄 수 있으므로([보안 위협 TM-002](../architecture/security.md#위협-영향과-확인-방법)), 내용 대조는 독립 표시 장치가 맡고 앱은 그 장치를 보라고 안내한다.

아래 M/K/O/E 번호는 초기 시안의 화면군을 가리킨다. 구현 인수에는 위 상세 페이지 ID와 상태 ID를 사용한다. M01–M04는 W01/W07–W11/W25, M05는 W02–W06, M06–M07은 T01–T07, M08은 W18–W19, M09–M10은 W13–W15/W28, M11은 W11, M12는 W06/W12/W23/W26/W27에 연결된다. 기존 E01/E02는 X01–X02와 X03–X06으로 세분화했다. 가맹점의 기존 K/O 번호는 같은 업무의 시작 화면으로 유지한다.

검토 도구와 실제 사용자 화면을 함께 캡처한 예도 볼 수 있다. [가맹점 견적 검토 화면](page-wallet-review.png) · [예약금 확정·잔금 환불 확인 중 화면](page-booking-refund.png)

## 모바일 화면과 전이

지갑 홈의 기본 단위는 **선택한 프로필·네트워크·계정**이다. 예시의 128.50은 대여 프로필의 결제 가능 예치금이다. 하단 탐색은 지갑·결제·둘러보기·설정 순서를 유지한다. 결제 검토와 권한 승인은 전체 화면으로 열어 DApp 웹 콘텐츠나 배경 주문의 버튼과 섞이지 않게 한다. [모바일 IA](../products/p02-user-app/ia.md) · [기기 승인 설계](../wallet-and-mobile.md)

| 화면·진입 | 첫 화면의 우선순위와 행동 | 예외·종료·돌아갈 곳 |
|---|---|---|
| M01 지갑 / M02 계정·자산 | 프로필·보드 연결, 네트워크, 사용 가능한 금액, 받기/보내기. 자산 행에서 거래 이력과 마지막 조회 시각을 연다. | 오프라인은 마지막 갱신 시각을 표시한다. 테스트넷·메인넷 전환은 명시적 선택, 금액 가리기는 읽기 보조에도 적용한다. |

## 시각 규칙과 사용성 인수

- 금액은 자리 폭을 고정하고 자산 단위를 같은 줄에 둔다. 지갑은 계정·잔액, 매장은 메뉴 사진·합계, 운영자는 원장 표와 선택 행에 시선을 모은다. 어두운 녹색은 주요 동작, 연두는 확인을 도와주는 강조색이다. 확인 중에는 시계 아이콘과 상태명을 함께 사용한다.
- 고객 모바일 터치 영역 목표는 최소 48×48, 키오스크 주요 행동은 최소 64px 높이다. 글자 200%에서는 모바일 세로 스크롤·단일 열을 허용하고 금액, 받는 곳, 거절 동작을 계속 읽을 수 있어야 한다. 스크린리더 순서는 출처 → 수취인 → 금액·단위 → 수수료 → 기기 동작 → 거절이다. 동작 줄이기와 고대비·한국어/영어 표시를 실기에서 확인한다.
- 파일럿 인수 시 초보자·고령자 포함 10명 중 9명 이상이 도움 없이 모의 결제를 마치고 10명 모두 잘못된 금액을 거절해야 한다. 미확정 화면에서 재결제하는 사례, 타인의 장바구니·폰 선택 착오, 권한 없는 정산 자료 접근을 기록한다. 시안 데이터만으로 이 목표의 달성 여부를 판정하지 않는다.
- 검토 장면은 모바일 세 화면을 나란히 놓은 보드, 가로형 터치 단말, 데스크톱 운영/탐색 화면이다. 세로 단말과 큰 글씨에서는 메뉴 아래 장바구니 트레이, 표에서는 행 상세로 전환한다. 보드 버튼 배치·리비전은 연결한 기기 프로필과 실제 표기를 대조한 뒤 안내한다.
