# P06 StableNet 결제 계약 · 제품 요구사항

[제품별 설계 목차](../README.md) · [PRD](prd.md) · [기획](plan.md) · [유즈케이스](use-cases.md) · [정보구조](ia.md)

## 사용자와 결과

가맹점은 확정된 주문의 지정 스테이블코인을 등록 주소에서 즉시 쓸 수 있다. 개발자는 테스트넷에서 계약 주소·ABI·토큰·정산 버전을 고정하고 지급과 거절을 재현한다.

## 현재 출발점과 목표 범위

현행 PaymentSettlement는 예치금에서 가맹점 적립 후 인출하는 v1이다. v2 원자적 직접 지급은 새 계약·자금 정책·이벤트를 요구한다. [제품 README](../../../../../products/p06-stablenet-contracts/README.md) · [계약 원본](../../../../../products/p06-stablenet-contracts/src) · [직접 지급과 전환](../../merchant-payments.md)

## 기능과 인수 조건

| ID | 기능 | 제품이 보장할 동작 | 인수 시 관측할 결과 |
|---|---|---|---|
| R1 | 거래 도메인 | 체인·계약·토큰·상점·주문·지급자·금액·기한·nonce와 견적에 결합한 지급 주소·버전을 현재 유효한 등록 정보와 대조한다. 주소 변경 시 옛 견적의 수취인을 조용히 바꿔 실행할 수 없다. | 다른 도메인의 서명·만료·기사용 주문은 잔액 변화 없이 거절. |
| R2 | 직접 지급 | 주문 소비와 등록 수취 주소로의 정확한 이전을 한 트랜잭션에서 처리하고 실제 가용 잔액 증가를 확인한다. | 지급 30이면 주소의 사용 가능한 잔액 증가 30. 성공을 반환하고 미이체하는 토큰도 revert, 상태·토큰 이동 원복. |
| R3 | 이벤트·환불 | 버전·주문·수취 주소·금액으로 지급을 식별한다. 원결제에 연결한 별도 재원/권한의 환불에서 누적 한도를 검증한다. | 부분·전체 환불 후 누적액 ≤ 원금. 체인 확정 전 매장 영수증을 완료로 판정하지 않는다. |
| R4 | 배포·공존 | 8283 지정 TestUSDC와 계약 버전을 manifest로 고정한다. v1 적립금/인출을 계속 대사하고 새 버전에 독립 재원을 둔다. | v1 잔액과 v2 재원 간 무단 이동 0건, 같은 업무 주문의 동시 지급 방지는 P05의 버전 결합과 통합 검증. |

## 출시 판단

허용 토큰마다 반환값과 실제 이전 효과를 검증하고 실행 가스는 지급 원금과 분리한다. 감사·재원·주소 정책이 정해지기 전에는 직접 지급 테스트넷 데모로 제한한다.

## 기존 계약과 선택형 배포 범위

v1 개설·예치·한도·지연 인출·반납과 점주 cashOut은 마이그레이션 회귀 대상이다. 기존 확장 설계의 WKRC·일반 EOA·Smart Account, DID·CafePass·x402는 개별 테스트 프로필로 관리한다. 8283 가맹점 데모의 허용 자산은 지정 TestUSDC 하나다. 별도 채택 시 프로필·ABI·체인 증거, 자격 철회·재생과 유료 자원 제공 조건을 인수한다.
