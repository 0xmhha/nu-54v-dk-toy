# 상용 제품 구현 및 PoC 리팩토링 계획

첫 통합 목표는 **한 매장에서 고객 두 명이 공용 키오스크와 각자의 폰으로 독립 주문하고, 보드에서 승인한 결제가 가맹점 등록 주소의 실수령·영수증·부분 환불·일마감까지 이어지는 것**이다. StableNet 테스트넷 8283의 지정 TestUSDC, 신규 v2 전용 테스트 예치금, 가맹점 가스 부담으로 범위를 고정한다. 이 경로에서 펌웨어·앱·SDK·원장·계약·인덱서의 연결을 먼저 검증하면, 이후 구독과 예약도 같은 승인·지급·환불 경로를 사용할 수 있다. 개인 지갑의 여섯 네트워크와 여행·시장·MPC는 아래에 별도 완료 단위로 잡았다.

기준 코드는 `4ca2e59`다. 상용 동작의 기준은 [데이터 설계와 ERD](architecture/README.md), [제품별 PRD·유즈케이스](products/README.md), [페이지·상태별 설계](screens/book.html)다. 기존 12주 수용 기록은 v1 회귀 기준으로 보존한다. 아래 작업 번호는 선행 관계와 인수 책임을 나타낸다. 큰 작업은 같은 번호 아래 스키마·도메인·어댑터·화면·통합 시험 PR로 나눌 수 있다.

작업별 코드·독립 검수·실기 상태는 [구현 진행 장부](implementation-progress.md)에 기록한다.

**병렬화 순서.** 01 직후 02(데이터)와 03(빌드)를 함께 시작한다. 04에서 펌웨어·가맹점·계약 담당이 동일 견적 바이트를 확정하면 05(보드), 07(주문), 08(계약)을 분담한다. 09는 08의 ABI 후보로 개발하고 배포 manifest와 재생 결과가 일치할 때 인수한다. 11의 단말 UI는 모의 서버로 먼저 만들 수 있으며 12에서 두 실물 고객 경로를 합친다. 14는 06 이후 가맹점 파일럿과 병행 가능하다. 19·20의 실패는 해당 선택 기능의 활성화에만 영향을 준다.

인력·보드 리비전별 수량·독립 복구 부품·iOS 시험 환경·외부 제공자의 검증 일정은 확정 전이다. 첫 반복에서 플랫폼/QA가 실제 빌드·기기 시험 소요를 재고, 05~06에서 펌웨어/모바일 담당이 OS별 등록과 복구 가능 조합을 확인한 뒤 달력 일정을 산정한다. 그전까지 진척은 아래의 **동작 및 증거**로 보고한다.

## 리팩토링과 데이터 전환

예를 들어 단말의 기존 지급 판정은 v1 회귀 시험으로 고정하고, v2에서는 P07이 확정 증거를 생산하고 P05가 주문·이행을 판정하며 P04는 그 결과를 표시한다. 단말의 10초 대기 만료는 확인 중 상태로 전환한다. 견적 만료만으로 실패를 확정하거나 재고를 해제하지 않고, 기한 내 포함 여부와 확정 미소비·무효화 증거를 대조한다. [기존 단말 판정](../../../products/p04-merchant-kiosk/src/payment/submit.ts) · [확정과 해제 조건](architecture/ledger.md)

공통 기능 추출은 **기존 호출을 시험으로 고정 → 공통 원자 기능/벡터 추가 → 새 어댑터로 소비자 하나 전환 → 구·신 결과 비교 → 마지막 소비자 전환 후 중복 제거** 순서로 한다. UI는 명령과 조회를 호출하고 저장·서명·시간 포트는 제품 진입점에서 주입한다. 지갑 키, 지점 DB, MPC 지분, 체인 지급의 쓰기 권한은 해당 제품에 남긴다. [패키지 소유와 의존 방향](architecture/packages.md)

## 인수와 공개 범위

### 첫 반복의 병합 순서
