# NU-54V-DK 하드월렛과 가맹점 결제 시스템 상용화 설계

2026-11-20 · 기준 코드 `4ca2e59` · 신규 제품 요구사항에 대한 설계 제안 · [12개 요구사항 대조 결과](#요구사항-12개-대조-결과)

여행자는 빈 보드로 개인 지갑을 만들고, 자신의 폰에서 내역을 읽고 보드 버튼으로 결제를 승인한다. 매장에 도착한 두 고객은 한 사람이 키오스크 화면에서 메뉴를 고르는 동안 다른 사람이 자기 폰에서 먼저 주문할 수 있다. 가맹점주는 등록한 주소에서 실제 수령한 금액과 주문별 정산을 확인한다. **여섯 네트워크에서 자산을 관리하는 지갑**과 **StableNet 테스트 스테이블코인만 받는 데모 가맹점**은 지원 범위가 다르다.

| 구현 전에 답해야 할 질문 | 상세 설계 |
|---|---|
| 디스플레이 없는 보드에서 무엇을 확인하고, 폰이나 보드를 잃었을 때 무엇을 복구할 수 있는가? | [하드월렛과 모바일 앱](wallet-and-mobile.md) |
| 같은 보드가 소유자 폰에는 지갑 기능을, 처음 보는 매장에는 주문 한 건의 결제만 제공하려면? | [BLE 프로토콜과 배포 계약](protocol.md) |
| 두 고객이 동시에 주문하고 결제 도중 앱이 종료돼도 어느 주문을 누구에게 지급하는가? | [키오스크·주문·가맹점 정산](merchant-payments.md) |
| 여행자가 줄 서지 않고 주문하고, 가진 코인으로 원화 가격을 내고, 여행지를 예약하고 도움을 받으려면? | [여행자 주문·환전 결제·여행 도움 기획](traveller-services.md) (초안) |
| 하드월렛·모바일 앱·키오스크 유즈케이스가 지금 코드와 맞는가, 손님 확인과 수령은 어떻게 하는가? | [유즈케이스 점검과 결정(2026-11-27)](use-case-review.md) |
| 어떤 보드와 의존성으로 무엇을 빌드했으며 어떤 증거가 있어야 실제 자산을 맡길 수 있는가? | [보안 검토와 출시 검증](security-and-release.md) |

제품 하나를 구현할 때는 해당 제품의 PRD에서 인수 조건을 고른 뒤 기획, 유즈케이스, 화면·서비스 정보구조 순으로 확인한다. [10개 제품별 설계 및 요구사항 추적](products/README.md)

개인 지갑의 자산 관리와 고객 결제, 단말 주문, 가맹점 정산을 각 페이지의 정상·오류·재개 상태로 검토할 수 있다. [페이지별 상용 화면 설계](screens/book.html) · [PRD·유즈케이스와 페이지 대조표](screens/coverage.md) · [대표 시안](screens/README.md)

제품 구현의 데이터 원본·스키마·기능 모듈과 보안 통제는 [상용 데이터 설계](architecture/README.md)와 [검증된 스키마의 ERD](architecture/erd.md)를 따른다.

## 제품 경계와 데이터 소유권

| 경계 | 소유 데이터와 책임 | 다른 제품에 제공하는 것 |
|---|---|---|
| 펌웨어 | 개인키, 계정·파생 정책, 승인 중인 요청 1건, 시도 횟수. 기기에서 원문을 해석하고 버튼 후 서명 | 공개 주소, 표시할 거래 필드, 제한된 서명 결과 |
| 모바일 지갑 | 등록한 보드, 공개 계정 색인, DApp 권한, 구독 일정, 여행 예약 접근권. 운영체제 보안 저장소 사용 | 본딩된 소유자 세션, 주문·예약 클라이언트, 사용자가 읽을 확인 화면 |
| 프로토콜 프로젝트 | 메시지·오류·바이트 규칙, SDK, 호환성 표, 정답 벡터 | 펌웨어·앱·키오스크가 같은 릴리스를 소비 |
| 가맹점 단말 | 단말 신원과 모드, 공개 카탈로그 캐시, 처리 중인 주문 참조 | 매장 발견 정보, 서명된 견적, QR 또는 BLE 결제 진입점 |
| 가맹점 서비스와 운영 콘솔 | 가맹점·단말·역할, 가격 버전, 주문·재고·예약 원장, 환불 승인, 주방 전달 | POS API, 주문 상태, 멱등 명령, 재전송 가능한 웹훅, 매출 보고서 |
| 체인·인덱서 | 체인은 지급 사실을 확정. 인덱서는 검증된 이벤트를 조회용으로 투영 | 체인·계약 버전을 포함한 지급/환불 증거, 재처리 커서 |

가맹점 서비스는 기존 Go 운영 코어 위에 주문·카탈로그·결제·원장 모듈을 둔 단일 서비스로 시작한다. 별도 워커가 체인 제출, 인덱싱, 알림, 주방 전달을 수행한다. 첫 버전에 서비스 간 분산 락을 도입할 이유가 없다. 지도 공급자와 DApp은 지갑의 외부 입력이다. 어느 쪽에도 개인키나 단말 관리 권한을 넘기지 않는다.

기존 12주 일정에 상용 개발 일수를 덧붙이지 않았다. 2단계의 보드 저장소·복구 부품 실험, 3단계의 OS별 BLE 실험에서 확보한 결과로 인력과 일정을 산정한다. 데모는 4단계에서 독립적으로 시연할 수 있다.

### 구현 착수와 출시 판정

프로토콜 벡터·테스트넷 주문·모의 UI 개발은 위 설계로 시작할 수 있다. **개인용 메인넷 서명**은 지원 보드·폰 조합에서 본인 확인, 거래 표시, 독립 복구, 키 저장 경계를 검증한 뒤 열고, **가맹점 실자금 지급**은 등록 주소 실수령·환불 재원·기존 채권 청산과 지역별 운영 조건을 검증한 뒤 연다. 지원 조합별 한도, 독립 복구 부품, 출시할 자산과 지역은 위 결정표의 담당자가 근거와 함께 확정한다. 여기서 제안한 부하·지연·UX 수치는 파일럿 인수 목표다.
