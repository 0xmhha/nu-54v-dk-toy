# 12 로컬 합성 소프트웨어 인수

`make commercial-pilot-test PILOT_OUT=/tmp/nu54-pilot-evidence POSTGRES_BIN=/path/to/postgresql/bin`은 새로운 PostgreSQL 클러스터와 두 loopback Anvil 인스턴스를 띄운다. `PILOT_OUT`에는 비어 있는 폴더를 지정한다. Go와 Foundry는 잠금 파일의 버전을 사용한다. P02/P04 합성 어댑터 실행에는 설치된 workspace 의존성과 `node:module`의 동기 loader hook을 제공하는 Node가 필요하다. macOS에서 CMake가 OpenSSL을 찾지 못하면 설치된 OpenSSL 3 경로를 `OPENSSL_ROOT_DIR`으로 지정한다.

100명의 독립 지급자와 각자의 영수증, 5분 공용 단말 점유까지 재현하려면 비어 있는 출력 경로로 다음 명령을 실행한다. 기본 Make 대상은 독립 지급자 100명의 전체 지급을 켜지 않는다.

```sh
python3 scripts/test_commercial_integrations.py --independent --human-units \
  --public-hold-seconds 300 --pilot-output /tmp/nu54-full-pilot \
  --postgres-bin /path/to/postgresql/bin
```

실행은 도구 버전, 100개 요청의 왕복시간과 락 시도, 체인·원장 연결, 공용 슬롯 시각, 알림 수렴을 각각 JSON으로 남긴다. 기준 측정에는 300초 실제 시간을 사용한다. 개발자가 짧게 재실행할 때는 같은 러너를 `--public-hold-seconds 8`로 호출할 수 있다. 8초 실행은 5분 판정의 증거가 될 수 없다. CI의 `commercial-integration-test`는 별도의 무건너뜀 통합 관문이다.

한 상품의 두 옵션을 같은 고객이 함께 주문하는 조건은 `--independent`를 `--independent-same-sku`로 바꾸고 별도의 빈 출력 폴더를 지정한다. 이 모드는 300초 점유와 100명의 서로 다른 구매자를 요구한다. 상품 재고 205개와 옵션별 재고 105개에서 출발해, 주문 단계가 끝나면 세 잔량이 각각 5개이고 옵션 예약 200개가 고유 주문 100개에 연결되어야 한다. 요청 절반은 옵션 순서를 바꿔 전송한다. 95백분위가 1초 이상이면 전체 결과를 실패로 기록하고, 지급·영수증·중복 여부는 계속 측정한다. [동시 주문 검증과 결과 형식](../../../products/p05-operations-backoffice/internal/settlement/pilot_independent_test.go)

11월 21일 첫 5분 조건 실행에서는 한 상품의 두 옵션 주문 100건이 모두 생성됐고 교착은 0건이었다. 95백분위는 2.614초였다. 당시 시험이 시간 기준에서 멈춰 이 실행의 결제·영수증은 미검증이다. 별도 진단에서 100건씩 네 번 반복했을 때 한 상품의 두 옵션은 1.633초와 1.042초, 서로 다른 상품은 0.674초와 0.303초였다. 진단에서는 공용 단말 점유를 단축했으므로 정식 5분 조건의 결과는 해당 실행의 원장에서 확인해야 한다.

## 증거의 범위

- P01 설치 정책과 보드 승인 C 함수를 호스트 프로그램에서 실행했다. P02 소유자 세션과 P04 보드 결제 로직은 같은 서명과 견적을 합성 V2 송수신 경계에서 검증했다. 발급 레코드와 가맹점 프로필은 합성 시험 데이터다.
- P02가 P04와 같은 포맷의 QR 위치자를 해석하고 P05에서 비교 번호, 직원 확인과 기존 클레임 재조회를 실행했다. 고객 인증 mTLS 경로 10회와 P02 근거리 클라이언트에서 P04 근거리 중계로 보내는 경로 10회가 같은 지급 승인을 전달했다. 카메라 광학 스캔과 실제 BLE 무선은 사용하지 않았다.
- P05 원장과 P07 실 인덱서 프로세스는 로컬 체인의 실제 로그를 대조했다. 두 지급과 환불은 테스트 서버의 제품 핸들러 및 워커로 수행했다. 별도로 구동한 실제 `opsd`는 100개 주문 생성과 재무 마감, mTLS 발송과 소비자 inbox 양쪽의 커밋을 수행했다.
- 로컬 실행에서 방송 후 P07 프로세스를 같은 세대로 재시작했다. P05 워커의 DB 로그인과 메모리 상태를 재구성해 이미 등록된 해시를 대사했다. 알림 전후 실제 `opsd` 프로세스를 교체하고 송신 fence가 다시 증가하지 않는 것을 확인했다.
- v1 계약의 미결 7 단위 에스크로와 활성 대여 레코드를 v2 업무 전후에 확인했다. 프린터 응답 유실은 합성 장치에서 검증했다. 모르는 결과는 자동 출력하지 않았고 직원이 같은 영수증의 재출력을 한 번 승인할 수 있었다.

같은 작업의 P04 React Native 구성요소 시험에서는 활동으로 60초 유휴 타이머가 갱신되며 QR의 별도 만료가 슬롯 재사용을 막지 않는지 확인한다. 300초 실시간 측정은 실제 단말 화면이 아닌 P04 슬롯 모델과 실제 HTTPS 메뉴 조회로 구성했다.

100건 지급·소비자 부하는 아래 별도 실행으로 측정했다. 공용 단말의 실제 광학·무선과 실물 프린터 입력, 현장망 p95, 외부 테스트넷, 실기 설치는 별도 인수 대상이다.

## 2026-11-20 로컬 측정

20시 30분 두 번째 전체 실행에서는 대여와 지급 주소 변경 시험이 연속 통과했다. 이 실행은 100인 주문 생성 p95가 **1,144.13ms**여서 1초 기준을 넘었다. 재고 잔여 5/5, 교착 0건이었다. 같은 실행의 새 운영자 시험에서 한글 지점 이름 등록이 HTTP 400을 반환했다. 직후 호스트 1분 load average는 337.41이었고 여러 모바일 빌드와 시뮬레이터가 실행 중이었다. 그 수치만으로 지연의 원인을 확정할 수 없어 정상 부하와 빌드 병행 조건을 나눠 측정한다. 이번 실행을 통과 표본으로 집계하지 않는다.
