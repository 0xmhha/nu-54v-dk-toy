# 결제용 하드월렛: 행위자별 유즈케이스와 시나리오 추적

작성 2026-11-23. 기준 설계: [화면 없는 결제용 하드월렛](spending-wallet.md).

정정 (2026-11-23): escrow는 주문 한 건의 구매 보호다. 결제 금액은 escrow에 잠기고, 사용자가 수령을 확인해야 가맹점에 지급된다(P09). 원래 지갑에서 보드 계정으로 자산을 보내 두는 것은 escrow가 아니다(S07). 서명 시험은 입금 전에 반드시 한다(S05).

같은 상황에서 세 행위자가 각자 무엇을 하는지 한 줄에 나란히 적는다. 각 줄을 실제 사용 순서대로 이어 붙여 추적하면, 한 행위자가 기다리는데 다른 행위자에게 할 일이 정해지지 않은 곳이 드러난다. 그런 곳은 "빈 곳"에 모았다.

새로 그릴 화면과 상태: 결제 확인(금액·가맹점·품목, 한도·잔액 결과, "보드로 승인"), 결제 막힘(입금으로 이동), 보드 승인 대기, 제출 중·결과 확인 중, 결제 완료·준비 완료, 주문 상세의 환불 행, 반납, 보드 교체 감지, 보드 분실, 정책 만료, 탭 위의 승인 대기 띠, 휴대전화 교체 진입 행.

## 7. 키오스크 화면 설계

키오스크 화면 시안은 가로 1280×800 단말을 가정했다. 메뉴와 장바구니(K01·K02), 결제 연결과 승인 대기(K08), 결제 완료와 주문번호(K08), 주방 접수(K05)를 그렸다. 3장의 결제 단계에서 키오스크가 하는 일을 화면마다 하나씩 받는다.

| 화면 | 받는 유즈케이스 | 설계 요점 |
|---|---|---|
| 메뉴와 장바구니 | P01 | 장바구니를 오른쪽에 늘 띄운다. 주 버튼은 "하드월렛으로 결제" 하나다 |
| 결제 연결과 승인 대기 | P02–P05, E03 | QR과 연결 표식을 보여 주고, 진행 단계 4개(연결 → 내용 보냄 → 하드월렛 승인 중 → 결제 확인)를 표시한다. 승인 중에는 자동 초기화를 멈춘다 |
| 결제 완료 | P06 | 주문번호를 크게 보여 주고, 휴대전화로 보냈다고 알린다. 10초 뒤 처음 화면으로 돌아간다 |
| 주방 | P07, P08, E05 | 새 주문, 준비 중, 픽업 대기 세 칸이다. 자동 갱신과 알림음, "준비 완료 · 고객에게 알림" 버튼, 환불 요청 입구를 둔다 |

## 8. 중요 빈 곳 6건의 처리 제안 (검증 반영본)

결정 기록(2026-11-23): 이번 출시에서 클라우드 지갑(W20–W22)은 메뉴에서 숨기고 코드는 남긴다.

첫 제안을 별도 감사가 계약과 코드에 대조했다. 그대로 타당한 항목은 없었다. 다섯 건은 고친 뒤 타당하고, G6은 전제가 틀렸다. 아래는 그 결과를 반영한 제안이다.

**철회**: 이 장의 이전 판에 있던 "누구나 부르는 `returnAll`", "escrow 입금 제한", "결제 금고에 미리 하는 묶기와 approve"를 모두 철회한다. 입금 단계에 계약을 끌어들인 설계였다.

### 공통 원칙: 계약은 주문 결제에만 쓴다

- **입금**: 원래 지갑에서 보드 계정으로 보내는 보통 송금이다.
- **결제**: 주문할 때 그 주문의 금액만 escrow에 들어간다.
- **반납**: 보드가 남은 잔액을 원래 지갑으로 보내는 보통 송금이다.

### G1. 입금 (S05–S07)

서명 시험을 통과한 주소만 보여 주고, 사용자는 한 번 송금한다. 별도의 승인 거래는 없다.

### G2. 휴대전화 세션 (S06, P06, P08)

- 보드 식별 키(`INSTALL_ID`, `device_install.c:196`)로 서명한다. 서명 본문에는 다음 값을 넣는다.
  - 용도 구분값 `NU54-PHONE-SESSION-v1`
  - 서버 이름, challenge, 만료 시각, 지급자 주소, 휴대전화 공개키
- 이 키는 TLS 키와 같으므로, 용도 구분값으로 G5 등록 서명과 섞이지 않게 한다.
- management 프로필에서 등록된 owner에게만 이 명령을 허용한다. 지금 펌웨어에는 이 명령이 없으므로 새로 만든다.
- 세션 토큰을 쓰는 요청마다 휴대전화 키로 소유를 증명한다.
- 지급자를 비활성화하면 토큰도 폐기한다.
- P05에는 mTLS 없는 공개 수신부와 요청 제한을 새로 둔다. 지금 수신부는 클라이언트 인증서를 요구한다(`cmd/opsd/commerce.go:467-468`).
- **보드 없이 쓰는 경로(분실 E09, 초기화 뒤 E08)**: 휴대전화가 아니라 원래 지갑의 서명(EIP-712)으로 요청자를 확인한다.

### G3. BLE 범위 밖의 주문번호 (P06)

- BLE로 받지 못하면 G2 세션으로 조회한다.
- 서버는 주문의 지급자와 토큰의 지급자가 같을 때만 답한다.
- 조회는 처음 2분 동안 5초마다, 이후 30초마다 한다. 확정되거나 실패하면 멈춘다.
- 서명은 했지만 키오스크에 전달하지 못한 경우에는 "결제 전달 실패, 같은 주문을 다시 연결" 상태를 둔다.

### G4. 키오스크 자동 초기화 (P04, E03)

- **멈추는 조건**: 60초 타이머(`MerchantScreen.tsx:390-394`)와 QR 만료 타이머(`:1035-1052`)를 둘 다 멈춘다. 조건은 단순 연결이 아니라 지급자 결합(`payerBound`, `:1005-1006`) 또는 견적 발급 이후로 한다.
- **결합 뒤 화면**: QR을 숨기고 "결제 취소" 버튼을 보여 준다. 다음 손님이 앞 주문을 스캔하지 못하게 하기 위해서다.
- **최대 대기**: 견적 기한에 30초를 더한 시각까지 기다린다. 견적 기한의 일반 상한은 `core/src/nu54_pilot.c:168`이다.

### G5. 지급자 등록 (S06)

보드 계정을 미리 계약에 등록하지 않는다. 주문 escrow는 주문마다 보드 서명과 가맹점 서명을 확인한다. 가맹점 등록은 지금처럼 governor가 한다.

### G6. 버튼 초기화 뒤 남은 잔액 (E08)

되찾을 방법이 없다. 버튼 초기화는 PIN을 요구한다(2026-11-23 결정). 앱은 초기화 전에 남은 잔액을 잃는다고 알린다.
