# 화면 없는 결제용 하드월렛: 감사, 설계, 구현 계획

작성 2026-11-23. 상태: 설계 제안. 결정이 확정되지 않은 항목은 "결정 필요"로 표시한다.

## 1. 목표 모델

보드는 Bluetooth Ledger Nano처럼 동작한다. 화면이 없어서 사용자는 버튼을 누른 뒤 처리가 됐는지, 보드가 지금 어떤 상태인지 알기 어렵다. 휴대전화 앱(NU Wallet)이 화면을 대신하는 것은 이 상태 확인 용도다. 보드는 LED 켜짐·꺼짐 패턴으로 상태를 알리고, 앱은 각 패턴의 뜻과 다음에 누를 버튼을 안내한다. 보드에는 다음 특성이 들어간다.

| 기능 | 동작 |
|---|---|
| 공장 초기화 | 처음 펌웨어를 설치한 상태로 되돌린다. 앱에서 시작할 수도 있고, 앱 없이 보드 버튼 패턴으로도 시작할 수 있다 |
| 지갑 설정 | mnemonic 없이 보드 안에서 무작위 키를 만든다. 사용자는 원래 지갑에서 보드가 만든 계정(보드 계정)으로 자산을 직접 보내 두고 쓴다. 원래 지갑은 노출되지 않는다. 이 예치는 escrow가 아니다 |
| 코인 설정 | 체인마다 계정을 활성화한다. 보드가 만든 주소를 앱이 독립적으로 검증하고 동기화한다. **자산을 보내기 전에** 그 주소의 키로 서명 시험을 통과해야 한다 |
| 결제 | 주문마다 구매 escrow에 금액을 맡긴다. 앱이 서명을 요청하면 보드가 서명해 앱에 돌려주고, 앱은 키오스크로, 키오스크 쪽은 가스비를 대납해 제출한다. 물건을 받고 사용자가 "수령"을 눌러야 escrow가 가맹점에 지급된다. 수령 뒤에는 취소할 수 없다 |
| 반납 | 남은 자산을 원래 지갑으로 모두 돌려보낸다. 키를 파기하고 공장 초기화 상태로 돌아간다 |

결정 기록: `~/.claude/decisions/nu-54v-dk-toy/20261123-owner-shop-payment/`.

### 정정 (2026-11-23)

escrow는 사용자의 예치금이 아니라 **주문 한 건의 구매 보호**다.

- **escrow가 필요한 이유**: 돈을 먼저 보내면 물건을 못 받을 수 있다. 그래서 결제 금액을 escrow에 맡겨 둔다.
- **지급 조건**: 물건을 건넸고 사용자가 수령을 확인하면, 그때 가맹점에 지급한다.
- **수령 뒤 취소 불가**: 물건을 받은 뒤에는 결제를 취소할 수 없다.
- **보드 계정 예치는 escrow가 아니다**: 원래 지갑에서 보드 계정으로 자산을 보내 두는 것은 escrow가 아니다.
- **서명 시험 먼저**: 보드 계정이 정확한 개인키에서 나온 주소인지 확인하는 서명 시험은 자산을 보내기 전에 반드시 한다.

이전 판의 "escrow 입금", "입금한 지갑만 돌려받는다", "누구나 부르는 반환", "결제 금고에 미리 하는 묶기와 approve"는 모두 철회한다. 입금과 반납은 보통 송금이고, 계약은 주문 결제에만 쓴다.

## 3. 빠진 기능(제안)

1. **[중요] 보드를 잃으면 보드 계정의 잔액도 잃는다.** 백업이 없으므로 분실·고장·초기화 때 잔액을 되찾을 수 없다. 현금처럼 쓸 만큼만 넣도록 앱이 입금 화면과 초기화 화면에서 알린다. 버튼 초기화는 PIN을 요구한다. PIN을 5회 틀리면 기다리게 하고 지우지 않는다.
2. **반납 주소는 처음 설정 때 정한다.** 원래 지갑 주소를 PIN과 SW1로 확인해 보드에 저장하고, 반납 서명은 그 주소로만 한다. 앱만으로는 바꿀 수 없다.
3. **결제 내용 확인과 손실 한도(결정 S0, 2026-11-23: 앱이 확인).** 앱은 상태 안내와 함께 결제 금액·가맹점도 보여 주고, 사용자는 이를 보고 SW1을 누른다. 독립 표시 장치는 테스트넷 결제용 프로필에서 쓰지 않는다. 악성 앱이 실제 서명과 다른 금액을 보여 줄 수 있으므로 다음 세 가지로 손실을 제한한다.
   - 보드가 건당·일일 한도를 강제한다.
   - 보드는 운영자가 등록한 가맹점 키가 서명한 quote에만 승인한다.
   - 보드 계정 잔액이 최대 손실이 된다. 쓸 만큼만 넣도록 안내한다.
4. **보드 진품 확인.** 등록할 때 보드 인증서와 식별 키 서명을 휴대전화가 검증한다. 가짜 보드로 자산을 보내는 일을 막는다.
5. **자산을 보내기 전 서명 시험.** 체인마다 보드가 그 계정 키로 일회용 challenge에 서명한다.
   - 앱은 서명에서 주소를 복원(ecrecover 등)하고, 공개키로 주소를 다시 계산해 둘 다 같은지 확인한다.
   - 통과하기 전에는 입금 주소를 보여 주지 않는다.
   - 보드의 식별 키 서명(`{체인, 경로, 주소}`)도 함께 확인한다.
6. **여러 체인 계정.** 무작위 키 하나로는 체인별 파생 규칙(BIP32/SLIP-10)을 적용할 수 없다. 그래서 보드 안에서 무작위 seed를 만들고 체인별 계정을 파생한다. seed는 내보내지 않고 백업도 하지 않는다. 지금 HD 코드를 recovery UART 없이 쓰는 프로필이 필요하다. 다른 체인 자산에도 1번의 위험이 똑같이 있다.
7. **PIN을 5회 틀리면 기다리게 한다(결정 2026-11-23).** 5회 뒤부터 1분, 5분, 15분, 이후 1시간씩 기다려야 다시 입력할 수 있다. 자동으로 지우거나 영구히 잠그지 않는다. 전원을 껐다 켜면 그 단계의 대기를 처음부터 다시 센다. PIN을 잊으면 운영자가 서명한 초기화로 지우며, 이때 남은 잔액은 잃는다.
8. **자동 잠금.** 일정 시간 동안 쓰지 않으면 PIN을 다시 묻는다.
9. **DApp 메시지 서명.** EIP-191/712 서명이다. 내용은 휴대전화가 보여 주고, 보드는 한도와 도메인 정책을 강제한다.
10. **미결 주문 중에는 초기화와 반납을 막는다.** escrow가 수령 확인 전이면 반납하지 않는다. 지금 있는 규칙(W12 eraseblocked)을 넓힌 것이다.
11. **펌웨어 서명 검증, 롤백 방지, 디버그 포트 잠금.** 디버그 포트 잠금(APPROTECT)은 되돌릴 수 없으므로 출시 직전에 따로 결정한다.
12. **버튼 패턴 공장 초기화.** 앱이 없거나 휴대전화를 잃어버려도 보드를 초기화할 수 있다. 쓰는 중에 하며, 전원을 다시 넣을 필요가 없다.
    - 실수로 누르지 않도록 세 단계로 한다: SW2+SW3을 함께 5초 누름 → PIN 입력 → LED 확인 패턴 → 10초 안에 SW1 길게 누름(PIN 요구는 2026-11-23 결정).
    - PIN 입력이나 승인 대기 중에는 받지 않는다. 미결 주문이 있으면 거절한다.
    - 남은 잔액은 잃는다. PIN을 모르는 사람은 이 방법으로 지울 수 없다.
13. **LED 상태 패턴과 앱 안내.** 상태마다 하나의 패턴을 정해 앱 안내와 같은 표로 관리한다(`screens/board.json`). 버튼을 누를 때마다 누름이 접수됐다는 짧은 깜박임을 준다.

## 4. 설계

### 기본 방향(결정 S1, 2026-11-23: v2)

v2 상용 경로 위에 "결제용 프로필"을 추가한다. v2를 기준으로 삼는 이유는 세 가지다.

- 실물 보드와 휴대전화의 owner TLS 연결과 PIN 등록이 확인된 경로다.
- 가맹점이 서명한 quote를 보드가 검증한다.
- 지금 앱과 키오스크가 이 경로를 쓴다.

v1을 되살리면 펌웨어 변경은 적다. 대신 운영자 의존이 남고, 앱과 키오스크의 v2 경로를 다시 만들어야 한다.

구현 상태(2026-11-23): 결제용 프로필을 `app/spending.conf`, `core/src/nu54_order.c`, `app/src/device_order.c`, `app/src/device_pilot.c`에 구현했다. 호스트 시험과 실제 칩용 컴파일까지 확인했고 보드에는 기록하지 않았다.

- 보드가 서명하는 값은 실제 계약이 받아들인 공통 벡터(`packages/protocol/v2/testdata/order-lock.vectors`)와 같다.
- 자산을 보내기 전의 서명 시험은 읽기 동작이라 버튼 없이 응답한다(명령 `0x79`). 계정 키와 보드 식별 키가 함께 서명한다.
- 하루 한도의 기본값 100.00 TestUSDC는 구현할 때 정한 값이다(`CONFIG_NU54_SPENDING_DAILY_CAP`). 건당 한도는 허가의 값을 쓴다.
- 허가 하나에 가맹점이 하나인 제약과 부팅마다 허가가 필요한 제약은 그대로 남아 있다.
- 배포용 빌드 스크립트(`scripts/fw.py`)에는 아직 연결하지 않았다.

3단계(초기화, 반납, PIN 대기, LED)도 같은 날 구현했다. 호스트 시험과 실제 칩용 컴파일까지 확인했고 보드에는 기록하지 않았다.

- **별도의 지갑 키**: 사용자 자산의 키를 설치용 키(`INSTALL_PAYER`)와 분리했다. 설치용 키와 한 번만 쓸 수 있는 표식(write-once)을 지우면 보드가 상용 서비스를 다시 시작하지 못한다(`core/src/nu54_install.c`의 부팅 판정).
- **공장 초기화가 남기는 것**: 보드 식별 키, 설치 표식, 시각·버전 하한, 보드의 세대 번호. 사용자 자료는 남지 않는다. 지우는 것은 지갑 키, PIN, 소유자, 반납 주소, 결제 기록, 하루 누계다.
- **전원이 끊겨도 이어서 지운다**: 초기화 표시를 먼저 저장하고, 다음 부팅에서 남은 작업을 마친다. 끝나면 재시작하고 새 키를 만든다.
- **초기화를 막는 조건**: 아직 실행될 수 있는 결제 승인이 있으면 초기화와 반납을 거절한다. escrow에 잠긴 주문은 보드가 알 수 없으므로 앱이 확인해야 한다.
- **반납 주소는 한 번만 정한다**: 바꾸려면 초기화해야 한다. 나중에 휴대전화가 오염돼도 반납금을 다른 곳으로 돌릴 수 없다.
- **명령**: 반납 주소 `0x7a`, 반납 `0x7b`, 앱 초기화 `0x7c`, 운영자 초기화 `0x7d`·`0x7e`, 상태 `0x7f`. 앱 초기화와 반납은 SW1과 PIN, 운영자 초기화는 서명과 SW1이 필요하다.
- **감사 뒤 고친 것**: 초기화한 보드가 다시 등록되지 않던 결함, 서명한 주문의 유효 시간이 제한되지 않던 결함(지금은 180초), 복구 세션에서 운영자 초기화를 쓸 수 없던 결함, 소유자를 철회한 보드를 초기화할 수 없던 결함.
- **한도 밖의 이체**: 반납은 하루 한도에 들어가지 않는다. 저장한 주소로만 가고 SW1과 PIN이 필요하다.
- **버튼 순서**: SW3을 먼저 1초 넘게 누른 뒤 SW2를 더하면 복구 창도 함께 열린다. 두 버튼을 같이 누르도록 안내한다.
- **LED**: 누름 접수 0.6초 켜짐, PIN 대기 아주 짧게 다섯 번, 초기화 확인 대기 0.08초 간격 깜박임, 초기화 완료 1.5초씩 두 번.

### 계약(P06)

계약은 주문 결제에만 쓴다. 입금과 반납에는 쓰지 않는다. 지금 `SettlementV2.settle`은 결제 즉시 가맹점에 지급하므로(`SettlementV2.sol:265-303`), 수령 확인까지 맡아 두는 주문 escrow를 새로 만든다.

| 기능 | 내용 |
|---|---|
| 주문 잠금 `lock(quote, confirmer, merchantSig, payerSig)` | 주문할 때만 부른다. 보드 서명에 견적과 휴대전화 키(`confirmer`)가 함께 묶여 릴레이가 바꿀 수 없다. 휴대전화 키는 주문마다 묶이므로 미리 등록하지 않는다. 보드가 그 주문의 금액 이동에 서명하고, 릴레이가 가스를 내고 제출한다. 그 금액만 escrow에 들어간다 |
| 전달 표시 `markDelivered(orderId, merchantSig)` | 매장이 "전달 완료"를 누르면 기록한다. 확인 기한(기본 2일)이 이때부터 흐른다 |
| 수령 확인 `release(orderId, phoneSig)` | 사용자가 앱에서 수령을 누르면 휴대전화 키 서명으로 가맹점에 지급한다. 전달 표시가 있을 때만 받는다. 이후 취소할 수 없다 |
| 매장 청구 `claim(orderId)` | EVM 계약은 스스로 실행되지 않는다. 전달 표시 뒤 기한이 지나고 이의가 없으면 매장이 청구해야 대금이 나간다. 받는 주소는 주문을 잠글 때 정한 수취 주소로 고정이라, 누가 제출해도 다른 곳으로 가지 않는다 |
| 일괄 청구 `claimBatch(orderIds[])` | 여러 주문을 거래 한 건으로 청구한다. 기한 전·이의 중·이미 지급된 주문은 건너뛰고 `ClaimSkipped`에 이유를 남긴다. 한 건 때문에 묶음 전체가 실패하지 않는다. 수취 주소가 같은 주문끼리 묶고, 한 번에 최대 100건이며, 시험에서 실행 가스는 약 147만이었다. 지금 worker의 한도 500,000으로는 부족하다 |
| 이의 철회 `withdrawDispute(orderId, phoneSig)` | 이의를 낸 사용자가 물건을 받았다고 인정하면 지급한다. 전에 서명한 수령 확인으로는 할 수 없다 |
| 이의 제기 `dispute(orderId, userSig)` | 기한 안에 "못 받았어요"를 누르면 매장 청구를 막는다. 운영자가 지급 또는 환불로 정리한다 |
| 취소·미전달 환불 | 수령 전 가맹점이 취소하거나 정해진 기간 안에 전달 표시가 없으면 보드 계정으로 돌려준다 |
| 이벤트 | `OrderLocked`, `OrderDelivered`, `OrderReleased`, `OrderDisputed`, `OrderCancelled`, `ClaimSkipped` |
| 토큰 | 주문 금액을 서명 한 번으로 옮기려면 토큰이 서명 이동(EIP-3009 방식)을 지원해야 한다. 지금 TestUSDC에는 없다. approve는 쓰지 않는다 |
| 사용자 서명의 범위 | 수령·이의 서명은 전달 표시 시각에 묶인다. 전달 전에 한 서명이나 다른 전달에 대한 서명은 쓸 수 없다 |
| 배포 | 8283에 새로 배포한다. 배포 직전에 승인을 받는다. 배포할 때 토큰에 `setTrustedSender`로 escrow를 등록해야 한다. 등록하지 않으면 거부 모드인 계정으로 지급과 환불이 실패한다 |
| 감사에서 남은 것 | 이의 처리 기한(결정 필요), 전체 일시 정지, 잘못 보낸 토큰 회수, 휴대전화 분실 때 이의 수단, 서명과 잠금 사이의 기한 설정 변경 |
| 구현 상태 | `products/p06-stablenet-contracts/src/OrderEscrow.sol`과 `src/test-token/TestUSDC3009.sol`을 로컬에서 구현했다. 배포하지 않았다 |
| 기한 기본값 | 확인 기한 2일은 사용자가 정했다. 미전달 환불 기한 7일과 묶음 최대 100건은 구현할 때 정한 값이다 |

| 4 | 앱: 등록·활성화·입금·결제·반납·초기화 화면 | 앱 시험이 통과한다. 설계서 W03·W04·W10·W11·W12의 배치와 일치한다 |
| 5 | 키오스크·서버: 자동 조회, 주문번호 전달, 주방 조회, 준비 완료 알림, 정산 시스템의 일괄 청구 | 버튼을 누르지 않아도 결제 확정과 주문번호가 표시된다. 기한이 지난 주문 여러 건을 한 번에 청구하고, 이의 중인 주문만 제외되며, 재시도해도 이중 지급이 0건이다 |
| 6 | 실물 종단 시험: 보드 1대, Galaxy 1대, 키오스크 기기 1대 | 서명 시험 → 입금 → 결제(잠금) → 주문번호 → 준비 완료 알림 → 수령 확인 → 반납 → 초기화를 한 번에 통과하고, 원래 지갑 잔액이 입금하고 남은 금액과 같다 |

### 위험

- 실물 BLE로 결제한 적이 아직 없다. 키오스크와 휴대전화 사이, 휴대전화와 보드 사이 모두 해당한다. 6단계 전에 2·5단계 결과로 실물 왕복을 먼저 한 번 해 본다.
- S0에 따라 결제용 프로필은 독립 표시 규칙(security TM-002)에 예외를 둔다. 테스트넷 빌드에서만 켜고, 손실은 3장 3번의 한도로 제한한다.
- 보드 계정에는 백업이 없다. 보드를 잃으면 잔액도 잃는다.
- 보드를 훔친 사람은 4자리 PIN을 오래 시도할 수 있다. 1시간 간격이면 10,000가지를 모두 시도하는 데 약 417일이 걸린다. 쓸 만큼만 넣도록 안내한다.
- 키오스크 기기가 한 대 더 필요하다. 에뮬레이터에는 블루투스가 없다.
