# 여행자 주문·환전 결제·여행 도움 기획

2026-11-25 · 기준 코드 `4701806` · 상태: **큰 선택은 받았고 `제안`이라고 적힌 조건은 묻지 않았다. 원화 토큰 단계만 승인되었다. 다른 단계는 그 단계의 감사와 시안 승인 뒤에 구현한다.**

한국을 여행하는 사람이 이미 가진 스테이블코인으로 환전 없이 원화 가격을 결제하고, 줄을 서지 않고 주문하고, 여행지를 찾아 예약하고, 막히는 일을 물어볼 수 있게 한다. 이 문서는 지금 있는 것과 없는 것을 코드로 확인해 나누고, 유즈케이스와 기능, 위험, 순서를 정리한다.

조사는 정적 읽기로 했다. 키오스크 첫 화면만 에뮬레이터에서 직접 실행했다. 구현을 막는 바깥 조건만 2026-11-24에 조사했고 11장에 출처를 적었다. 법률·세무는 조사하지 않았고 "확인 안 됨"으로 적는다.

### 휴대전화 주문

- **등록한 매장 한 곳에서는 코드상 이미 된다.** 인터넷으로 메뉴를 보고 장바구니를 만들어 결제하며 키오스크를 거치지 않는다(`CustomerOrders.tsx:836`, `:968`, `:1993`). 이 경로를 끝까지 도는 시험은 없다.
- **키오스크를 막지 않는다.** 키오스크의 손님 화면과 휴대전화 주문은 따로 처리된다(`nearbyRelay.ts:80`). 블루투스로 동시에 붙는 휴대전화는 두 대까지다(`NearbyBluetooth.kt`, `links.size >= 2`).
- **처음 가는 매장에서는 안 된다.** 휴대전화는 매장 등록을 하나만 담고, 새 매장은 직원이 등록서를 발급해야 한다. 다른 매장 QR은 `SHOP_WRONG_BRANCH`로 막힌다(`CustomerOrders.tsx:1057`).
- **거리 확인과 매장 응답 시한이 없다. 받을 시각은 화면과 자료에 있으나 주문 계약 매장에서는 막힌다**(`CustomerOrders.tsx:1339`). 매장이 주문을 무시하면 환불 기한은 계약의 전달 기한(문서 기본 7일)이다.

### 환전 결제와 세금

- 다리(bridge), 환율 공급, 원화 정산, 환급 코드는 **없다.** 가격에는 세금 칸이 저장되지만 주문과 영수증까지 이어지지 않는다(`operator_catalog.go:110`). 결제 경로는 체인 8283, 토큰 이름, 소수 여섯 자리에 고정되어 있다. 매장마다 다른 토큰을 쓸 수 있지만 배포 승인을 켜면 달러 이름과 6자리만 통과한다.
- `OrderEscrow`는 정해진 토큰 하나만 받고 같은 토큰으로 내준다(`OrderEscrow.sol:109`, `:419`). 사용자가 낸 토큰과 매장이 받는 토큰이 다를 수 없다.
- 시험 토큰 `tKRWC`는 `receiveWithAuthorization`이 없어 **주문 계약의 토큰으로 쓸 수 없다**(`TestToken3009.sol`에서 0건). 소수 18자리는 서버의 배포 승인 검사(6자리)와 보드(64비트 금액, 한 번 한도 30,000,000단위)에도 맞지 않는다.
- 결제용 보드 펌웨어는 체인 8283과 이름 `NU54 Test USD`로만 서명한다. 결제 계정으로는 L2에서 서명할 수 없다. 복구용 지갑 빌드의 거래 서명은 별개다.
- **실제 보드는 허가에 적힌 매장 한 곳의 주문만 서명하고, 허가는 부팅마다 운영자가 넣으며 길어야 24시간이다**(`nu54_install.c:139`, `nu54_install.h:9`, `architecture/spending-wallet.md:146`).
- 보드의 계정 증명에는 신원 서명이 있으나 앱은 버리고 서버는 검사하지 않는다(`ownerWire.ts:128`, `wallet_return.go:69`). 시험 보드는 신원 서명을 0으로 채운다.
- 매장 QR에는 지점 번호만 있고 서버 주소가 없다(`shop-identity.ts:13`).
- 손님과 운영자가 같은 서버 포트를 쓰고 그 포트는 클라이언트 인증서를 요구한다(`opsd/commerce.go:492`). 주방의 취소 함수는 매장 수신 확인이 없으면 거절한다(`053:60`). 결제 뒤 취소는 재고를 되돌리지 않는다.
- 쓸 수 있는 것: 시험 시장 계약의 두 공급자 환율 검사 방식, 인덱서의 최종 확정 처리 방식, 가스 대납 계약, 운영자 서명 네트워크 목록.

### 여행과 도움

- 지도, 검색, 장소 상세, 식당 자리 예약, 보증금, 취소·일부 환불, 픽업 예약, 일정, 추천 코스 코드는 **있다.** 그러나 앱에 서버 주소가 비어 있어(`publicDeployment.ts:2`) 실행하면 "설정을 확인하세요"만 나온다. 장소 자료도 시험용뿐이다.
- 현재 위치, 가는 길, 날씨, 추천 장소 목록, 숙박·입장권·교통 예약, 사진은 **없다.** 앱의 위치 안내문은 위치를 읽지 않는다고 적고 있다.
- 여행 예약 결제는 이전 정산 계약을 쓴다. 지금의 주문 계약 매장에서는 **거절된다**(`107:265`, `CustomerOrders.tsx:1339`).
- 원격 문의, 채팅, 전화, 번역, 긴급 도움, 답변하는 운영 화면은 **없다.** 푸시 알림도 없다.
- 여행 화면은 한국어만 있다.

### 결제 내역

- 진행 중 주문과 최근 기록이 매장 이름·금액·시각으로 보인다. 여러 매장을 합친 목록, 환율, 세금, 품목, 거래 해시, 기간 검색이 없다. 서버가 주는 거래 해시와 전달 기한을 앱이 버린다(`customerClient.ts:37`). 확인 기한과 이의 기한은 저장한다.

| [중요][High] | 결제 뒤 취소는 재고를 되돌리지 않는다 | 자동 환불이 쌓이면 팔 수 있는 것이 품절로 남는다 | 시작 전 취소는 재고를 되돌린다 |
| [중요][High] | 계정 하나로 여러 매장을 쓰면 결제와 충전이 블록체인에서 이어진다 | 매장이 다른 매장의 결제와 원래 지갑을 볼 수 있다. 충전 서명이 원래 지갑과 보드를 공개 체인에서 잇는다(`architecture/spending-wallet.md`의 "원래 지갑은 노출되지 않는다"와 다르므로 확인이 필요하다) | 개인정보 안내에 적는다 |
| [중요][Mid] | 보드 분실, 하루 한도, 인터넷 끊김, 인덱서 정지, 중계 거래 막힘, 고정 환율과 시장의 차이 | 여행 중에 결제하지 못하거나 풀이 손해를 본다 | 단계마다 중단 시험과 화면을 둔다. 환율에는 계약의 최소·최대를 둔다 |
| [중요][High] | 자동 주방이 만들지 않은 주문을 전달로 기록한다 | 매장이 돌려줄 화면이 없고 시작 전 자동 환불도 쓰이지 않는다 | 시험 매장에서만 켜고 화면에 적는다. 손님의 확인 기간과 이의가 남는다. 매장은 운영 웹에서 전달 기록 전까지 취소한다 |
| [치명][High] | 거짓 완료 기록이 입금을 잠근다 | 완료된 입금은 환불되지 않는다 | 기록에 별도 키의 확인 서명을 요구하고, 입금한 사람이 이의를 내면 14일 안에 확인하지 못한 입금은 돌아간다. 한 사람이 키를 맡는 동안에는 보호가 약하다 |
| [중요][Mid] | 매장 사진의 저작권, 알레르기 번역 오류 | 잘못된 정보가 사람을 다치게 할 수 있다 | 알레르기는 매장이 넣은 값만 보이고 자동 번역하지 않는다. 사진은 매장이 올리고 형식과 크기를 제한한다 |

## 4. 원칙

1. **원화 가격이 기준이다.** 매장은 원화로 가격을 정하고 원화 토큰으로 받는다. 코인 금액은 그 순간의 환율로 계산해 보여 준다.
2. **확정된 것만 확정이라고 쓴다.** 환율, 입금, 지급, 주문번호는 각각 단계가 있고, 앞 단계가 정해진 확정 기준을 채우기 전에는 다음 단계가 없다. 한도 안의 빠른 경로만 예외다.
3. **보드가 승인하지 않은 돈은 움직이지 않는다.** 앱과 서버는 보드가 서명한 금액, 받는 곳, 시한을 바꿀 수 없다.
4. **막히면 정해진 곳으로 끝난다.** 주문은 전달되지 않으면 계약의 기한 뒤 손님에게, 전달되었고 확인 기간에 이의가 없으면 매장에 간다. 충전은 지급되지 않으면 원래 지갑으로 돌아간다. 거짓 완료에는 입금한 사람의 이의가 있다(규격 문서).
5. **위치와 대화는 필요할 때만.** 화면을 열고 동의한 동안에만 쓰고, 무엇을 보내는지 보여 준다.

## 5. 유즈케이스

### 줄 서지 않는 주문

- **주체와 시작 조건** 보드를 가진 여행자. 매장 근처 또는 가는 중. 매장은 주문을 받는 상태.
- **정상 흐름** 매장 선택(지도, 근처 목록, 매장 QR, 최근 매장) → 메뉴 또는 "지난번 그대로" → 옵션 → 받는 방법(매장 식사·포장) → 원화 금액과 낼 코인 확인 → 보드 승인 → 결제 확정 → 주문번호 → 준비 완료 → 전달 기록 → 받았어요.
- **예외** 너무 멀면 주문을 막고 이유와 거리를 보여 준다. 위치를 허용하지 않으면 매장 QR을 찍어 대신한다. 품절·가격 변경이면 바뀐 줄만 다시 확인받는다. 매장이 바쁨이면 예상 시간을 보여 주고 고르게 한다.
- **종료** 전달됨, 자동 환불, 손님 취소, 운영 웹 취소.
- **합격 증거** 키오스크에서 한 사람이 고르는 동안 휴대전화 세 대의 주문이 모두 번호를 받는다. 직원이 아무것도 누르지 않아도 번호가 나온다.

### 키오스크 앞에서 휴대전화로 바로 주문

- **정상 흐름** 키오스크 화면 구석의 매장 QR을 찍는다 → 그 매장 메뉴가 휴대전화에 열린다 → 위와 같다. 키오스크의 손님 화면은 바뀌지 않는다.
- **합격 증거** 앞사람의 장바구니가 그대로 남고 두 주문이 섞이지 않는다.

### 키오스크에서 고른 주문을 보드로 내기

- **정상 흐름** 키오스크에서 고름 → 받는 방법 → 결제 QR → 휴대전화가 주문을 읽고 확인 번호를 보임 → 키오스크에서 같은 번호를 고름 → 보드 승인 → 결제 확정 → 키오스크와 휴대전화에 주문번호.
- **예외** 시간이 지남, 거절, 연결 끊김, 결과 모름, 잔액 부족. 매장 QR과 결제 QR은 이름과 자리를 나눈다.
- **합격 증거** 옆 사람이 결제 QR을 먼저 찍어도 확인 번호가 달라 앞사람의 주문이 묶이지 않는다.

### 받은 것을 알리기

- **정상 흐름** 준비 완료 → 손님이 번호를 보임 → 매장이 전달을 기록 → 확인 기간이 시작됨 → 손님이 "받았어요" → 매장에 지급.
- **예외** 손님이 답하지 않으면 확인 기간이 끝난 뒤 매장이 지급을 청구할 수 있다. 못 받았으면 확인 기간 안에 이의를 낸다. 준비 완료에서는 아직 받았다고 알릴 수 없다.

### 매장의 주문 받기

- **정상 흐름** 확정된 주문이 번호 순서로 처리된다 → 조리 시작 → 준비 완료 → 안내판과 휴대전화 → 전달. 주방 태블릿을 연결하기 전에는 자동 주방이 이 단계를 기록한다.
- **예외** 재료 소진은 운영 웹에서 한 번에 품절로 바꾼다. 바쁨을 켜면 새 주문의 예상 시간이 늘거나 멈춘다. 시한 안에 시작하지 않은 주문은 먼저 크게 알리고, 다음 시한에 자동 환불한다.
- **합격 증거** 주방이 꺼져 있을 때 들어온 주문이 시한 뒤 환불되고, 손님에게 이유가 보인다.

### 원래 지갑에서 충전

- **주체와 시작 조건** L2에 시험 USDC를 가진 여행자. USDT는 첫 단계에서 뺀다. 서명 시험을 마친 보드.
- **정상 흐름** 충전할 금액 → 앱이 1회용 충전 번호로 환전 페이지를 엶 → 환율·수수료·받을 원화 안내 → 원래 지갑의 이체 서명 → 입금 → 금액별 확정 기준을 채움 → 원화 토큰이 보드 계정에 도착 → 적용 환율과 실제 원화를 기록.
- **예외** 지급 마감(견적 만료에서 2시간)까지 원화가 지급되지 않으면 그 2시간 뒤부터 서명자 둘로, 입금에서 7일 뒤에는 누구나 보낸 거래로 원래 지갑에 돌아간다. 서명한 뒤 견적이 만료되면 코인은 나가지 않고 다시 견적을 받는다. 보드 주소로 L2의 코인을 보내면 꺼낼 수 없다고 보내기 전에 알린다.
- **합격 증거** 어느 단계에서 서버를 꺼도 입금 합과 지급·환불 합이 맞고, 같은 입금이 두 번 지급되지 않는다.

### 원화로 결제하고, 모자라면 충전

- **정상 흐름** 주문 또는 예약의 원화 금액 → 보드 계정의 원화 토큰으로 승인 → 예치 확정 → 주문번호.
- **모자랄 때** 결제를 시작하지 않는다. 모자란 금액과 충전 버튼 → 위 충전 → 같은 장바구니의 가격·품절 확인 → 결제.
- **합격 증거** 모자란 잔액으로는 보드에 승인을 요청하지 않는다. 충전 중 품절된 주문은 돈을 빼지 않고 알린다.

### 결제 내역 보기

- **정상 흐름** 월별 목록(매장 그림, 이름, 원화 금액, 상태, 시각) → 종류 고르기 → 항목 선택 → 상세.
- **상세** 품목과 옵션, 정가, 세금, 뺀 금액, 낸 원화, 진행 단계(예치·전달·지급·환불), 주문번호, 매장 정보, 거래 링크, 영수증 공유, 문의하기. 코인 금액과 환율, 수수료는 결제가 아니라 충전의 상세에 둔다.
- **예외** 확인하지 못한 단계는 "확인 중"으로 두고 마지막 확인 시각을 적는다.

### 여행지 찾기와 예약

- **정상 흐름** 지도에서 추천·분류·영업 중으로 좁히기 → 장소 상세(사진, 설명, 시간, 가격) → 가는 길(지도 앱을 엶) → 예약(날짜, 인원) → 원화 금액 → 보증금과 잔금 결제 → 예약 확인과 미리 알림 → 도착 확인.
- **예외** 보증금과 잔금이 취소 기한 앞뒤로 어떻게 되는지 결제 전에 보여 준다. 업체 취소와 노쇼 규칙을 나눈다.
- **합격 증거** 같은 자리를 두 사람이 잡으려 할 때 한 사람만 결제된다. 취소하면 안내한 금액이 돌아온다.

### 여행 중 도움 요청

- **정상 흐름** 도움 버튼 → 무엇이 막혔는지 고르기(주문, 결제, 예약, 길, 기타) → 관련 주문·예약을 붙이기(선택) → 글·사진 보내기 → 답변 → 해결 또는 이어 묻기.
- **담당자 쪽** 대기 목록, 붙은 주문의 상태(읽기), 답변, 넘기기, 종료, 기록.
- **예외** 긴급이면 공식 신고 번호를 먼저 보여 준다. 근무 시간 밖이면 언제 답하는지 말한다. 담당자는 돈을 움직이거나 보드 정보를 볼 수 없다.
- **합격 증거** 붙이지 않은 정보는 담당자 화면에 보이지 않는다. 종료 뒤 정해진 기간에 지워진다.

| 결제 내역 | 매장 통합 목록, 상세, 기간·상태 거르기, 영수증 | 서버의 거래 해시·기한 | 목록 응답 형식 |

## 7. 정한 것

2026-11-24부터 25일까지 사용자가 고른 것이다. `제안`이라고 적힌 조건은 아직 묻지 않았다.

- **환전은 입금할 때 한다.** 여행자가 자기 지갑에서 보낸 코인이 원화 토큰으로 바뀌어 보드 계정에 들어온다. 보드 계정은 보드가 만든 새 계정이다.
- **결제는 보드 계정의 원화 토큰을 먼저 쓴다.**
- **원화 토큰이 지불할 금액보다 적으면 결제하지 않고 충전을 안내한다.** 모자란 금액을 보여 주고, 충전이 확정된 뒤 같은 주문을 다시 결제한다.
- **예약도 같은 규칙을 쓴다.** 결제하는 순간의 L2 이체(채택하지 않은 안, 규격 문서)는 만들지 않는다. 보드는 L2에서 서명하지 않는다.
- **충전은 여행자의 원래 지갑에서 한다.**
- **충전은 환전 페이지에서 이체 서명(EIP-3009) 한 번으로 한다.** 서명에 금액, 입금 계약, 시한, 견적, 보드의 StableNet 주소를 묶는다. 가스는 중계 서버가 내고 계정마다 하루 횟수와 최소 금액을 둔다.
- **시험 원화 토큰은 소수 2자리다**(이름 `NU54 Test KRW`, 기호 `tKRW`). 다리보다 먼저, 맨 앞에 만든다. 예전 18자리 `tKRWC`는 주문에 쓰지 않는다. 지금의 `TestUSDC` 매장은 그대로 두고 원화 매장은 새 주문 계약으로 새로 등록한다. 보드의 한 번 한도는 단위 수만 보므로 30,000,000단위는 300,000원이고 하루 한도 기본값 100,000,000단위는 1,000,000원이다. 자릿수는 코드의 고정 숫자가 아니라 토큰 정보로 읽는다. 실제 원화 토큰의 자릿수는 확인 안 됨이다.
- **새 원화 매장은 StableNet의 메인 코인 KRWC를 먼저 쓴다.** 계정의 코인 잔액이 주소 `0x…1000` 토큰의 잔액과 같다. 체인에서 그 토큰의 이름과 기호는 `WKRC`, 18자리이고 받기와 보내기의 이체 서명이 있다(2026-11-25에 시험망에서 읽음). 모든 화면에서 이름은 `KRWC`이고 토큰 상세에 탐색기의 이름 `WKRC`를 함께 적는다. 서명에는 `WKRC`를 쓴다. 보드는 금액을 8바이트로 다루므로 0.01원 단위로 세고(`boardDecimals` 2), 서명과 검사에서만 18자리로 바꾼다. 그래서 한 번 300,000원과 하루 1,000,000원의 한도가 `tKRW`와 같다. 0.01원보다 작은 잔액은 반납하지 못한다. 이 이름은 이 주소에서만 받는다. `tKRW`는 로컬 시험과 금액이 큰 시연에 남긴다. 이 저장소의 문서에 적힌 시험망 수도꼭지는 주소마다 하루 2,000 WKRC다. 체인의 거래 금지 목록에 오른 계정은 코인을 받지도 보내지도 못해서, 그동안 지급과 환불은 주문 계약에서 기다린다. 펌웨어 원본은 바꾸지 않았고 시험 보드의 사본만 바꿨다.
- **남은 원화는 원래 지갑으로 반납한 뒤 환전 페이지에서 되바꾼다.** 규약은 되바꾸기 감사에서 설계하고(2026-11-27에 바꿈) 구현은 충전이 시험을 통과한 다음에 한다. 그전에는 "준비 중"으로 보이고 반납은 된다. 자세한 규칙과 규약을 되바꾸기 감사로 미루는 제안은 규격 문서 5장에 있다. 반납 주소를 저장할 때 직접 관리하는 지갑인지, 거래소 주소가 아닌지 확인받는다. `tKRW`는 되바꾸기가 열리기 전까지 시험 토큰 받기로 얻을 수 있고 열리면 끈다.
- **L2는 Base Sepolia 하나로 시작한다.** 작은 금액은 safe 단계, 큰 금액은 최종 확정 뒤에 지급한다. 기준 금액과 하루 한도는 아래 풀의 한도를 따른다. 2026-11-24에 공개 시험망에서 두 번 잰 값은 최신 블록보다 safe가 204초·208초, 최종 확정이 1,217초·1,221초 늦었고 StableNet은 0초였다.
- **환율은 공급자를 갈아 끼울 수 있게 만들고, 처음에는 고정 환율을 쓴다.** 공급자는 값, 시각, 이름을 주는 같은 모양이다. 처음에는 설정에 적은 고정 환율 공급자 하나를 쓰고 화면에 시험용 고정 환율이라고 적는다. 바깥 공급자를 쓸 때는 둘 이상이 1% 안에서 맞고 120초 안의 값이며 직전보다 5% 넘게 변하지 않을 때만 견적에 서명한다. 견적은 2분 유효하고 환율은 사용자가 서명할 때 고정되며 0.01원 아래는 버린다. 환율과 수수료는 나눠 보인다.
- **원화 가격은 원 단위다.** 운영자가 적은 가격·세금·할인이 원 단위가 아니면 서버가 거절한다. 환전으로 받은 잔액의 0.01원은 막지 않고 그대로 보인다. **달러는 소수 둘째 자리까지 보이고 나머지는 버린다. 반올림하지 않는다**(설계 결정 N31과 같다). 계산과 서명에는 버리지 않은 금액을 쓴다. CSV의 기준 단위는 자르지 않는다. **달러를 적는 곳(보내기, 메뉴 가격·세금·할인)은 둘째 자리까지만 받는다.** 잔액의 셋째 자리 이하는 보내기로 보낼 수 없고 반납은 전액 나간다.
- **원화는 메뉴 밖에서도 원 단위다(2026-11-27 사용자 결정).** 원화 토큰에서 서버는 메뉴 가격처럼 여행 예약의 예약금·잔금과 구독 금액을 원 단위로만 받는다. 서버가 계산하거나 받는 환불 금액은 손님에게 유리하게 원 단위로 올리고, 낸 금액을 넘기지 않는다. 달러 토큰은 그대로다. 휴대전화 앱이 원화를 원 단위로 보이게 된 뒤로, 이 규칙이 없으면 보이는 금액과 움직이는 금액이 원 미만만큼 달라질 수 있어서다.
  - **막는 곳.** `opsd`는 예약 보류 요청의 예약금·잔금과 운영자의 환불 신청 금액을 메뉴 가격과 같은 검사(`wholePrice`)로 거절한다. 운영 웹의 환불 금액 입력은 원화를 원 단위로만 받는다. 장부는 마지막으로 한 번 더 막는다(migration 127). 새 예약 조건, 새 예약, 새 구독 상품, 새 구독 동의, 환불 신청이 대상이다. 예약 조건과 구독 상품은 서버 API 없이 SQL로 넣으므로 장부의 검사가 유일한 검사다.
  - **장부가 1원을 아는 방법.** 장부에는 토큰의 자릿수가 없었다. `opsd`가 시작할 때 원화 매장의 토큰 주소와 1원의 기준 단위 수(`tKRW` 100, `KRWC` 10^18)를 `ledger.whole_amount_asset`에 적는다. 한 번 적힌 값은 바꾸지 못하고, 다른 값을 적으려 하면 `opsd`가 시작하지 않는다. 적히지 않은 자산(달러)에는 아무 규칙도 더해지지 않는다. 이 방법은 구현하면서 정한 것이고 승인 대기다. 12장에 적었다.
  - **환불 계산.** 취소한 예약이 돌려받는 금액은 `원지급액 × 환불 비율`을 원 단위로 올린 값이고, 그 값이 원지급액보다 크면 원지급액이다. 33,333원의 50%는 16,666.50원이 아니라 16,667원이다. 나눠서 돌려줄 때는 10,000원과 6,667원처럼 원 단위로만 신청할 수 있고, 합이 16,667원이 된 뒤에는 1원도 더 신청할 수 없다. 원 미만이 든 채 저장된 33,333.50원을 전액(100%) 돌려줄 때는 33,334원이 낸 금액을 넘으므로 33,333.50원이다. 이때만 원 단위가 아닌 금액을 받으며, 남은 원금 전부일 때로 한정한다. 손님에게 보이는 예상 환불액, 신청 한도, 예약을 끝내는 기준, 체인으로 나가는 금액, 장부 전표는 모두 같은 숫자다.
  - **이미 저장된 금액.** 바꾸지 않는다. 원 미만이 든 예약 조건은 금액을 고치기 전까지 새 예약을 받지 못하고, 이미 받은 예약과 이미 동의한 구독은 그 조건으로 계속 간다. 그 예약의 환불도 위 계산으로 올린다. 손으로 정해야 하는 경우가 하나 있다. 취소했지만 아직 끝나지 않은 예약에 옛 계산의 금액(33,333원 중 16,666.50원)이 이미 환불된 경우다. 새 기준은 16,667원인데 모자란 0.50원은 원 단위도 아니고 남은 원금 전부도 아니어서 신청을 받지 않는다. 배포 전에 [읽기 전용 질의](../../../products/p05-operations-backoffice/COMMERCE.md#whole-won-amounts)로 그런 줄을 먼저 본다.
  - **지금 닿는 범위.** 원화 토큰은 주문 계약 매장에만 등록할 수 있고(`cmd/opsd/commerce.go`의 등록 검사), 주문 계약 매장은 메뉴 주문만 결제받는다(위 2장 "여행과 도움"). 주문 계약은 주문 금액 전부를 돌려주며 일부나 비율로 돌려주는 기능이 없다(`OrderEscrow.sol`의 `_refund`). 그래서 오늘 원화로 결제된 여행 예약, 구독, 일부 환불은 없다. 이 규칙은 그 길이 열리기 전에 넣은 것이고, 시험은 이전 정산 계약 경로에 원화 토큰을 붙여(운영 설정으로는 만들 수 없는 구성) 확인했다.
- **세금과 환급은 결제 금액에 미리 반영한다.** 품목마다 환급 대상과 세율을 설정하고, 자격이 있는 여행자에게는 환급액을 뺀 최종 금액으로 결제를 요청한다. 주문 계약은 그 금액 하나를 매장에 지급하며 나누지 않는다. 가격은 세금 포함이고 세금은 품목 줄마다 원 단위로 버려 계산한다(제안). 정가는 공급가액과 세금의 합이고 낸 금액은 정가에서 뺀 금액을 뺀 값이다. 세금은 품목 줄마다 원 단위로 버린다. 정가·공급가액·세금·뺀 금액·낸 금액을 품목별로 저장하고 영수증에 보이며, 취소는 실제 낸 금액으로 한다. 시험 단계의 자격은 운영자가 켠 시험용 표시이고 신원 정보는 받지 않는다. 자격을 확인하지 못하면 정가로 결제한다.
- **손님은 결제한 보드로 확인한다.** 서버가 주문마다 새 값을 주고, 보드가 계정 증명(`NU54_ACCOUNT_PROOF_OP`)으로 서명하면 서버가 복원한 주소를 그 주문의 결제 주소와 대조한다(2026-11-27 결정). 다른 사람의 보드는 서명이 맞아도 주소가 달라 거절된다. 기기와 휴대전화는 어디에도 등록하지 않는다. 직원 등록서는 운영 단말과 기존 매장에만 남긴다. 결제 전 재고는 계정마다 한 건, 짧게만 잡는다. 매장은 자기 주문만 본다.
- **주문은 매장 반경 안에서 받는다.** 반경의 시작값은 1km이고 매장마다 바꾼다. 위치를 거부하면 매장 QR로 대신하고, 예약 주문은 거리를 보지 않는다. 거리 검사의 좌표는 휴대전화 안에서만 쓰고 보내거나 저장하지 않는다. 지도와 가는 길에서 위치를 보내야 하면 따로 동의를 받는다. 여기서 예약 주문은 자리·체험 예약이다.
- **품절, 바쁨, 멈춤은 운영 웹에서만 바꾼다.** 운영 웹에서 여러 품목을 골라 한 번에 품절로 바꾸고 되돌린다. 재료로 묶는 자료는 만들지 않는다. 만들 수 없는 주문은 주문마다 "준비할 수 없음"으로 취소한다. 자동 주방이 켜진 동안에는 **운영 웹에서 주문번호로 찾아 전달이 기록되기 전까지 취소하고 환불한다.** 권한이 있는 사람이 한 번 더 확인하고 누르며 누가 눌렀는지 남긴다. 품절 표시와 재고 수량은 따로 두고, 멈춤에는 다시 받을 시각을 적되 자동으로 풀지 않는다. 누가 언제 바꿨는지 남긴다. 이미 결제한 주문은 바뀌지 않고 결제 전 장바구니는 결제할 때 다시 확인한다.
- **카페 주문은 모두 바로 만든다.** 받을 시각을 정하는 주문은 첫 범위에서 뺀다. 식당과 체험의 시간 예약은 여행 단계에 있다.
- **매장이 시작하지 않은 주문은 결제가 확정된 때부터 5분에 매장에 크게 알리고 15분에 취소해 환불한다. 주문마다 절대 시한 하나를 저장한다. 서버가 꺼져 있었으면 한 번 미루고 결제부터 합쳐 60분까지다(제안).** 자동 주방이 켜져 있으면 시작이 바로 기록되어 이 규칙이 쓰이지 않으므로, 자동 주방을 끈 시험으로 확인한다. 매장이 바쁨을 켠 동안 결제한 주문은 알린 시간에 10분을 더한 때와 15분 가운데 늦은 쪽에 취소하고, 60분을 넘지 않는다. 15분이 지나고 시작 전이면 손님이 휴대전화에서 먼저 취소할 수 있다. 바쁘지 않으면 손님 취소와 자동 취소가 같은 시각이라 손님 취소는 바쁠 때 쓰인다. 손님 취소에는 보드 버튼이 필요 없고 돈은 보드 계정으로만 돌아간다. 알린 시간과 시한은 결제할 때 주문에 고정한다. 시작과 취소는 서버가 하나만 받아들이고 진 쪽에 이유를 보인다. 값은 매장마다 바꾼다. 서버가 멈추면 계약의 전달 기한이 마지막 안전 장치다.
- **준비 완료 안내판은 같은 앱에서 따로 열 수 있고 손님용 화면의 소리는 기본으로 끄며 새 번호가 생기면 잠깐 강조한다. 연결이 끊기면 마지막 확인 시각을 보이고, 4개 밖의 번호는 작게 두며, 전달을 기록하면 사라진다.**
- **키오스크 첫 범위:** 첫 화면(여기서 주문, 휴대전화로 주문 QR), 원화 가격, 독립 옵션, 사진·설명, 매장 식사·포장, 바쁨·멈춤과 한 번에 품절과 휴무일, 준비 완료 안내판. 새 주문 소리와 5분 알림은 주방을 연결할 때 켠다. 매장의 태블릿은 손님용 한 대다. **주방용은 필요하지만 기기가 모자라 이번에는 두지 않고, 주방 태블릿이 할 일(시작, 준비 완료, 전달 기록)은 자동으로 수행한다. 주방 태블릿은 나중에 연결한다.** 자동 주방은 시험 매장마다 하나의 자격으로 주방 상태 변경 요청을 보내는 별도 프로세스다. 카페 주문은 주방 단말 자격으로 바꿀 수 없고(`053`), 지금의 운영자 자격은 준비할 수 없음까지 할 수 있으므로, 시작·준비·전달만 할 수 있고 시험 매장에만 쓰는 권한(`pickup_auto`)을 새로 둔다. 주방을 연결할 때 끈다. 시험 체인이면서 시험 매장으로 표시한 지점에서만 켜지고 하나라도 아니면 서버가 거절한다. 손님 화면과 운영 웹에 "시험 매장 · 자동 주방"이라고 적는다. 만든 것을 확인하지 않으므로 손님의 확인 기간과 이의가 지키는 길이다. 시작, 준비, 전달까지의 시간은 설정이며 시작값은 접수 뒤 30초, 알린 시간, 준비 뒤 2분이다. 바쁘지 않을 때의 알린 시간은 매장 설정이고 시작값은 5분이다. 자동 주방이 다시 켜지면 멈춘 곳에서 이어서 기록하고 건너뛰지 않는다. 확인 기간은 사용자가 정한 2일이다(`architecture/spending-wallet.md`). 1시간은 로컬 체인의 자동 시험에서만 쓰고, 사람이 쓰는 시험 매장은 2일이다. 메뉴·가격·사진은 운영 웹에서만 바꾸고 매장이 올린 사진만 쓴다. 태블릿의 기기 설정은 원격으로만 바꾼다. 인쇄, 겸용 태블릿, 품목별 매출은 뺀다.
- **카페 옵션은 묶음으로 적고 게시할 때 조합을 만든다.** 온도, 크기, 샷처럼 따로 고르는 옵션을 운영 웹에 묶음으로 적으면 게시할 때 조합마다 메뉴 줄 하나를 만들고 화면은 묶음별로 보인다. 가격, 재고, 장바구니, 영수증의 기준은 지금처럼 상품과 옵션 하나다. 게시할 수 있는 줄은 600개, 묶음은 상품마다 4개까지이며 넘으면 게시할 때 거절한다. 옛 SQL은 고치지 않고 새 이전 파일로 바꾼다.
- **메뉴 사진은 운영 서버에 두고 키오스크가 지금의 인증 연결로 새 경로에서 받는다.** JPEG와 PNG를 5MB, 가로·세로 4,096까지 받고 서버가 800×600 JPEG 150KB 아래로 다시 만들어 위치 정보와 숨은 자료를 없앤다. 상품마다 1장, 지점마다 200장이다. 게시 자료의 SHA-256과 다르면 보이지 않고, 사진이 없으면 상품 이름만 보이며 주문을 막지 않는다. 키오스크에만 보인다. 올릴 때 저작권을 확인받는다. 새 라이브러리를 쓰지 않는다.
- **지도와 길 안내는 네이버, 장소와 예약은 우리 자료다.** 지도를 열면 보는 지역과 접속 주소가 네이버에 전달되므로 안내문과 동의 화면에 적는다. 길 안내는 설치된 지도 앱을 연다. 지도 부분은 한 컴포넌트로 감싸고, Client ID가 없거나 지도가 열리지 않으면 목록과 지금의 자체 지도로 동작한다. Client ID는 사용자가 발급하고 저장소 밖에 둔다. 구현할 때 라이브러리와 SDK를 내려받는다. 시험 장소는 한 지역 30곳 안팎의 공공장소와 가상의 매장이다. 날씨는 뺀다.
- **네이버 장소 검색은 걸러 낼 수 있을 때 더한다.** 거르는 기준(분류, 언어, 예약 방법, 결제 수단, 접근)과 확인하지 않은 장소를 숨기는 것은 제안이다. HUB의 약관을 확인할 때까지 보류한다(11장).
- **예약은 식당 자리와 시간제 입장권·체험이다.** 보증금과 잔금은 서로 다른 주문 두 건이고 한 건은 전액 지급 또는 전액 환불만 한다. 취소 기한 전이면 둘 다 환불하고, 뒤면 보증금은 업체에 지급하고 잔금은 환불한다. 늦은 취소에도 손님의 이의가 되고 14일 안에 정하지 않으면 보증금도 손님에게 돌아간다(제안). 예약 끝에서 하루를 더한 시각이 결제 뒤 60일보다 앞인 것만 받는다(제안. 사용자가 고른 것은 60일 안이다). 계약의 전달 기한이 결제 시각부터 세기 때문이다. 기한이 매장마다 하나이므로 예약은 별도 매장 등록을 쓴다(제안). 두 주문이 모두 예치되어야 예약이 확정되고, 10분 안에 안 되면 먼저 낸 것을 취소한다(제안). 노쇼 보증금은 손님이 이의를 내면 운영자가 14일 안에 정해야 지급되고, 정하지 않으면 손님에게 돌아간다고 결제 전에 알린다(제안). 업체는 운영 웹에서 시간과 인원을 넣고 예약과 도착을 본다. 하루 전과 한 시간 전에 앱이 알린다.
- **문의는 매장과 운영자로 나눠 보낸다.** 준비·픽업은 매장, 결제·환불·보드·길·예약 분쟁은 운영자에게 간다. 매장이 5분 안에 답하지 않으면 운영자에게도 보인다. 답은 사람이 여행자의 언어로 하거나 준비한 문장을 고르고, 담당자는 읽기와 답변만 하며, 환불은 이의 절차로만 한다. 비밀 값은 묻지도 받지도 않고 긴급한 일은 공식 번호로 넘긴다. 답변 시간은 설정이고 화면에 보인다. 사진은 위치 정보를 지우고, 대화와 사진은 대화를 끝낸 때부터 30일 보관하며, 분쟁 중이면 분쟁이 끝난 때와 30일 가운데 늦은 때까지 둔다. 푸시, 실시간 번역, 자동 답변은 첫 단계에서 뺀다.
- **첫 출시 언어는 한국어와 영어다.** 여행자가 지나는 화면 전체와 키오스크 손님 화면을 두 언어로 내고 장터, 개발용 화면, 주방 화면, 운영 웹은 뺀다. 문장은 파일로 모으고 언어마다 키가 같은지 시험한다. 돈과 관련된 문장은 사람이 검수한 뒤 낸다. 앱은 휴대전화 언어를 따르고 한국어가 아니면 영어를 쓰며 설정에서 바꾼다. 메뉴 이름은 운영 웹의 한·영 칸을 쓰고 없으면 한국어 그대로 보인다. 금액은 언제나 원화로 보인다.
- **풀의 한도(시험 원화, 설정값):** 충전 1건 1,000~300,000원, 보드와 원래 지갑 각각 하루 1,000,000원(2026-11-27), 처음 쓰는 지갑과 보드의 짝은 첫 충전 50,000원까지(서버만 막음), 풀 하루 지급 3,000,000원, 풀 5,000,000원. 빠른 경로는 1건 50,000원, 하루 합 500,000원. 수수료는 0이고 견적에 칸만 둔다. `tKRW` 풀은 운영자가 발행해 채우고 KRWC 풀은 얻어서 채우며, 자동으로 채우지 않는다. 한도를 올리려면 두 사람의 승인과 24시간 대기가 필요하고, 내리거나 멈추는 일은 한 사람이 바로 한다. 되바꾸기는 풀에 있는 코인 안에서만 한다. 입금 계약으로 그냥 보낸 코인은 두 사람의 승인으로 보낸 주소에만 돌려준다. 하루 전송 횟수와 시험 토큰 한도는 배포할 때 정한다.
- **이번에는 한 사람이 시험 키를 모두 맡는다.** 계약과 절차는 셋 중 둘의 서명을 그대로 쓰고 키는 서로 다르게 만든다. 환불 키는 중계 서버 밖에 둔다. 한 사람이 맡는 동안에는 둘의 서명이 실수 하나를 막지 못하고, 키가 한꺼번에 새면 모든 보호가 사라지므로 이 사실을 화면과 기록에 적는다. 다른 사람의 자산을 받기 전에 여러 사람이 나눠 맡는 일을 다시 정한다.
- **자동 취소(제안):** 시작, 손님 취소, 운영 취소, 시한 취소를 한 함수로 모은다. 판매 행 → 진행 행 순서로 잠그고 아직 시작 전·전달 전인 주문에만 바꾸며 진 쪽에 이유를 준다. 매장 수신 확인은 조건에서 뺀다. 계약의 취소 서명에는 상태와 시한이 없으므로 서명 직전에 체인 상태를 다시 읽는다(제안). 건수와 금액 상한은 정했다: 지점마다 한 시간 10건 또는 300,000원(달러 매장 300달러), 영업일 하루 30건 또는 1,000,000원(1,000달러) 가운데 먼저 닿는 쪽이고 설정이다. 넘으면 그 지점의 자동 취소와 새 주문을 멈추고 운영 웹에 크게 알린다. 권한이 있는 사람이 이유를 적고 다시 켜며 자동으로 켜지지 않는다. 손님에게는 "매장이 확인하고 있습니다. 지금 취소할 수 있습니다"라고 보인다. 손님 취소와 운영 취소는 세지 않고 멈추지 않는다. 주방이 꺼져 있는 시간은 빼지 않는다. 시작 전 취소는 재고를 되돌린다. 환불은 확정되어야 끝났다고 쓴다.
- **첫 단계의 충전 코인은 USDC다.** USDC 주소는 설정으로 두고 이체 서명의 이름과 버전은 토큰에서 읽는다. 로컬과 공개 시험망 시연은 우리 시험 USDC를 쓴다. 배포 승인 뒤 Circle의 Base Sepolia USDC로 충전을 한 번 시험하고 차이를 기록한다. USDT는 이체 서명이 없어 첫 단계에서 뺀다. 입금 계약에는 다른 방식을 더할 자리를 두고, 앱과 환전 페이지에는 USDT를 준비 중으로 보인다. StableNet의 시험 토큰 `tUSDT` 등은 바꾸지 않는다.
- **열린 주문이 있어도 남은 잔액은 반납한다.** 이 결정은 `architecture/spending-wallet.md`의 "미결 주문 중에는 막는다"와 "수령 전 주문이 없을 때만"을 대신한다. 지금 잠그는 중인 주문이 있을 때만 막는다. 반납 화면은 지금 돌려받는 금액과 나중에 돌아올 수 있는 금액을 주문별로 나눠 보이고, 나중에 돌아온 금액은 앱이 알아채면 다시 반납할지 묻는다. 자동으로 보내지 않는다. 열린 주문이 있으면 앱에서 보드를 초기화하지 못하고, 보드 버튼 초기화는 앱이 막지 못하므로 잃는 금액을 첫 설정과 반납 화면에서 미리 알린다. 대여 보드는 열린 주문이 없을 때만 반납 완료로 본다. 끝나지 않은 충전이 있으면 앱에서 보드 초기화를 막는다(2026-11-27). 반납 완료를 막는 것은 제안이다.
- **결제 목록은 하나이고 처음에는 결제만 보인다.** 위에서 종류(결제, 충전, 되바꾸기, 반납)를 고른다. 되바꾸기는 구현될 때까지 보이지 않는다. 취소와 환불은 원래 결제 항목 안에 보인다. 날짜별로 나누고 달마다 쓴 원화 합계를 보이며 환전 합계와 섞지 않는다. 50건씩 읽는다. 앱을 지운 뒤에는 서버가 같은 계정의 기록을 다시 보내고, 초기화한 보드의 옛 기록은 다시 연결할 수 없다. 확인하지 못한 단계는 확인 중으로 두고 마지막 확인 시각을 적는다.
- **받는 곳은 보드가 만든 주소 하나다.** 앱은 그 주소와 자산을 보이고 복사 버튼을 둔다. 이 화면은 StableNet 원화 토큰 전용이며 L2로 보낸 USDC·USDT는 꺼낼 수 없다고 먼저 보인다. 충전은 이 주소가 아니라 환전 페이지에서 한다. 휴대전화가 한 대이므로 QR을 쓰지 않는다.
- 충전을 기다리는 동안 주문은 장바구니로만 남고 재고를 잡지 않는다. 충전 뒤 가격과 품절을 다시 확인한다.
- 모자란 금액보다 조금 넉넉한 충전 금액을 제안하고, 실제로 들어온 원화를 보여 준다.
- 보드를 잃으면 충전한 원화도 잃는다는 안내와 "쓸 만큼만"을 충전 화면에도 보인다.
- 메뉴를 고르는 화면에서 잔액이 모자란 것을 미리 알린다.

환전의 자세한 규칙은 [충전과 되바꾸기 규격](traveller-exchange.md)에 있다. 그 문서에는 2026-11-27의 결정을 반영했고, 아직 확정하지 않은 것은 제안으로 적혀 있다.

## 8. 화면

- **결제 탭**: 위에는 진행 중 주문, 아래에는 월별 결제 내역. 항목은 매장, 원화 금액, 상태 한 줄. 누르면 상세.
- **홈**: 진행 중 주문과 오늘 예약을 할 일에 넣는다.
- **둘러보기 탭**: 지도가 첫 화면. 추천, 분류, 검색, 근처 매장 주문, 내 예약, 도움.
- **장소 상세**: 사진, 설명, 시간, 가는 길, 주문하기 또는 예약하기.
- **도움**: 어느 화면에서든 오른쪽 위. 열면 지금 보던 주문이나 장소를 붙일지 묻는다.
- **키오스크**: 첫 화면에 "여기서 주문"과 "휴대전화로 주문" QR을 나란히 둔다. 손님 화면마다 작은 매장 QR을 둔다. 준비 완료 안내판은 손님용 화면 위에 번호 띠(최대 4개)로 두고 쉴 때는 전체로 보인다. 번호만 보이고 접수와 만드는 중을 나누며, 세 번째 기기는 첫 단계에서 등록하지 않는다.

화면 시안은 구현 전에 그려 승인을 받는다.

### 카페답게의 순서

정할 것은 모두 정했다(7장). 앞의 것이 시험을 통과하면 다음으로 간다. 화면은 만들기 전에 시안을 승인받는다.

1. 옵션: 묶음을 받아 조합 줄을 만드는 게시, 600줄, 쪽 나눠 읽기. 이어서 운영 웹의 묶음 편집과 키오스크·휴대전화의 묶음 고르기. 값에는 더하는 금액(0 이상)과 더해지는 알레르기 성분을 적는다. 성분을 적지 않은 상품에는 값의 성분도 적지 못한다. 세금이 있는 상품에는 2번이 끝날 때까지 더하는 금액을 받지 않는다. 앱의 읽기 한도(쪽 32KB, 근거리 응답 2,023바이트)를 넘는 메뉴는 게시할 때 거절한다. 손님 화면은 아무 값도 미리 고르지 않는다(2026-11-26 시안 승인). 값의 코드는 운영 웹이 만들고 다시 쓰지 않으며, 주방과 이의 화면은 코드 대신 값의 이름(`optionLabel`)을 받는다. 종단 시험에 옵션 상품을 고르는 흐름을 더해 토큰마다 18개가 됐다(`test/order-flow/**`, `scripts/test_order_flow.py`). 기존 시험 파일에는 상거래 시험 `menu_options_test.go`에 이름 확인을 더한 것 말고 바꾼 것이 없다.
2. 품목별 세금 자료와 원화 가격 화면. 2026-11-26 시안 승인. 운영 웹에서 상품마다 세금 종류(부가세 10% 포함, 면세)와 환급 대상 표시를 고른다. 세금 종류를 고른 가격은 세금 포함이고 그 위에 세금 금액을 더하지 않는다(서버가 거절한다). 종류가 없는 옛 상품은 지금처럼 더한 금액으로 받는다. 세금은 품목 줄마다 공급가액(가격의 10/11)을 원(달러는 센트) 단위에서 반올림하고 나머지를 세금으로 계산하고(같은 날 다시 정한 결정 B: 국세청 예규 간세1235-4254의 반올림 권장과 서면3팀-254의 "세액은 공급가액의 10%"에 맞춤. 처음에는 국고금관리법 제47조 제2항을 근거로 버림으로 정했다가 바꿨다), 장바구니·키오스크 결제 화면·휴대전화 영수증에 보인다. 환급은 금액에서 빼지 않는다. 환급 대상 표시는 같은 날 결정(B)대로 관할 세무서장이 지정한 외국인관광객 면세판매장만 쓴다. 운영 웹의 "외국인 세금 환급"에 지정 번호, 지정받은 날, 환급 창구 운영사를 적고 지정서를 확인했다고 체크해야 저장되며, 이 시스템은 국세청에 지정 여부를 묻지 않으므로 손님 화면에 "매장이 적은 번호"라고 밝힌다. 부가세 10%이고 "포장해 가져가는 물품"인 상품만 표시할 수 있고(서버가 게시 때 지정 번호와 함께 검사한다), 매장에서 먹고 마시는 것과 면세 상품은 대상이 아니다. 키오스크 장바구니는 대상 물품 합계와 15,000원 이상인지, 여권과 출국 때 반출 조건을 보이고, 휴대전화 영수증은 대상 줄과 지정 번호를 남긴다. 원화 결제에서만 보인다. 지정 번호를 지우면 손님 화면의 환급 안내가 모두 꺼진다. 근거: 조세특례제한법 제107조, 외국인관광객 등에 대한 부가가치세 및 개별소비세 특례규정 제3조~제5조, 같은 시행규칙 제2조. 휴대전화는 결제할 때 품목 줄을 주문 기록에 남겨 영수증에 쓴다. 세금이 있는 상품의 옵션 금액 제한은 세금 종류를 고른 상품에서 풀린다.
3. 품절, 바쁨, 멈춤, 휴무일과 한 번에 바꾸기(운영 웹). 바쁨의 알린 시간. 2026-11-26 시안 승인. 운영 웹의 "주문 받기"에서 받는 중, 바쁨(5~60분, 5분 단위), 멈춤(다시 받을 시각은 안내일 뿐 저절로 풀리지 않음)을 고르고 한 번 더 확인한 뒤 바꾼다. 휴무일은 오늘부터 1년 안의 날짜를 더하고 빼며 그날은 매장 시간대로 하루 내내 새 주문을 받지 않는다. 품절은 게시한 메뉴의 상품을 여러 개 골라 한 번에 바꾸고 모든 옵션 조합에 걸리며 남은 수량과 따로 둔다. 바꾼 사람과 시각은 지우거나 고칠 수 없는 기록에 남고 운영 웹은 최근 20건을 보인다. 운영자 이름 자료가 없어 바꾼 사람은 "나" 또는 운영자 참조 끝 네 자리로 보인다. 서버는 멈춤과 휴무일을 영업시간 검사(`catalog_is_open`)에 더해 새 주문과 견적을 거절하고(`CATALOG_CHANGED`), 품절 상품의 주문 줄은 재고 없음(`OUT_OF_STOCK`)으로 거절한다. 손님 앱은 메뉴 첫 쪽과 함께 상태를 받고, 품절 상품은 남은 수 0으로 받아 메뉴 응답 크기가 늘지 않는다. 키오스크는 새 손님마다, 휴대전화는 메뉴를 읽을 때마다 상태를 다시 읽는다. 결제하려는데 멈춤이 되면 키오스크는 장바구니를 비우고, 휴대전화는 장바구니를 그대로 두며 둘 다 돈이 나가지 않았다고 알린다. 손님 화면에는 아직 시한 취소 문구를 보이지 않는다(다음 단계). 모션(같은 날 승인 A): 담기(장바구니 수 280ms, 새 줄 200ms), 주문번호(가려진 칸 안에서 420ms), 결제 진행 단계(선 300ms), 결제 완료(표시 360ms, 테두리 500ms)를 한 번만 움직이고 되풀이하지 않으며 움직임 줄이기 설정을 따른다. 안내판의 새 번호 강조는 5번 안내판과 함께 만든다.
4. 사진: 올리기, 다시 만들기, 게시, 키오스크가 받기. 사진을 2·3번보다 먼저 만들었다(2026-11-26 결정 A). 휴대전화 앱에도 보인다(같은 날 결정 B). 서버는 상세용 800×600(150KB까지)과 목록용 320×240(18,000바이트까지) JPEG를 만들고 원본은 남기지 않는다. 앱은 SHA-256 이름으로 `catalog.photo`를 18,000바이트씩 나눠 받는다(앱 응답 한도 32KB). 목록에는 작은 사진만 받고, 받은 사진은 이름으로 다시 받지 않는다. 휴대전화는 서버에 닿을 때만 받고, 닿지 못하면 이름만 보인다.
5. 안내판: 손님 태블릿 자격으로 번호와 상태만 읽는 함수와 화면. 금액, 품목, 주문 참조는 읽지 못하게 한다. 2026-11-26 구현: 서버 함수 `ready_board`는 매장 태블릿 자격(`terminal`)에만 오늘 번호를 준비됨(최근 것 먼저), 만드는 중, 접수로 나눠 각 40개까지 주고, 전달·준비 불가·환불된 번호는 뺀다. 요청 종류 `C3/board.read`를 더했다. 키오스크는 아무도 주문하지 않을 때 전체 안내판(준비된 번호 4개는 크게, 나머지는 한 줄)을 보이고, 주문하는 동안에는 위쪽에 번호 띠(최대 4개)를 둔다. 5초마다 읽고, 읽지 못하면 마지막 판과 "연결이 끊겼습니다 · 마지막 확인 시각"을 보인다. 새로 준비된 번호는 칸 안에서 올라오고 3초 동안 강조되며 화면 읽기 프로그램이 한 번 읽는다. 소리는 내지 않는다. 시안의 "자동 주방으로 운영 중" 표시와 매장 QR은 6번(자동 주방)과 함께 넣는다.
6. 자동 주방과 운영 취소, 시험 매장 표시. 2026-11-26 구현(마이그레이션 121): 시험 매장 표시와 자동 주방 켜기는 플랫폼이 배포할 때 `ledger.branch_test_store`에 적고, 운영자 경로로는 바꾸지 않는다. 자동 주방은 계획의 "별도 프로세스" 대신 opsd의 2초 주기 작업으로 돌고, 시험 체인(8283)인 지점만 움직인다. 기록에는 지점마다 정한 자동 주방 식별자가 남아 사람의 기록과 구별된다. 한 번에 한 단계씩만 넘겨 꺼졌다 켜져도 건너뛰지 않고, 같은 사이에 사람이 바꾼 단계가 이긴다. 시간은 접수 뒤 30초에 시작, 알린 시간(바쁨이면 그 분, 아니면 매장 설정 5분) 뒤 준비 완료, 준비 뒤 2분에 전달이다. "준비할 수 없음"은 자동으로 기록하지 않는다. 운영 웹의 "주문 취소"에서 오늘 주문을 번호로 찾아, 전달 기록 전이면 한 번 더 확인한 뒤 "준비할 수 없음"으로 취소한다. 찾기와 취소에는 주방 관리 권한(`pickup_manage`)이 있어야 하고, 같은 요청을 다시 보내도 한 번만 반영되며, 취소한 사람과 환불 확인 상태(확인 중, 환불됨, 보내지 못함)를 보인다. 돈은 기존 예치 취소 경로로 손님의 보드 계정에 돌아간다. 운영 웹, 키오스크 메뉴와 안내판, 휴대전화 메뉴에 "시험 매장 · 자동 주방"을 적는다. 안내판의 매장 QR은 넣지 않았다(첫 화면의 "매장 입구 QR 보기"가 있다).
7. 손님 30건과 중단 지점 5개의 종단 시험, 에뮬레이터 확인. 2026-11-26 구현(`test/order-flow/**`, `scripts/test_order_flow.py`): 흐름이 토큰마다 20개가 됐다. "thirty customers"는 매장 취소 3건, 사람이 주방을 돌린 25건(5건마다 안내판 번호 = 주방의 준비 완료 번호를 대조), 시험 매장 자동 주방이 끝까지 돌린 2건을 받기까지 보내고, 매장 수입이 27건 값과 같은지 본다. "five interruptions"는 환불 전송 뒤, 잠금 전송 뒤, 포함 뒤 기록 전(보낸 직후 작업자가 죽고 서버가 8초 멈춘 동안 블록이 쌓임), 주방 시작 뒤(서버 8초 멈춤), 전달 기록 뒤(전달 호출 직후 작업자가 죽음)에서 각각 멈췄다가 새 작업자로 이어 가며, 주문마다 잠금이 한 번인지와 작업자가 죽은 호출의 순서를 본다. 작업자가 죽는 것은 체인 연결을 감싸 거래가 체인에 닿은 뒤 오류를 돌려주는 방식이고, 다시 켜진 작업자는 데이터베이스에 남은 것만 안다. 실행 끝에 주문마다 잠금 = 지급 + 환불 + 보관을 대조한다(전체 합계 대조는 전부터 있었다). 이 세계의 보드 하나가 손님 전부를 대신하므로 시험 보드의 하루 한도를 1,000,000원어치에서 20,000,000원어치로 올렸다(시험 보드 빌드 설정만, 제품 펌웨어는 그대로). 흐름이 길어져 세계의 수명과 실행 제한을 20분으로 늘렸다. 옵션 합계 표 일치는 기존 "options picked on the phone" 흐름이 본다.

시한 취소(15분)와 손님 취소는 다음 단계인 줄 서지 않는 주문에서 만든다.

### 줄 서지 않는 주문 전에 정할 것

- 여러 매장 허가 형식과 벡터(펌웨어가 지금 매장 하나만 본다), 공개 종단의 주소와 인증, 7일 접근권의 표와 철회, 설치된 보드 목록, 시험 보드의 실제 신원 서명.
- 시한 취소의 저장 값, 매장의 동시 주문 한도, 재고를 잡는 시간.
- 위치 안내문 새 판과 다시 받는 동의.

2026-11-26 정함(사용자 결정, 원문은 결정 기록에 둠):
1. **여러 매장 허가:** 이번 단계는 매장 한 곳으로 한다. 보드 허가 형식과 펌웨어는 바꾸지 않는다. 여러 매장은 시험 매장이 둘 이상이 될 때 다시 정한다.
2. **손님이 들어오는 길:** 매장은 손님의 휴대전화나 보드를 등록하거나 관리하지 않는다. 매장이 보는 것은 주문번호, 주문 내용, 결제 확정뿐이다. 손님 확인은 위 "손님은 결제한 보드로 확인한다"를 따른다. 서버의 새 값에 보드가 계정 증명으로 서명하고, 서버가 주소를 결제 주소와 대조한다. 결제에 쓴 서명을 다시 받지 않는다. 인증서 발급, 7일 접근권, 설치된 보드 목록은 만들지 않는다. 손님 요청은 클라이언트 인증서 없이 받는 별도 입구로 받고 요청 속도를 제한한다. 결제 전 재고는 계정 증명의 주소마다 한 건만 잡고, 그 주소의 잔액이 장바구니 금액보다 적으면 잡지 않는다. 결제 뒤 상태 조회, 준비 알림, 취소, 받았어요, 이의는 한 번 계정 증명을 받은 뒤 그 주문이 끝날 때까지 그 주문만 다루는 세션으로 한다(2026-11-27 결정 A). 수령은 세션으로 하지 않고 매번 증명한다. 매장 QR은 주문할 매장을 고르는 데만 쓴다. 2026-11-26에 정한 "등록서 길만"을 2026-11-27에 바꿨다.
3. **자동 취소 시한:** 결제가 확정될 때 주문마다 절대 시한 하나를 저장한다(평소 15분, 바쁨이면 알린 시간 + 10분, 60분 상한). 서버가 꺼져 있었으면 다시 켜질 때 한 번만 미루고, 결제부터 60분을 넘지 않는다. 계약의 전달 기한이 마지막 안전 장치다.
4. **동시 주문 한도:** 결제됐지만 아직 시작하지 않은 주문을 센다. 시작값은 10건이고 매장 설정(1~50)이며 운영 웹에서 바꾼다. 닿으면 새 주문은 결제 전에 거절한다.
5. **결제 전 재고:** 견적 수명 + 30초 동안 잡는다(지금 설정으로 최대 150초). 계정마다 한 건이라 새로 잡으면 이전 미결제 예약을 푼다.
6. **위치와 매장 고르기:** 이번 단계의 매장 주문은 위치를 쓰지 않는다. 매장은 앱의 매장 목록(이름 검색, 최근 매장)에서 골라 가는 길에 미리 주문한다. 매장 QR은 지점 번호만 담는 "매장 바로가기"로, 찍으면 그 매장의 매장 화면이 열린다. 2026-11-26에 정한 "매장 QR로만"을 2026-11-27에 바꿨다.
7. **매장 화면:** 모든 매장은 한 화면에서 매장 소개, 매장의 주소와 위치, 영업시간과 운영 정보를 보이고, 메뉴 주문과 예약 같은 기능을 연다(2026-11-27 사용자 요구, 참고: 네이버 지도의 장소 화면). 매장 목록과 매장 바로가기는 모두 이 화면으로 들어온다. 매장의 위치는 매장 자료이며 손님의 위치는 쓰지 않는다. 화면에는 이름과 종류, 영업 상태, 매장이 쓴 소개, 사진, 주소(복사와 지도 앱으로 열기), 요일별 영업시간, 전화, 편의·주차·결제수단, 메뉴와 주문, 운영자 연락처를 둔다. 리뷰·평점, 배송 상품, 주변 장소는 두지 않는다. 지도 앱으로 열 때는 매장 주소가 바깥 앱으로 간다고 알린다. 예약 단추는 매장이 예약을 켰을 때만 보이고, 예약 기능은 "여행지 찾기와 예약" 단계에서 만든다(2026-11-27 결정 A). 이번 단계에는 예약을 켠 매장이 없다. 앱의 위치 안내문은 그대로 둔다. 지도에서 고르는 숙소·관광지 예약은 예약 결제로 하고 거리 검사와 매장 QR 없이 진행한다(예약 결제 기능은 "여행지 찾기와 예약" 단계에서 만든다).
8. **수령 확인:** 준비가 끝나면 손님이 앱에서 받으러 왔다고 알리고, 보드가 서버의 새 값에 계정 증명으로 서명한다. 서버는 결제 주소와 맞으면 무작위 일회용 값만 담은 수령 QR을 준다. 수명은 60초 안팎이고 지나면 새로 받는다. 직원이 브라우저로 운영 웹의 주문 확인에서 그 주문을 열고 찍으면, 서버가 매장, 그리고 연 주문과 QR의 주문이 같은지를 대조하고 "전달됨"을 기록한다(2026-11-27). 다른 주문의 QR은 받지 않는다. 서버에는 결제한 보드의 서명, 찍은 매장 기기, 시각이 남는다. 지급은 지금 규칙을 따른다. 손님이 받았어요를 누르거나 확인 기간이 끝나면 매장이 받고, 못 받았다는 이의는 이 기록으로 판정한다(2026-11-27 결정 A). 찍는 순간 지급하는 방식은 쓰지 않는다. 점검과 결정의 자세한 내용은 [유즈케이스 점검과 결정](use-case-review.md)에 있다.

각 단계에는 전환, 되돌리기, 감시, 기록 보관을 함께 적는다. 각 단계는 더미 보드를 붙인 에뮬레이터에서 먼저 확인하고, 공개 시험망 배포와 보드 기록은 따로 승인을 받는다. 이 컴퓨터에는 태블릿과 실제 보드가 없어 키오스크는 시험대에서만 확인한다.
