# 3인 작업 분류와 12주 통합 계획

> 현재 상태: 사용자가 작업 목록 구체화를 먼저 요청하여 개인별 배정·공수 산정·주차별 확정은 보류했다. 아래는 이전 제안 기록이며, [상세 작업 목록](work-breakdown-plan.md)을 정리한 뒤 다시 검토한다.

작성: 2026-09-18. 사용자 확정: **15개 목표는 모두 앱 연동까지 완료하며 참여자는 총 3명**이다. 기능 목록은 [12주 완료 범위 v3](twelve-week-completion-scope-v3.md)를 따른다. A/B/C는 사람의 이름이 아닌 역할 제안이며 개인별 역량·투입 시간은 아직 확인하지 않았다.

## 1. 역할 제안

| 역할 | 최종 책임 | 직접 맡을 구현 | 경계 |
|---|---|---|---|
| A — 기기·펌웨어·모바일 기기 연결 | 실제 NU 기기가 기능을 수행하고 앱이 제어할 수 있음 | HW wallet·키 보호·FOTA·패스키·마이크/녹음 전송·찾기·기기 스탬프, BLE/거리 측정, 모바일 기기 연결 모듈과 설정 화면 | Google/Apple 계정 서버와 MPC Cloud Wallet 서버 전체를 맡지 않음 |
| B — 앱·매장·여행·운영 서비스 | 사용자/사장님/운영자의 흐름이 실제 서비스와 연결됨 | 유저 앱 골격·소셜 로그인 연동, RN 키오스크, 가맹점/메뉴/주문/환불/매출·정산 업무 API, 백오피스, 위치/후기/발자취·AI 코스/챌린지, DApp 공통 화면 | 고객 키를 업무 서버에서 직접 보관·서명하지 않음. 기기 설정 화면은 A가 구현하여 유저 앱에 통합 |
| C — 온체인·지갑 서비스·Indexer | 지갑/계약 실행과 결과 조회가 테스트넷에서 일치함 | 토큰·EOA/스마트 계정·DeFi/FX/Perpetual/STO/DID/x402, DEX 실행 서비스, MPC Cloud Wallet 서명·복구 서비스 통합, Indexer·체인 어댑터 | 매장 매출 원장과 개인 여행 데이터는 B 책임. Cloud Wallet 로그인 연결은 B와 공동 구현 |

이 분류는 프론트/백엔드만 나누는 구조가 아니다. A는 기기 기능이 앱까지 도달하는 구간, B는 실제 사용 흐름과 업무 데이터, C는 지갑·체인 실행과 조회를 맡는다. B와 C의 범위가 넓으므로 공통 화면·SDK·기존 서비스 재사용이 필요하며, 아래 담당 범위를 작업별 추정 없이 균등한 업무량이라고 보지 않는다.

## 2. 15개 요구사항의 담당 매핑

|---|---|---|---|

| 2 | FOTA | A | B가 앱 업데이트 흐름·운영 배포 UI 연결. 업데이트/중단/복구 실기 기록 |

## 3. 서로 기다리지 않기 위한 연결 규칙

| 연결 구간 | 제공 책임 | 받는 책임 | 초기에 합의할 계약 |
|---|---|---|---|
| NU ↔ 유저/키오스크 앱 | A | B | 기기 식별·인증된 세션·명령/응답·진행/오류·취소·연결 복구, 실제 서명 내용과 표시의 일치 |
| 계정 ↔ Cloud Wallet | B: 사용자 식별 / C: 지갑 권한 | B·C | 로그인 계정과 지갑 주소 연결, 승인·복구 API, 기기 변경/탈퇴·중복 계정 정책 |
| 앱 ↔ 체인 거래 | C | A·B | 네트워크/토큰 식별, 서명 요청, 견적·가스 상한, 제출/미확정/실패·거래 식별 |
| Indexer ↔ 주문 원장 | C: 관측 / B: 원장 | B·C | 체인·토큰·주소·정수 금액·로그 식별·확정 상태, 중복/재구성·지연 처리 |
| DEX/계약 ↔ 앱 | C | B | 기능별 견적/실행/조회 API·ABI, 대표 입력, 상태·실패 사유·예상 화면 결과 |

모의 응답은 개발 중 인터페이스를 연결할 때 사용할 수 있으나, ‘앱 연동 완료’ 증거는 실제 대상 서비스/테스트넷/기기에서 얻는다. 버전이 바뀌면 담당자끼리 예제 요청·응답과 계약 테스트를 함께 갱신한다.

## 5. 업무량과 병목 관리

- 3명이 12주 전일 참여할 때의 상한은 **36인주**다. 실제 근무시간을 확인하지 않았으므로 가용량으로 확정하지 않는다. 마지막 2주를 세 명 모두 통합·수정·인수에 배정하면 그 구간은 6인주이며 신규 기능 작업과 이중 계산하지 않는다.
- A의 핵심 병목은 HW 서명 보호·FOTA·표준 패스키·오디오를 한 보드에서 함께 동작시키는 부분이다. 필요한 부품·보드 메모리·대상 폰/OS를 개발 초기에 확인한다.
- B의 핵심 병목은 유저/매장/운영 앱과 여행/DApp 화면의 폭이다. 앱 공통 컴포넌트·권한·조회 상태를 재사용하고 A가 기기 설정 화면을 맡아 나눈다. C는 API/SDK와 기능별 실행 예제를 제공한다.
- C의 핵심 병목은 MPC와 Perpetual/STO/DID/x402의 신규·미완성 영역이다. 검증된 기존 서비스/라이브러리의 재사용 여부를 먼저 결정하고, 해당 영역을 모두 새로 구현하는 비용을 감추지 않는다.
- 매주 각자가 완료 증거, 다음 주 의존성, 남은 작업 추정을 갱신한다. 역할 간 이동은 실제 역량과 남은 용량을 보고 결정하며 다른 사람에게 검증되지 않은 암호·펌웨어 작업을 이름만 넘기지 않는다.

현재 상태에서 3명이라는 사실만으로 12주 완수를 확약할 수 없다. **첫 2주 안에 기능별 작업 추정·도입 자산·위험 경로의 결과로 일정 실행 가능성을 재판정**하는 것을 제안한다. 초과하면 재사용 확대·인력/지원·일정 조정을 제시하며, 사용자가 확정한 범위와 지원 깊이를 자동 축소하지 않는다.

## 6. 완료 판정과 검토 책임

각 기능은 다음을 모두 갖춰야 완료로 기록한다.

1. 대상 앱에서 사용자가 기능을 시작하고 결과를 확인할 수 있다.
2. 해당 기능이 의존하는 실제 기기·서비스·StableNet 테스트넷에 연결된다.
3. 정상 동작 외에 관련 실패·권한·중복/재시도·복구 시나리오를 확인한다.
4. 빌드/앱/펌웨어/계약/API 버전과 재현 절차, 해당 증거를 남긴다.
5. 주담당 외 한 명이 확인한다. A 작업은 B/C 중 관련자가, B의 결제·권한은 C가, C의 서명·키 경계는 A가, C의 화면/조회 흐름은 B가 검토한다.

이는 내부 교차 검토이며 외부 보안 감사·표준 인증을 대신한다는 의미가 아니다. 고객 소셜 로그인만 구현하고 MPC 서명/복구를 생략하거나, 계약만 배포하고 앱 동작을 생략한 상태는 완료가 아니다.

## 7. 다음에 정할 내용

1. 세 사람의 주력 분야와 주당 투입 시간에 맞춰 A/B/C를 실제 인원에 배정한다.
