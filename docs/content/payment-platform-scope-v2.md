# 지갑·매장 운영 플랫폼 — 요구사항과 확장 후보

> 2026-09-18 범위 갱신: [12주 완료 범위 v3](twelve-week-completion-scope-v3.md)가 최신 기준이다. 아래 기존 검토에서 패스키·녹음·스마트 계정 등을 후보/후속으로 둔 부분은 새 범위를 따른다. 초기 EOA 개발 순서와 고객 가스 부담은 유지하며, 새 Cloud Wallet의 MPC는 별도로 설계한다.

갱신: 2026-09-17. 진행 중인 인터뷰의 작업 문서이며, 최종 Seed 또는 구현 완료 보고서가 아니다. 사용자 확정 사항과 설계 제안을 구분한다. 공개 원고와 달리 내부 요구사항 정리용이다.

## 1. 사용자 확정 사항

- 첫 시연은 사용자 지정 [StableNet RPC](https://api.test.stablenet.network/)와 [탐색기](https://explorer.stablenet.network/)를 사용한다. 조회 결과 체인 ID는 8283이다. 초기 가스는 고객의 네이티브 토큰으로 지불한다. [확인 기록](stablenet-testnet-baseline.md)

- NU-54V-DK를 이용한 휴대형 지갑. 화면·버튼·IMU·BLE와 키오스크 근접 조건을 활용한다.
- 한국의 협력 카페가 있으며, 주 대상은 한국 방문 외국인 관광객이고 일부 한국인도 포함한다.
- 여행 중 지갑을 대여하고 반납한다. 고객의 기존 보유 자산을 사용한다.
- 첫 지원 자산은 USDC. 다른 스테이블코인은 이후 확장한다. 카페는 스테이블코인을 직접 수령하며 첫 버전의 원화 자동 환전·정산은 제외한다.
- 결제 네트워크 수수료는 **초기 고객 부담 → 후속 운영자 후원** 순서로 구현한다. 초기 가스는 사용자가 지정한 StableNet 체인의 네이티브 토큰으로 납부한다. 후원 한도/시점은 아직 미정이다. 환불 수수료 정책까지 확정한 답변은 아니다.
- 모바일 앱에서 mnemonic/private key 가져오기와 신규 지갑 생성을 선택한다. 가져오기 전송은 인증된 키 교환과 암호화로 보호한다. 실행영역·접근권한 분리 방향에 동의했다.
- 고객 결제 서명은 보드에서 수행하는 방향. 매 결제에 고객 폰의 공동 서명을 요구하지 않는다. 이 기존 결정은 하드웨어 지갑에 관한 것이다. 새 12주 범위에는 별도의 MPC Cloud Wallet이 포함된다.
- 지갑은 **초기 일반 지갑(EOA) → 후속 스마트 계정** 순서로 구현한다. 후속 주소 유지·자산 이동·권한 전환 방식은 아직 미정이다.
- 모바일 앱은 기기 설정 전용으로 끝내지 않는다. 지갑을 활용할 다양한 기능을 제공한다. 구체적인 추가 기능은 검토 중이다.
- 태블릿 키오스크는 React Native 앱으로 개발하고 플랫폼별 빌드를 지원한다. 대상 OS 및 기종은 미정이다.
- 키오스크는 업체가 사용하는 앱이다. 가게 ID로 로그인하고 메뉴·매출·정산을 관리할 수 있어야 한다.
- 모바일 앱에서도 사장님 ID로 로그인하면 사장님 지갑의 자산 등을 확인할 수 있어야 한다.
- 서비스 운영용 백오피스를 포함한다.
- [poc-platform](https://github.com/0xmhha/poc-platform)의 웹 DApp·지갑·SDK·Bundler·Paymaster 서버도 기존 자산으로 활용할 수 있다. [검토 및 재사용 계획](poc-platform-reuse-plan.md). 실제 카페 업무와 NU 연결은 추가 구현/통합 대상이다. 초기 일반 지갑(EOA), 후속 스마트 계정 적용으로 확정했다. 운영자 후원도 후속 단계다.
- DApp 온체인 기능은 기존 [stable-poc-contract](https://github.com/0xmhha/stable-poc-contract)를 재사용 가능한 자산으로 포함한다. 스마트 계정·운영자 후원은 후속 단계로 둔다. 모듈 선택·마이그레이션 방식은 아직 미정이다. [코드 검토와 적용 조건](stable-contract-reuse-plan.md)
- 테스트넷 USDC 확보가 어려워 개발·시연용 더미 토큰 컨트랙트를 배포하여 사용한다. 실제 서비스의 첫 자산은 USDC라는 결정을 유지한다. 배포 체인은 StableNet 8283이며, 토큰 주소는 아직 미정이다.
- 처리 결과와 이벤트 조회에는 기존 [Indexer 백엔드](https://github.com/0xmhha/indexer-go)와 [웹 프론트엔드](https://github.com/0xmhha/indexer-frontend)를 활용한다. 저장소를 전달받았으며 소스 검토 결과와 연동 제안은 [별도 문서](indexer-integration-and-test-token.md)에 기록한다.
- 하드웨어에는 결제 외에 비대칭키와 Bluetooth 6.0을 활용하는 실용적이고 재미있는 기능을 추가로 검토한다.
- 카페 패스포트 방향에 사용자가 동의했다. 상세 보상·발급·사용 정책은 미정이다.
- 첫 테스트 휴대폰은 Galaxy S25 Ultra로 확정했다. 설치된 Android/One UI 버전은 아직 확인하지 않았다. 다른 OS 지원 범위를 철회한 결정은 아니다.
- NU-54V-DK와 측정 모듈용 Nordic nRF54L15 DK는 모두 보유한다고 답했다. 실제 기기를 이용한 검증은 개발 단계에서 진행하고 현재는 다음 설계로 넘어가도록 지시했다.
- 휴대·부착할 수 있는 디자인과 클립 형태를 원한다. 버튼 녹음 → BLE로 폰에 전송·저장 → 음성 텍스트 변환·AI 정리 기능을 추가 후보로 제시했다. 패스키 또는 근접 로그인 추가 인증의 가능성도 검토 요청했다. 후속 2026-09-18 결정에서 패스키·녹음기·찾기·스탬프를 12주 필수 범위에 포함했다. 상세 성능/호환 기준은 미정이다.

기존 문서의 12주 목표는 테스트넷 결제 시연이었다. 확대된 제품 범위에서 실제 자산 파일럿을 12주 필수로 포함할지는 아직 답변받지 않았다. 수수료는 초기 고객 부담, 운영자 후원은 후속으로 구현한다.

## 2. 앱과 운영 도구의 역할 — 설계 제안

| 구성 | 사용자 확정 범위 | 추가로 제안하는 화면·기능 |
|---|---|---|
| 지갑 모바일 앱 · 고객 | 설정 이상의 지갑 활용 기능 | 자산·송수신·결제 이력·영수증·쿠폰·기기 찾기·반납 준비 |
| 지갑 모바일 앱 · 사장님 | 사장님 계정 로그인 후 자산 조회 | 매장별 수취 내역·환불 상태·기간별 입금 요약. 출금·환불 실행 권한은 미정 |
| React Native 매장 앱 | 태블릿 주문·결제, 가게 로그인, 메뉴·매출·정산 관리 | 고객 주문 모드와 관리자 모드 분리, 품절 처리, 주문 처리, 일 마감, 거래 대사 |
| 운영자 백오피스 | 서비스 운영 도구 | 가맹점·단말·대여/반납·장애·Indexer 지연·대사 불일치 관리 |
| 컨트랙트 | 개발·시연용 USDC 대체 더미 토큰 | StableNet 8283에서 표준 ERC-20 기반 제안. 배포 주소·세부 사양 미정 |
| 기존 Indexer 연동 | 처리 결과·이벤트 조회 | 체인별 확정 상태, 누락 재조회, 중복 제거, 재구성 처리 여부 확인 |

매장 앱은 사장님이 로그인하여 가게를 선택하고 운영 설정 후 고객 주문 모드로 전환하는 흐름을 제안한다. 고객 화면에서 관리 화면으로 돌아갈 때 재인증한다. 직원별 권한이나 여러 매장은 확장 가능한 구조를 제안하되, 첫 버전 필수 기능으로 확정하지 않는다.

모바일 고객 앱도 React Native로 만들고 계정·조회·BLE 관련 코드를 공유하는 것은 후보이다. 사용자가 React Native를 명시적으로 확정한 대상은 태블릿 키오스크이다.

## 3. 같은 계정, 서로 다른 권한

제안 연결 구조는 `사용자 계정 → 매장 소속과 역할 → 연결된 지갑 주소`이다. 가게 ID는 매장을 식별하고, 실제 로그인 주체와 권한은 별도로 관리하도록 제안한다. 공유 비밀번호 하나를 모든 직원이 사용하는 구조를 전제로 하지 않는다.

- 로그인하면 권한이 있는 매장과 지갑의 조회 화면을 제공한다.
- 지갑 주소 연결 시 해당 지갑 소유 확인 절차를 둔다. 공개 주소만으로 가능한 잔액 조회와 사적인 주문·고객 정보 접근 권한을 구분한다.
- 로그인 성공이 개인키 전달이나 출금 권한 부여를 의미하지 않는다.
- 고객 주문용 태블릿에 사장님 지갑 개인키를 배포하지 않는 구조를 제안한다.
- 환불·출금 실행까지 앱에 포함할 경우, 사장님 지갑의 보관 위치·서명 장치·분실 복구·직원 권한을 따로 결정한다. 아직 사장님용 하드웨어 지갑이 확정된 것은 아니다.
- 서비스 로그인·쿠폰 등 부가 기능에는 결제 키와 별도의 역할별 키 및 승인 정책을 사용하는 방향을 제안한다. 동일 알고리즘을 쓸 수 있다는 이유로 결제 키를 모든 요청에 재사용하지 않는다.

## 4. 매출·정산·지갑 잔액의 의미 — 확인할 제안

현재 합의된 직접 수령 구조에서 ‘정산 관리’는 우선 주문과 USDC 수취 내역을 대조하는 기능으로 정의하는 것을 제안한다. 새로운 원화 환전 기능을 암묵적으로 추가하지 않는다.

| 표시 | 의미 |
|---|---|
| 주문 매출 | 주문 금액·할인·취소·환불을 근거로 계산한 판매 지표 |
| 결제 상태 | 요청, 제출, 확인 중, 확정, 실패 등 구분. 최종 상태는 선택 체인 정책에 맞게 결정 |
| USDC 수취·환불 | 실제 온체인 전송과 주문의 연결 |
| 차이 내역 | 미확인 결제·중복·금액 차이·연결되지 않은 전송·Indexer 지연 |
| 지갑 잔액 | 현재 보유량. 주문 외 입출금도 포함하므로 매출과 같지 않음 |

한 화면에 원화 메뉴 가격과 결제 당시 USDC 금액을 함께 남기는 것을 제안한다. 환율 출처·견적 유효기간·반올림·환불 환산 정책은 아직 미정이다. 이 정의가 세무상 매출·영수증 처리 요건을 충족한다고 판단한 것은 아니다.

Indexer는 조회를 돕지만 모든 이벤트가 최종 결제 완료를 뜻하지 않는다. 주문 서비스는 기대한 체인·토큰·수취 주소·금액·전송 상태를 확인하고 주문과 연결해야 한다. 주문 단위 추적 방식과 Indexer API는 구현 전 확인한다.

## 5. 지갑 앱의 기능 후보

고객에게는 `내 자산 / 결제·영수증 / 혜택 / 내 기기`를 기본 탐색 구조로 제안한다. 사장님은 같은 앱에서 매장 권한을 선택하여 자산과 매장 수취 내역을 볼 수 있다.

- 자산: USDC 잔액, 받기 주소/QR, 보내기 요청, 거래 상태. 자산 전송은 설정된 지갑의 실제 서명 권한으로 승인한다.
- 기록: 구매 메뉴·가게·결제액·영수증·환불 진행 상태. 여행 지출 요약을 결제 이력에서 만든다. 위치 상시 추적을 전제로 하지 않는다.
- 혜택: 디지털 스탬프, 쿠폰, 방문 기록. 카페 패스포트 방향은 사용자가 수용했으며 상세 기능은 구체화한다.
- 기기: 연결·배터리·화면 설정·찾기·대여 기간·반납 시 잔액 회수 지원. 배터리 표시 등은 하드웨어 측정 지원 필요.
- 사장님: 매장 자산, 입금과 주문 연결, 매출/수취 요약, 환불 상태. 조회를 넘는 자금 이동은 별도 결정한다.

## 6. 하드웨어를 반복 사용하게 하는 확장 후보

### A. 카페 패스포트 — 방향 수용, 상세 정책 미정

결제 확인 후 매장 스탬프를 모으고, 기기 화면에서는 작은 도장·캐릭터 반응을 보여준다. 앱에서 방문 기록과 쿠폰을 보고 재방문 시 기기로 사용을 승인한다. 여러 협력 매장 확대는 이후 단계이며 현재 다수 매장 확보를 가정하지 않는다.

매장 측에서 혜택을 발급하고 고객은 보유 자격을 증명한다. 한 번 사용한 쿠폰은 서버에서 중복 사용을 막는다. 근접만으로 구매·쿠폰 자격을 인정하지 않는다. 이 기능에 NFT 발행이나 별도 온체인 포인트가 반드시 필요한 것은 아니다. 대여 기기를 반납해도 기록과 혜택은 고객 계정 또는 연결된 지갑에 남도록 설계한다. 반납 시 기기 연동과 자격은 해제한다.

### B. 물리적 승인 키 — 비대칭키 활용성이 가장 직접적

자사 앱·백오피스 로그인 또는 중요한 변경 요청이 오면 기기에 서비스·행동 내용을 표시하고 버튼으로 승인한다. 예: ‘OO카페 관리자 로그인’, ‘정산 수취 주소 변경’. 사장님 출금·환불 승인으로의 확대는 사장님 지갑 정책을 결정한 뒤 검토한다.

서비스별·용도별 인증 키와 결제 키를 분리하고, 승인 내용을 요청에 묶으며 재사용을 막는 구조가 필요하다. 타사 사이트에 바로 쓰는 범용 FIDO2 보안키나 운영체제 로그인 장치로 완성된다는 뜻은 아니다. 표준 호환 기능은 별도 과제다. 로그인 승인 자체에 온체인 거래가 필수인 것은 아니다.

### C. 내 지갑 찾기

앱에서 찾기를 누르면 연결된 지갑이 LED 또는 추가 부저로 응답한다. 호환 기기에서는 Channel Sounding으로 ‘가까워짐/멀어짐’을 표시하는 확장을 검토한다. 소리·진동은 추가 부품과 전력 검토가 필요하다.

Bluetooth 6.0 표기만으로 폰·태블릿의 Channel Sounding 지원을 보장할 수 없다. 일반 BLE 연결/RSSI를 정확한 거리 측정으로 표현하지 않는다. 연결 끊김은 거리 외 원인도 있으므로 놓고 감 알림은 보조 알림이다. GPS 추적이나 Apple Find My/Google Find Hub 연동을 기본 제공하는 것으로 보지 않는다.

### D. 가까운 사람과 금액 요청하기

두 기기를 가까이 두고 상대 식별·금액 요청을 교환한 뒤, 송금자는 기기에서 수취인·금액을 확인하고 승인한다. 코인을 BLE로 직접 이동시키는 구조가 아니라, BLE는 요청 전달과 상대 확인을 돕고 실제 이체는 체인에 제출한다. 인터넷이 없는 상태에서 결제가 확정되는 기능으로 제안하지 않는다. 별도 P2P 사용자 흐름이 생기므로 우선순위는 후속으로 제안한다.

## 7. Bluetooth 6.0과 React Native의 검증 조건

조사일 기준 공식 자료에서 nRF54L15는 Channel Sounding을 지원한다. 이것은 NU-54V-DK의 특정 SDK·안테나·보드 설정에서 거리 성능과 보호 서명을 동시에 검증했다는 의미는 아니다.

- Channel Sounding은 상호 호환되는 두 장치와 지원 소프트웨어가 필요하다. 결제용 근접 조건은 사용자 승인·인증을 보완하며 단독 승인 수단으로 삼지 않는다.
- Android 16의 Ranging API는 장치별 지원 기술·가용성을 확인하도록 한다. 현재 문서는 서드파티 앱의 백그라운드 ranging을 지원 UWB에 한정하고 있어, Bluetooth Channel Sounding 상시 백그라운드 알림을 보장하지 않는다.
- 키오스크 태블릿이 미지원이면 키오스크 측 대응 보드/거리 측정 장치를 연결하는 대안을 검증할 수 있다. 이는 추가 하드웨어·연결 방식 검증을 수반하는 대안이며 확정 부품이 아니다.
- React Native는 공통 화면·업무 로직과 플랫폼 네이티브 코드를 연결할 수 있다. 일반 BLE와 정밀 거리 측정은 지원 API가 다를 수 있으며, Android/iOS 빌드가 된다는 사실만으로 같은 BLE 기능이 동작하는 것은 아니다. iOS 지원 경로는 미검증이다.
- 거리 이탈 시 승인 대기 요청을 중단할 수 있으나, 이미 서명·제출된 거래를 BLE 해제로 취소할 수 있다고 표현하지 않는다.

## 8. 개발 순서 제안 및 미정 항목

네 기존 저장소를 반영한 최신 작업 순서와 수용 기준은 [통합 작업 계획](payment-integration-workplan.md)에 있다. 먼저 조회 API 연결을 맞추고, 소프트웨어 주문·대사와 개발 단계의 보드 검증을 병행한다. 아래 순서는 상위 단계의 개요로 유지한다.

1. 보드 서명·보호영역·BLE/거리 측정과 대상 태블릿 호환성을 먼저 검증한다. 모바일 자산 조회와 매장 계정·메뉴·주문 골격도 함께 정의한다.
2. 테스트넷 주문→기기 승인→전송→Indexer 확인→매장 매출/수취 표시 흐름을 연결한다. 대여 설정·잔액 회수·반납을 검증한다.
3. 결제 내역/영수증과 사용자가 수용한 카페 패스포트를 구체화한다. 추가로 요청한 근접 인증과 음성 기록은 별도 기술 검증 후 완료 범위를 정한다.
4. 실제 자산 파일럿은 완료 기준과 법률·보안·운영 검증 조건을 정한 후 진행 여부를 판단한다.

이 순서는 작업 제안이며 인력·기존 구현 자산을 확인하지 않았으므로 전체 범위를 12주 내 완료할 수 있다는 일정 보장이 아니다.

미정: 추가 인증·음성 기록의 구현 범위와 우선순위, 사장님 앱의 조회/자금 이동 범위, 체인의 확정 정책·가스 확보 경로·후속 후원 정책, 정산의 최종 의미, 환불 정책, 모바일/태블릿 OS, Indexer 배포환경·연동 검증, 더미 토큰 세부 사양, 실자산 파일럿 필수 여부, 검증 기준과 담당자. Indexer 저장소와 더미 토큰의 개발·시연 목적은 확인했다. 최신 요구사항은 기존 인터뷰의 확장 내용이며 완료기준 질문에 대한 답으로 간주하지 않는다.

## 9. 클립형 지갑의 근접 인증·음성 기록 확장 검토

아래는 2026-09-17 사용자 제안에 대한 문헌 기반 타당성 검토다. 실제 보드·폰 테스트는 아직 수행하지 않았다. 제품 기능 전체를 12주 내 제공하기로 확정한 것이 아니다.

### 9.1 패스키와 근접 추가 인증

외장 FIDO2 인증기로 개발하여 기기에 종속된 패스키를 보관하는 방향은 가능성이 있다. 그러나 BLE 연결과 코인 서명 기능만으로 패스키가 되는 것은 아니다. CTAP2, 서비스별 자격증명, RP ID에 결합된 서명, 필요한 사용자 검증, 안전한 초기화·등록·삭제 절차와 OS/브라우저 호환성 검증이 필요하다. 버튼 누르기는 사용자 존재 확인이고 PIN 등 사용자 검증과는 다르다.

외장 키의 CTAP BLE 전송과, 휴대폰 QR 로그인에서 사용하는 hybrid 전송은 별도 경로다. FIDO의 hybrid는 BLE로 근접성을 확인하지만 이것이 정밀 Channel Sounding 지원이라는 뜻은 아니다. Microsoft Entra의 공식 호환표에는 BLE 보안키가 macOS/iOS/Android/ChromeOS에서 지원되지 않는다고 명시되어 있다. 이는 해당 제품의 호환표이며 모든 서비스에 대한 보편적인 OS 지원 판정으로 확대하지 않는다.

NU 보드의 USB 단자가 있다는 이유만으로 애플리케이션에서 USB FIDO 키를 구현할 수 있다고 가정하지 않는다. 디버거 연결과 애플리케이션 USB 장치 기능을 구분해야 한다. USB 또는 NFC 경로는 실제 보드 인터페이스와 SDK를 확인한 뒤 별도 결정한다.

근접 인증은 우선 자사 매장 앱·백오피스에서 검증하는 것을 제안한다.

`실제 로그인 클라이언트/등록된 매장 단말 ↔ 지갑 근접 확인 → 로그인 세션에 연결된 요청 표시 → 사용자의 기기 승인 → 서버 검증`

- 지갑과 사용자 폰이 가깝다는 사실만으로 먼 곳의 공격자 PC에서 시작한 로그인을 막을 수는 없다. 측정 상대를 실제 로그인하는 장치와 연결해야 한다.
- 일반 BLE 연결/RSSI 대신 Channel Sounding을 사용하더라도 측정 상대 인증, 로그인 세션 연결, 결과 신뢰성과 재사용 방지가 필요하다.
- 자사 서비스에서 근접·기기 승인을 필수로 검증하면 비밀번호만 탈취한 원격 공격자의 새 로그인을 막는 조건을 만들 수 있다. 실제 보안성은 구현과 검증에 달려 있다.
- 가까운 PC가 원격 조종되거나 감염된 경우, 이미 발급된 로그인 세션을 탈취한 경우, 기기가 도난당한 경우까지 거리가 해결하지 않는다. 로그인/중요 행동의 내용 확인과 별도의 사용자 검증·세션 정책이 필요하다.
- ‘세 번째 확인 단계’는 가능하지만, 거리를 독립된 인증 요소로 단정하여 ‘3요소 인증’이라고 홍보하지 않는다.
- 기존 제3자 서비스에 우리만의 거리 확인 단계를 임의로 추가할 수는 없다. 서비스/IdP 통합 또는 지원 인증기 내부 정책이 필요하고, 후자의 경우에도 실제 클라이언트와 측정 상대를 연결하는 구현·호환성 검증이 남는다.
- 자사 승인 기능과 범용 FIDO2 기능을 구분하여 개발·표시한다. 코인 결제 키와 서비스 인증 키를 분리한다.
- 대여 기기에 장기 로그인 자격증명을 등록한다면 반납 전 대체 로그인 수단 확보, 서비스 측 기기 등록 해제, 기기 초기화를 함께 설계해야 한다. 초기화만으로 다른 키 사본이나 이미 발급된 세션이 무효화되지는 않는다.

### 9.2 버튼 음성 기록 → 모바일 저장 → 텍스트·AI 정리

제안 흐름:

`외부 디지털 마이크 → NU-54V-DK의 짧은 RAM 버퍼 → 암호화된 BLE 데이터 전송 → 폰의 지속 저장 → 음성 텍스트 변환 → 요약·결정사항·할 일`

nRF54L15의 PDM/I2S 인터페이스는 공식 사양에 존재한다. 외부 마이크, NU 보드의 노출 핀과 전압·전원, 화면·IMU와의 핀/메모리 공유는 확인해야 한다. 내장 마이크나 배터리가 있다고 전제하지 않는다.

예시로 16kHz·16비트·모노 PCM은 순수 음성 데이터만 256kbps, 초당 32,000바이트, 1시간 약 115.2MB다. 100ms 버퍼는 3,200바이트, 500ms는 16,000바이트다. 이는 샘플 포맷에 따른 계산이며 달성한 전송 성능이 아니다. 무선 오버헤드와 암호화·재전송 비용은 별도다.

기기에 긴 파일을 저장하지 않는 방향은 가능하나, RAM 버퍼까지 없앨 수는 없다. 압축 코덱 적용 여부는 음질·CPU·RAM·전송량을 측정한 뒤 고른다. 첫 검증은 일반 BLE 데이터 스트림과 전용 수신 앱으로 계획할 수 있다. 이를 스마트폰 전체 앱에서 쓰는 표준 Bluetooth 마이크 또는 LE Audio 호환 제품으로 표현하지 않는다.

필요한 사용자 흐름을 다음과 같이 제안한다.

- 폰이 수신·저장 준비를 마쳤음을 확인한 후 녹음 시작을 표시한다. 녹음용 물리 버튼과 녹음 표시등을 둔다.
- 폰에서는 수신하는 동안 파일을 점진적으로 저장한다. 앱 메모리에 전체 회의를 모았다가 마지막에 저장하지 않는다.
- 짧은 지연은 버퍼로 흡수하고, 복구되지 않은 누락은 시간 구간으로 표시한다. 버퍼를 넘는 연결 중단은 알림과 함께 녹음을 중단하는 안을 제안한다. 저장하지 않은 음성을 나중에 복구할 수 있다고 약속하지 않는다.
- 폰 잠금·백그라운드·절전·앱 종료·통화 상황의 수신 지속 여부를 목표 기기에서 검증한다. Android의 백그라운드 BLE 경로와 iOS의 bluetooth-central/state restoration 지원이 곧 무중단 녹음 보장은 아니다.
- 회의 후 음성을 텍스트로 변환하고, 원문 구간을 참조할 수 있는 요약·할 일을 생성한다. 화자 구분·정확도는 별도 검증하며 사람이 수정할 수 있게 한다.
- 폰 로컬 처리와 클라우드 처리는 미정이다. 클라우드를 사용한다면 오디오 전송 범위·보관·삭제 설정을 앱에 드러낸다. 사용자의 명시적 녹음 시작과 상태 표시를 기본으로 한다.
- 녹음 데이터 처리와 지갑 서명은 접근권한·메모리를 분리한다. 녹음 중 결제 승인 버튼이 잘못 작동하지 않도록 버튼과 화면 상태를 나눈다. 동시 서명·녹음 가능 여부는 측정 전이다.

연결 없이도 회의 전체를 보존해야 한다면 외부 저장장치를 추가하거나 제품 요구사항을 바꿔야 한다. 이는 사용자 제안의 ‘폰에 바로 저장’ 설계를 임의로 변경한 확정 사항이 아니라 선택 가능한 대안이다.

### 9.3 외형과 사용성

둥근 모서리, 교체 가능한 후면 클립, 작은 상태 화면, 녹음 버튼, 구분되는 승인 버튼, 표시등과 짧은 피드백을 갖춘 외형을 제안한다. 옷·가방 부착뿐 아니라 클립을 받침으로 사용해 테이블에 놓을 수 있으면 음성 메모와 회의 녹음 두 상황에 대응하기 좋다.

가슴에 부착하면 본인 목소리는 가깝지만 먼 참석자의 목소리는 작고 옷 마찰음이 섞일 수 있다. 테이블 회의 품질은 마이크 위치·방향·잡음·케이스 진동을 별도로 평가한다. 금속 클립과 인체 근접은 안테나 및 거리 측정 성능에 영향을 줄 수 있으므로 케이스 완성 후에도 검증한다.

첫 시제품은 NU-54V-DK를 실제로 수용하는 크기로 설계한다. 작은 모듈/전용 PCB로 바꾸지 않고 초소형 완제품 치수를 미리 약속하지 않는다. 사용자 요청 없이 보드를 다른 모델로 교체하지 않는다.

### 9.4 개발 범위를 정하기 위한 선행 검증

1. 선택한 폰에서 30분 이상 연속 음성 수신, 화면 잠금, 연결 중단·재연결, 파일 복구, 누락 표시를 확인한다. 30분은 제안 시험 조건이며 사용자 확정 기준이 아니다.
2. 대응 단말과 보드의 근접 측정을 로그인 세션에 연결하는 자사 서비스 시연을 검증한다. 거리만으로 자동 로그인시키지 않는다.
3. NU 보드·배터리·마이크·화면을 넣는 클립형 케이스를 만들고 실제 착용/탁상 음질·무선 성능·소비전류를 측정한다.
4. 위 결과로 음성 기록과 인증 기능의 첫 버전 범위를 정한다. 기존 지갑·매장 앱·백오피스·컨트랙트·Indexer·패스포트 범위를 자동으로 대체하지 않는다.

첫 테스트 휴대폰은 사용자가 Galaxy S25 Ultra로 지정했다. 설치된 Android/One UI 버전은 미확인이다. 삼성 공식 제품 사양에는 Bluetooth v5.4로 표기되어 있으므로, 이 폰과 NU-54V-DK 사이의 Bluetooth Channel Sounding 지원을 전제로 설계하지 않는다. Android 16 이상이어도 OS API의 존재와 실제 장치의 기능 지원은 별개이며, 지원 기능 조회와 실기 검증이 필요하다.

S25 Ultra에서는 우선 일반 BLE 연결·지갑 통신·음성 데이터 수신 및 화면 잠금/백그라운드 저장 동작을 검증할 수 있다. 아직 실제 전송 성능이나 녹음 안정성을 측정하지 않았다. 정밀 거리 측정은 별도 지원 확인 항목으로 유지하며 RSSI를 같은 보안 수준의 대체 수단으로 취급하지 않는다. 사용자의 메시지에 남은 `2.`는 내용이 없어 추가 요구사항으로 해석하지 않았다.

### 9.5 S25 Ultra에 연결하는 외부 거리 측정 모듈 — 사용자 제안 검토

사용자는 폰에 다른 Bluetooth 6.0 장치를 연결하여 거리 측정만 맡기는 대안을 제시했다. 타당한 설계 후보이며 구매·최종 구성·12주 필수 범위는 아직 확정하지 않았다.

`NU-54V-DK 지갑 ↔ Channel Sounding 지원 측정 모듈 → USB 또는 일반 BLE → S25 Ultra 앱`

측정 모듈이 Channel Sounding 절차와 거리 계산을 수행하고 앱에는 결과를 전달한다. 폰 자체의 Bluetooth 기능이나 Android RangingManager가 업그레이드되는 것은 아니다. Nordic은 두 nRF54L15 DK로 initiator/reflector를 시험하는 경로와 보드에서 거리를 계산하는 샘플을 제공한다. NU-54V-DK 포팅·RF 설정은 별도로 검증한다. Bluetooth 6.0이라는 버전 표기만으로 충분하지 않으며 양쪽 장치와 펌웨어의 Channel Sounding 지원 역할을 확인해야 한다.

- **폰에 고정하는 USB-C 모듈:** 근접 인증의 초기 후보로 추천. 폰이 데이터를 읽고 전원을 공급할 수 있는 Android USB host 경로를 검증한다. USB 인터페이스·권한·전력·충전 중 사용은 확인 대상이다. 일반 Bluetooth USB 동글을 꽂으면 자동으로 된다는 의미는 아니다. 측정 펌웨어와 전용 앱 통신이 필요하다.
- **일반 BLE로 결과를 보내는 모듈:** 별도 배터리 또는 전원이 필요하고, CS 측정과 폰 연결의 동시 동작을 검증한다. 물리적으로 폰에 고정하지 않으면 측정값은 폰이 아니라 모듈과 지갑 사이의 거리다. 독립 설치는 매장 단말 또는 기준점과의 거리 측정에 활용할 수 있다.
- **로그인 적용:** 모듈과 지갑을 인증하고 최신 측정 결과를 실제 로그인 클라이언트의 세션에 연결한다. 오래된 결과나 모듈 연결 끊김은 근접 확인 성공으로 처리하지 않는다. USB 연결 자체만으로 모듈이 반드시 폰 옆에 있다는 증명이 되지는 않는다. 고정 형태와 신뢰 가정이 필요하며, 원격 조종된 클라이언트까지 근접성만으로 판별할 수는 없다.
- **기존 기능 유지:** 음성은 지갑에서 폰으로 직접 보내는 경로를 유지하는 안이다. 별도 측정 모듈에 음성·결제키 처리를 맡길 필요는 없다. 녹음·거리 측정·지갑 통신 동시 사용의 메모리와 무선 자원은 실측한다.

검증 순서는 두 보드 거리 측정 → 측정 모듈 결과를 폰 앱에서 읽기 → 로그인 세션 연동 → 착용·소형화로 제안한다. 별도 모듈은 키오스크/PC에도 재사용할 수 있는 설계 후보이지만 해당 플랫폼의 실제 연결 지원을 별도로 확인해야 한다. NU 보드의 디버거 USB 단자를 애플리케이션 USB 장치 기능으로 가정하지 않는다.

후속 작업으로 [부품·연결·시험 계획](ranging-module-validation-plan.md)을 작성했다. 첫 기준안은 NU-54V-DK 지갑 + Nordic nRF54L15 DK 측정 모듈 + USB로 S25 결과 수신이다. 사용자는 두 보드 보유를 확인했고, 실기 검증을 개발 단계로 미뤘다. 이어서 [소프트웨어 화면·권한·결제 흐름 초안](software-product-blueprint.md)을 작성했다. 구현·실기 시험이 완료되었다는 의미는 아니다.
