# [NU-54V-DK 02] 보안칩을 빼기로 한 이유: TrustZone으로 결제 키를 지키고 정산 컨트랙트를 먼저 세우다

### 4주차 점검 결과와 외부 보안칩을 빼는 결정, 그리고 5주차에 앞당겨 만든 정산 컨트랙트를 정리했습니다

> 스테이블코인 결제 기기 제작기 02 · 이전 글: [NU-54V-DK 01] 스테이블코인 결제 기기 만들기: 계획을 세우고 LED·버튼부터 켜다 (<1편 Medium URL>)

하드웨어 지갑이 휴대폰 지갑보다 안전하다고 말하는 이유는 결국 하나입니다. 서명에 쓰는 개인 키(private key)가 인터넷에 연결된 기기 밖으로 나오지 않는다는 것입니다. 그렇다면 결제 기기 안에서 그 키는 정확히 어디에 있어야 할까요?

가장 확실한 답은 전용 보안칩(secure element)입니다. 키를 칩 안에서 만들고, 서명도 칩 안에서 하고, 칩을 뜯어도 키를 꺼내기 어렵게 설계된 부품입니다. 저희도 처음에는 9주차에 외부 보안칩을 붙이는 계획을 세웠습니다. 하지만 부품을 조달하고 연결해 검증할 시간이 12주 일정 안에 나오지 않았습니다.

그래서 저희는 보드의 칩(nRF54L15)에 들어 있는 **Arm TrustZone**으로 키를 지키기로 했습니다. 이 결정으로 펌웨어 담당의 8~12주차 작업이 **28.5일에서 22.5일**로 줄었고, 9주차 보안칩 확인 지점은 없어졌습니다. 대신 정산 컨트랙트를 5주차에 앞당겨 만들어, 컨트랙트 한 건 결제의 실제 가스 비용(**165,399 gas**)을 먼저 쟀습니다.

이번 글에서는 4주차 점검에서 무엇을 확인했는지, 보안칩 대신 TrustZone을 고른 이유와 그 한계, 그리고 5주차에 만든 정산 컨트랙트를 살펴보겠습니다. TrustZone 펌웨어 구현은 8주차 작업이라 이번 글에서는 설계만 다룹니다. 이 프로젝트는 테스트넷과 시험용 토큰만 쓰는 개념 증명(PoC)이며 실제 자산 결제 서비스가 아닙니다.

> [그림 1] 대표 이미지: 결제 기기 칩 안을 두 구역(보안 구역과 일반 구역)으로 나눈 개념도. 보안 구역에는 열쇠 아이콘과 버튼 아이콘, 일반 구역에는 BLE와 LED 아이콘. (AI 생성 또는 직접 작성 예정)

## 1. 4주차 점검: 보드와 보안칩 자료를 확인하다

저희 일정에는 주차마다 "확인 지점(게이트)"이 있고, 약속한 결과가 나오지 않으면 미리 정한 순서대로 범위를 줄입니다. 4주차 확인 지점의 조건은 두 가지였습니다. 보드의 기본 기능이 동작하는지, 그리고 외부 보안칩 후보가 저희 서명 알고리즘(secp256k1)을 지원하는지입니다. 두 조건 모두 통과했습니다.

| 시험 | 확인한 것 |
|---|---|
| 부팅 로그 | 리셋 10회 모두 같은 부팅 기록. 전원을 다시 넣었을 때는 리셋 원인이 "전원 투입"이고 펌웨어 이름·버전이 같은 것을 확인 |
| LED, 버튼 | LED 4개 동작, 버튼 4개의 짧게·길게 누름 |
| 타이머 | 120초 동안 오차 9 ms(측정 방법의 지연 수준) |
| BLE 광고, 연결, 해제 | 휴대폰과 맥에서 검색, 연결, 양쪽에서 끊기 |
| BLE 쓰기, 알림 | 휴대폰이 보낸 데이터 수신, 기기가 보낸 알림 수신 |

전원을 다시 넣은 직후의 부팅 문장 자체는 받지 못했습니다. USB를 뽑으면 보드의 디버거도 함께 꺼져서, 컴퓨터가 시리얼 포트를 다시 잡기 전에 칩이 이미 부팅을 끝내기 때문입니다. 그래서 칩이 기록하는 "리셋 원인"과 펌웨어 정보를 대신 증거로 삼았습니다.

보안칩 후보는 세 가지를 제조사 자료로 확인했습니다. NXP SE050 계열만 secp256k1 서명을 칩 안에서 지원했습니다(NXP 응용 노트 AN12436 표 1). Infineon OPTIGA Trust M과 TROPIC01은 이 곡선을 지원하지 않았습니다.

> [그림 2] 4주차 점검 사진: LED 네 개가 켜진 보드 사진. (직접 촬영, 기존 사진 사용)

## 2. 보안칩을 빼기로 한 이유

SE050이 조건을 만족했는데도 빼기로 한 이유는 시간입니다. 보안칩을 쓰려면 개발 키트를 주문하고, I2C로 배선하고, 칩과 통신하는 드라이버를 이식하고, 칩과 MCU 사이 통신을 보호하는 설정까지 해야 합니다. 저희 계획에서는 이 작업이 6일이었습니다. 같은 시기에 펌웨어 담당은 폰 앱까지 맡고 있어서, 8주차에만 7일짜리 일정이 잡혀 있었습니다.

선택지는 두 가지였습니다. 보안칩 확인 지점을 한 주 미루고 일정을 감수하거나, 보안칩을 빼고 칩에 내장된 보안 기능으로 가는 것입니다. 저희는 두 번째를 골랐습니다. 이 PoC가 증명하려는 것은 "여행자가 확인하고 버튼으로 승인한 결제만 정산된다"는 흐름이고, 그 흐름은 TrustZone으로도 성립하기 때문입니다.

## 3. TrustZone으로 키를 지키는 구조

nRF54L15의 메인 코어는 Arm Cortex-M33이고 TrustZone을 갖추고 있습니다. TrustZone은 칩 하나를 보안 구역(secure)과 일반 구역(non-secure)으로 나눕니다. 일반 구역의 코드는 보안 구역의 메모리와 주변장치에 접근할 수 없습니다. 저희는 Arm이 만든 보안 구역용 펌웨어인 TF-M(Trusted Firmware-M) 위에 키 서비스를 올릴 계획입니다.

| 구역 | 하는 일 |
|---|---|
| 보안 구역(키 서비스) | 키 생성과 보관, 서명, 승인 버튼 입력, PIN 재시도 횟수 |
| 일반 구역(앱) | BLE 통신, 결제 메시지 검사, 폰 앱으로 결제 내용 전달, LED 안내 |

핵심은 **버튼과 서명을 같은 구역에 묶는 것**입니다. 일반 구역의 앱은 "이 결제 한 건에 서명해 달라"고 보안 구역에 등록만 할 수 있습니다. 보안 구역은 승인 버튼이 눌렸을 때 등록된 그 한 건에만 서명합니다. 그래서 일반 구역 코드가 뚫려도, 사람이 버튼을 누르지 않은 결제나 등록되지 않은 형식에는 서명이 나오지 않습니다.

칩의 암호 가속기 CRACEN은 secp256k1 서명을 지원합니다. 다만 칩의 하드웨어 키 보관 장치(KMU)는 저희가 확인한 SDK 코드상 P-256과 Ed25519 같은 곡선만 받고 secp256k1은 받지 않는 것으로 보였습니다. 그래서 키는 TF-M의 보호 저장소에 암호화해 두고, 서명할 때만 보안 구역 메모리로 불러옵니다.

> [그림 3] 서명 흐름도: 일반 구역이 서명할 결제를 등록 → 폰 앱에 결제 내용 표시 → 사람이 승인 버튼 → 보안 구역이 등록된 한 건에만 서명. (직접 작성 예정)

## 4. TrustZone이 막지 못하는 것

TrustZone은 소프트웨어 공격을 막는 데 강합니다. 하지만 기기를 손에 넣은 사람이 칩을 뜯거나, 전압과 클록을 흔들어 오작동을 유도하거나(fault injection), 전력 소모 패턴을 분석하는(부채널, side channel) 물리 공격은 보안칩만큼 막지 못합니다. 대여 기기는 누군가 오래 들고 있는 물건이라 이 한계는 가볍지 않습니다.

그래서 세 가지를 함께 둡니다. 첫째, 보호 저장소 암호화와 디버그 포트 잠금(AP-Protect)을 반드시 켭니다. 둘째, 정산 컨트랙트가 한 번 결제와 하루 결제의 한도를 강제해, 키가 새더라도 잃을 수 있는 금액을 제한합니다. 셋째, 이 한계를 12주차 수용 기록에 예외(waiver)로 남겨, 다음 단계에서 보안칩을 다시 검토할 근거로 둡니다.

## 5. 정산 컨트랙트를 먼저 세우다

펌웨어 일정에 여유가 생기는 동안, 정산 컨트랙트는 계획보다 한 주 앞서 5주차에 만들었습니다. 기기가 서명한 결제를 키오스크가 제출하면 컨트랙트가 순서대로 검사합니다.

1. 다른 체인이나 다른 배포에 쓰려는 서명인지
2. 이미 결제된 주문인지(같은 서명을 다시 보내면 여기서 멈춥니다)
3. 유효 시간이 지났는지
4. 서명한 기기의 계정이 살아 있는지
5. 가게가 등록되어 있고 받는 주소가 등록된 주소와 같은지
6. 이미 쓴 일회용 번호(nonce)인지
7. 한 번 결제·하루 결제 한도를 넘는지
8. 잔액이 충분한지

컨트랙트 시험 30개와 불변 조건(invariant) 시험 2개를 두었습니다. 불변 조건 시험은 입금, 결제, 같은 서명 재전송, 인출을 무작위로 수만 번 섞어 실행하면서 "컨트랙트는 언제나 갚아야 할 금액 이상을 들고 있다"와 "한 주문은 한 번만 정산된다"가 깨지지 않는지 확인합니다.

로컬 테스트 체인에서 잰 가스는 다음과 같습니다. StableNet 테스트넷의 가스 가격(47,600 gwei)으로 환산하면 결제 한 건에 약 7.9 WKRC입니다. 테스트넷 가스는 StableNet 테스트넷 faucet에서 하루에 한 번 2,000 WKRC를 받을 수 있어 충분합니다.

| 트랜잭션 | gas |
|---|---|
| 컨트랙트 한 세트 배포(시험 토큰, 가게 등록부, 정산) | 1,784,971 |
| 결제 한 건(settle) | 165,399 |
| 기기 계정 입금(depositFor) | 97,947 |

처음에는 결제 한 건을 150,000 gas로 추정했는데, 실제로는 이를 넘었습니다. 그래서 키오스크가 "가스가 부족하니 결제를 받지 않는다"고 판단하는 기준을 15 WKRC에서 20 WKRC로 올렸습니다. 추정으로 정한 값을 측정으로 고친 첫 사례입니다.

## 6. 바뀐 일정과 다음 글

1편의 일정표에서 달라진 것은 다음과 같습니다.

| 주차 | 1편 계획 | 바뀐 계획 |
|---|---|---|
| 5주차 | 정산 컨트랙트 핵심 | 핵심과 결제 처리까지 완료, 가스 실측 |
| 8주차 | TF-M 키 보관, 셋업 명령 | 같음 |
| 9주차 | 외부 보안칩 통합(확인 지점) | 보안칩 제외. 결제 채널 암호화와 폰 연결 |
| 10~12주차 | 폰 앱 | 폰 앱 결제 확인 화면을 11주차로 앞당김 |

## 마무리

이번 편에서는 4주차 점검을 통과하고, 외부 보안칩 대신 TrustZone으로 키를 지키기로 한 이유와 그 한계를 정리했습니다. 가장 어려웠던 점은 "더 안전한 선택"과 "12주 안에 끝낼 수 있는 선택" 사이에서 무엇을 포기하는지 분명히 적는 일이었습니다. 다음 편에서는 6주차에 정산 컨트랙트를 테스트넷에 배포하고, 기기 대신 소프트웨어 키로 서명한 첫 결제를 블록에 기록하는 과정을 다루겠습니다.
