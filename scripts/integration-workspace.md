# Disposable integration workspaces

Each run owns its build output, test caches, raw results and temporary credentials. On success, failure or interruption, stop the run's children, collect its result and remove those resources before returning. A compact result can retain the exit status, checks and input digests. A caller that supplies a reusable build or device retains ownership. For simultaneous runs, identify resources by the directory, process or device ID created by each invocation.

On macOS the privacy recovery rehearsal uses three PostgreSQL clusters at once for the live databases, the separate erasure journal and the restored data. If PostgreSQL reports `shmget` with `ENOSPC` for a 56-byte segment, compare `ipcs -m -a` with `sysctl kern.sysv.shmmni` to check the kernel's segment slots. Preserve the failed run's timestamp, data directory and reported IPC key in the compact diagnostic. They can identify a segment left by a failed bootstrap after its directory is gone. Two such segments were reclaimed by matching the project's error keys, verifying the owning user, checking for zero attachments and confirming that the creator process had exited. Coordinate other database tests around this three-cluster phase. [Recovery rehearsal](../products/p10-platform/recovery/test_erasure.py)

The commercial integration suite, travel booking suite, P07 generation tests, P03 PostgreSQL runner and native pickup, private records and erasure fixtures create one private workspace per invocation. PostgreSQL, service binaries, Go build output and temporary files belong to that invocation. Explicit readiness, DSN and test-result paths remain owned by the caller. When P07 runs inside the commercial suite it uses the caller’s isolated PostgreSQL and build cache, and owns its own Anvil process group. For a long-running suite, keep the process managed by its launching session through the cleanup receipt. A log that stops growing or a missing console handle does not establish that the database has stopped. During recovery, verify the exact cluster path and process with `pg_ctl status`, stop that cluster, confirm shutdown and check for remaining open files before removing its workspace.

The PostgreSQL launcher completes its bounded startup handshake before a queued interrupt is handled. This matters because PostgreSQL leaves the launcher process group. Cleanup first stops service process groups and reaps their leaders. It then tries PostgreSQL fast shutdown, followed by immediate shutdown if needed. Each stop attempt is followed by a status check. The workspace is removed only after PostgreSQL reports it is down. If the result is uncertain, the runner reports the owned path and retains it for inspection. A second TERM during cleanup does not interrupt those steps.

## Order scenario across the products

`python3 scripts/test_order_flow.py` runs the spending-wallet order scenario from enrollment to the board reset on one machine, without a board, a phone or a real chain. It takes about five minutes and prints one `PASS` or `FAIL` line for each of sixteen flows, then one result line. The exit status is zero only when every flow passed. Output of a failed run goes to standard error. Add `--verbose` to see it as it comes, or `--only PATTERN` to run the flows whose names match, for example `--only 'enroll|deposit|duplicate'`. Flows share one phone, board, kiosk and store and run in order, so keep `enroll` and `deposit` in the pattern.

The run needs Go, Node with the workspace dependencies, Foundry with the pinned compiler, CMake, OpenSSL 3, the Python `cryptography` package and PostgreSQL 15 (`--postgres-bin`, a Homebrew keg, or `PATH`). It owns a private PostgreSQL cluster, an Anvil chain 8283, the indexer, the server and the apps. All of them and the workspace under `/tmp/nu54-flow-*` are gone after success, failure, TERM, HUP or INT. Go's own build cache is the only shared directory.

|---|---|
| Contracts | `TestUSDC3009` and `OrderEscrow` from P06 on Anvil |
| Server and indexer | P05 handlers over mutual TLS, worker, dispatcher and receiver; the P07 `indexer` process. [order_flow_anvil_test.go](../products/p05-operations-backoffice/test/order-flow/testdata/order_flow_anvil_test.go) is compiled into the settlement package with `go test -overlay` and reuses the fixtures of `order_escrow_anvil_test.go` |
| Board | Firmware core plus the request, button, return and reset functions taken out of `device_pilot.c` by `extract_c.py`, in [board_host.c](../products/p05-operations-backoffice/test/order-flow/board/board_host.c) |
| Phone | The P02 screens `CustomerOrders` and `BoardLife`, `OwnerSession`, `CustomerNearby` and their records, under the P02 Jest setup |
| Kiosk | P04 `NearbyRelay` and `MerchantInbox`, `CommerceClient` over HTTPS, and `NearbyCommerceLink` on both ends |

Stood in for: the phone's native modules (storage, Bluetooth, key store, TLS to the board), the board's flash, PIN entry, buttons and lamp, the operator's grant, and the genesis hash the app pins. Retry delays of the server are shortened and the runner mines one block per second.
