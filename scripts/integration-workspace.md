# Disposable integration workspaces

Each run owns its build output, test caches, raw results and temporary credentials. On success, failure or interruption, stop the run's children, collect its result and remove those resources before returning. A compact result can retain the exit status, checks and input digests. A caller that supplies a reusable build or device retains ownership. For simultaneous runs, identify resources by the directory, process or device ID created by each invocation.

On macOS the privacy recovery rehearsal uses three PostgreSQL clusters at once for the live databases, the separate erasure journal and the restored data. If PostgreSQL reports `shmget` with `ENOSPC` for a 56-byte segment, compare `ipcs -m -a` with `sysctl kern.sysv.shmmni` to check the kernel's segment slots. Preserve the failed run's timestamp, data directory and reported IPC key in the compact diagnostic. They can identify a segment left by a failed bootstrap after its directory is gone. Two such segments were reclaimed by matching the project's error keys, verifying the owning user, checking for zero attachments and confirming that the creator process had exited. Coordinate other database tests around this three-cluster phase. [Recovery rehearsal](../products/p10-platform/recovery/test_erasure.py)

The PostgreSQL launcher completes its bounded startup handshake before a queued interrupt is handled. This matters because PostgreSQL leaves the launcher process group. Cleanup first stops service process groups and reaps their leaders. It then tries PostgreSQL fast shutdown, followed by immediate shutdown if needed. Each stop attempt is followed by a status check. A second TERM during cleanup does not interrupt those steps.

## Order scenario across the products

`python3 scripts/test_order_flow.py` runs the spending-wallet order scenario from enrollment to the board reset on one machine, without a board, a phone or a real chain. It takes about five minutes and prints one `PASS` or `FAIL` line for each of seventeen flows, then one result line. The exit status is zero only when every flow passed. Output of a failed run goes to standard error. Add `--verbose` to see it as it comes, or `--only PATTERN` to run the flows whose names match, for example `--only 'enroll|deposit|duplicate'`. Flows share one phone, board, kiosk and store and run in order, so keep `enroll` and `deposit` in the pattern. `--token won` runs the same flows at a store that takes the test won token, with a board built for that token. `--token krwc` does so at a store that takes StableNet's own coin, which this chain has only as a stand-in at the coin's address. `--token all` opens the three stores on one server, with one indexer, one gas account and three boards, runs nine flows at each at the same time, checks that a fourth branch whose settings do not match its chain takes no orders, and compares locked money with what was paid out, given back and held.

The run needs Go, Node with the workspace dependencies, Foundry with the pinned compiler, CMake, OpenSSL 3, the Python `cryptography` package and PostgreSQL 15 (`--postgres-bin`, a Homebrew keg, or `PATH`). It owns a private PostgreSQL cluster, an Anvil chain 8283, the indexer, the server and the apps. All of them and the workspace under `/tmp/nu54-flow-*` are gone after success, failure, TERM, HUP or INT. Go's own build cache is the only shared directory.

## User app on an emulator

`python3 scripts/simulate_user_app.py emulator-5554` opens the user app on an Android emulator in the same world as the order flow: the board, the kiosk and the store answer as they should. Use it to tell a fault of the app from a fault of the hardware. Build and install the debug app with `--build` the first time and after any change to what the APK contains.

- `--build` runs `./gradlew :app:assembleDebug` without the `ORG_GRADLE_PROJECT_*` variables of the environment, writes `app-debug.apk.inputs.json` beside the APK and installs the APK on the emulator. It asks for `pnpm install` first when `node_modules/.pnpm/lock.yaml`, pnpm's copy of the lockfile it installed, is not `pnpm-lock.yaml`. The record holds the SHA-256 of the APK and of each file the build reads: the app's `android` and `native` directories, `src/specs`, `package.json`, the Kotlin sources of `packages/protocol/platform`, the Gradle scripts applied from `scripts/android`, `pnpm-lock.yaml` and `.npmrc`. A new file counts wherever it lies below them, except what the build, the editor and the machine write there: the Gradle build directories, `node_modules`, `local.properties`. Screens and logic are left out because the bundler serves them from the working tree. [app_build_record.py](app_build_record.py) names the rules. A build that fails keeps the record of the build before it.
- Every run compares that record with the working tree and with the APK installed on the emulator before it touches the app. It stops when the record is missing, a recorded file changed, `node_modules` was installed from another lockfile, or the emulator holds another build than the recorded one. The installed app is what counts: the APK file in the build directory may have been built again since, as the lab scripts beside `gradlew` do. A build made with `./gradlew` alone has no record, so it stops too. It also stops when the installed app does not declare a permission that the run grants and `AndroidManifest.xml` declares.
- `--allow-stale-app` runs anyway. It prints `STALE APP ALLOWED` with the reason, adds it to the `PASS` or `FAIL` line of every flow and to the result line, and writes `STALE-APP.txt` into the `--walk` directory. A run let through this way ends with exit code 3 instead of 0 when nothing failed, and with 1 when a flow failed. Such a run is not a result for the current sources.
- `--walk NEW_DIRECTORY` taps through fifteen flows in about twenty minutes, prints one `PASS` or `FAIL` line for each and keeps screenshots: the agreements, setup, deposit, tokens, the faucet, networks, settings, a transfer, payment to receipt, refusal, limit, missing board, a connection lost after signing, the inner pages and the return with reset. The directory is made once the app is admitted, so a run refused for a stale app can be repeated with the same name.
- `--route entrance` runs the app as a build that orders without a registration at a store: the store finder, a store page, its menu, the checkout with the board's account proof, the order and its pickup QR. The repository's build binds no customer entrance and no order contract, so this route exists in a run only; [the next section](#the-route-without-a-store-registration) says how. With `--walk` it walks two parts, each in a world of its own because one world lives 43 minutes: `stores` (seven flows that need no board) and `orders` (thirteen flows that start with one). `--part stores` or `--part orders` walks one part, and may write into the directory the other part wrote.
- `--token won` or `--token krwc` opens a won store instead of the dollar store.
- Without `--walk` the app stays open for 43 minutes. `--step NAME JSON` takes the steps of the owner, kiosk, store or operator from another terminal, for example `--step order '{"quantity":2}'` puts an order on the kiosk and before the phone's camera, and `--step board '{"change":{"answer":"refuse"}}'` makes the owner refuse. [host.test.ts](../products/p05-operations-backoffice/test/order-flow/simulator/host.test.ts) lists them.

The app's screens and logic, its notifications, the firmware core, server, indexer and contracts are real. Bluetooth, TLS, the phone's protected storage and keys, the camera and the board's buttons and PIN are stood in for, and one-second countdowns tick every three seconds so that the screen can be read. Only the bundler configuration in that directory replaces the native modules, so no build of the app contains them. It runs on emulators only. The bundler listens on port 8785 and the stand-ins on 8790, both on this machine.

### The route without a store registration

`python3 scripts/simulate_user_app.py emulator-5554 --route entrance --token won --walk NEW_DIRECTORY` walks the route on which a phone registers at no store. Beside each screenshot it keeps the words of that screen in a text file of the same name, for reading the wording without the picture. A flow checks what the app's code says a screen shows. Where the app does something else the flow fails with a line that says what, after it took its screenshots, and the walk goes on.

The app opens this route only when its build binds a customer entrance and an order contract (`approvedCustomerEntrance` and `approvedOrderPayment` in `customerEntranceDeployment.ts`), and the repository binds neither. A run binds its own, for its own bundler alone:

1. The host writes a module with the two values into the run's directory under `/tmp`: the origin of the run's entrance, the CA made for the run and the SHA-256 of the entrance certificate's key; chain 8283, the run's `OrderEscrow` and its token. The values first pass the rules of a release's build file (`build-tools/customer-order-build.js`), so the run binds nothing a release could not ([orderBinding.ts](../products/p05-operations-backoffice/test/order-flow/simulator/orderBinding.ts)).
2. `NU54_SIMULATOR_ORDER_BINDING` names that module to the bundler of the run, and only [metro.config.js](../products/p05-operations-backoffice/test/order-flow/simulator/metro.config.js) beside the stand-ins puts it in the place of `customerEntranceDeployment.ts`. The host starts first, so the module is there when the bundler starts.
3. The app's own `metro.config.js`, its Babel configuration and its Jest never read that variable, and no module is kept in the repository. [binding.test.ts](../products/p05-operations-backoffice/test/order-flow/simulator/binding.test.ts) holds all of it: under Jest and in a bundle of the repository both values stay `undefined`, also while a run names its binding.

Made small or short for a run, so that the server itself answers: one request limit of the entrance (`--step limit '{"kind":"read","perMinute":4,"burst":1}'`, and without numbers the server's own again), after which the entrance answers 429 with its Retry-After; and the end of an unpaid cart's hold (`--step endHold '{}'`), after which the server's expiry loop closes the cart. On the phone's side of the connection the stand-in can lose one answer (`--step entrance '{"change":{"loseReply":"order.create"}}'`) or reach no server (`{"change":{"entrance":false}}`). `--step stock '{"sku":"cheesecake","count":1}'` sets what is left of a product, as another customer's order would, and `--step entrance '{"change":{}}'` shows the last requests the phone sent and how many of each kind got which answer.

## 키오스크를 로컬 매장에 붙여 보기

`python3 -B scripts/simulate_kiosk_app.py <에뮬레이터> <새 폴더> [--stay]`는 주문 흐름과 같은 서버·DB·체인을 띄우고, 같은 서버에서 운영 웹을 내준다. 운영 웹을 브라우저로 조작해 카페 메뉴 7개(사진 6장, 묶음 상품 3개)를 게시하고 재고를 넣은 뒤, 키오스크 앱을 에뮬레이터에서 태블릿 가로 화면으로 띄운다. 키오스크의 화면은 실제이고 네이티브 모듈만 `test/order-flow/simulator`의 것으로 바뀐다. 사진이 오는 동안에는 uiautomator가 화면을 읽지 못하므로 `--stay`로 띄워 두고 `adb`로 누르며 캡처한다. 실제 BLE와 보드는 확인하지 않는다.
