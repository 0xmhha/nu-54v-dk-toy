# 좌석 없는 픽업과 원주문 환불

T06은 등록 고객이 지정 지점의 픽업 가능 시간과 메뉴를 조회하고 시간·수량·가격을 검토한 뒤 기존 C3 주문으로 승인한다. 승인된 시간의 불투명 참조와 확인한 시작 시각을 장바구니 해시에 포함한다. 지점별 운영 설정에 게시된 활성 시간 중 메뉴 영업과 준비 여유가 있고 주문 여유가 있는 시간만 제공한다. 메뉴 가격·재고·픽업 시간이 달라지면 접수 전에 새 조건을 검토한다.

P05에서 주문 요청 확인, 픽업 시간 검증, 메뉴 재고 차감, 원주문과 픽업 시간 연결을 하나의 트랜잭션에서 수행한다. 확정된 동일 요청을 재시도하면 시간이나 재고가 바뀐 경우에도 원주문을 반환한다. 다른 시간이나 내용을 같은 요청 또는 원천 참조로 재사용하면 충돌한다. 기존 C3 지급·주문 재조회 멱등 키를 그대로 사용하며 좌석 원장을 사용하지 않는다.

T07은 원주문의 체인 지급과 기존 매장 접수 효과를 바탕으로 픽업 번호를 보여 준다. 주문 접수·준비 완료·수령과 이행 불가는 주문 상태에서 구분한다. 이행 불가 뒤 환불 요청·정산 워커·확정 증거는 동일 원주문을 참조하며 별도 지급 확인 전 환불을 완료로 표시하지 않는다. P02는 등록 지점의 본인 원주문에서만 이를 읽고, P04는 등록 지점 운영 역할의 접수 항목만 갱신한다.

C3 `order.status`의 일반 물품·카페 응답은 지급 확정 시 기존처럼 번호와 영수증을 반환한다. 098부터 여행 픽업 원주문은 지급 확정 뒤에도 같은 주문의 이행 접수 전까지 번호를 공개하지 않는다. 이 구간에는 `paid`, 기존 영수증·확정 거래, 그리고 `receiptKind: "pickup-awaiting-acceptance"`를 반환한다. 접수 후에는 같은 영수증과 고정 번호를 기존 실물 응답 형태로 반환한다. 전용 픽업 조회도 동일한 이행 접수 근거를 사용한다. 디지털 이용권과 좌석 예약 지급은 각각 `"digital"`과 `"booking"`을 유지한다. 미확정 주문에는 영수증 종류, 영수증 및 픽업 번호가 없다.

업데이트된 앱은 일반 원주문 목록에서도 이 구간을 지급 확정과 매장 접수 대기로 구분한다. 구형 C3 SDK는 이 중간 상태를 거절하므로 여행 전용 조회를 사용하거나 앱을 업데이트해야 한다.

## 지점 설정 및 상태 조회

P05 042·043을 적용한다. 지점 운영 설정에서 `travel_pickup_window`에 영업 범위의 시작·종료와 접수 가능한 주문 수를 등록한다. 예약된 시간에 이미 연결된 주문을 다른 시각으로 이동시키지 않는다. 시간 변경 시 새 시간 참조를 게시한다. 고객 API는 기간과 지점의 필요한 일정 정보만 제공한다.

조리 단말에는 별도 지점 단말 인증서를 발급한다. P05의 `travel_pickup_terminal`에서 현재 지점의 단말 권한과 연결하고, 해당 직원 장치 등록서에 `pickupKitchen: true`를 넣는다. P04 화면을 여는 해당 설정은 서버 권한을 부여하지 않는다. 공용 단말과는 다른 직원 통제 장치를 쓴다. 승인된 조리 역할은 원주문 준비·수령·이행 불가를 기록할 수 있다. 원결제가 `paid`이고 기존 이행 소비자의 접수가 기록된 경우에만 조리 목록에 표시된다.

이행 불가가 기록된 픽업의 정식 환불은 기존 재무의 `merchant_cancel` 경로에서 원주문을 지정한다. 검토·승인·재원 제출 권한과 지급 증거는 기존 P05 환불 원장을 따른다. 앞선 유효 요청을 다른 키로 중복 생성할 수 없고 남은 원금 전체를 기준으로 한다. P02는 요청·확정 상태와 별도 증거를 원주문에서 읽는다. 선택 정보·조리·재무 셋은 서로의 권한을 취득하지 않는다.

## 시험

```bash
P05_PICKUP_TEST_DATABASE_URL='<migrated-nu54_commerce_-disposable-dsn>' \
  go test ./products/p05-operations-backoffice/internal/commerce -run '^TestPickup' -count=1 -v
bash scripts/ios/scene-smoke/run-travel-pickup.sh <simulator-udid> <p02-derived> <p04-derived> <new-result-dir>
```

엄격한 통합 시험은 별도 P05 pickup DB를 생성해 세 `TestPickup` 검증을 필수로 실행한다. 네이티브 시험은 실제 P02와 P04, 서명된 합성 P09 카탈로그, P05 mTLS를 사용한다. 테스트 전용 루프백 제어기는 알맞은 합성 주문에 지급 관측과 이행 접수, 별도 재무 증거를 공급한다. 실제 보드, 토큰 송금, 운영 지점은 시험 대상에 포함되지 않는다.

정규 `make commercial-integration-test`는 `TestLoopbackSettlementEvidenceAndRefund/TravelPickupOriginalPendingToReady`를 요구한다. 실제 P01 C 호스트의 승인과 루프백 Anvil/P07 확정, P05 mTLS 이행 접수를 사용한다. 지급 전에는 번호와 영수증이 없고, 지급 후라도 같은 매장의 이행 접수 전에는 번호가 없다. 준비 시작과 준비 완료에서 번호 및 영수증은 같다. 원견적·제출·릴레이·지급·접수는 각 한 건이며 여행 좌석은 생성하지 않는다.

격리된 iOS에서 같은 경로를 보려면 `bash scripts/ios/scene-smoke/run-travel-t07-owned.sh --pickup <absolute-display-python>`를 실행한다. 이 경로는 서명된 합성 고객 앱을 설치하고 정상 여행 픽업에서 주문을 연다. 보드 운반과 C 호스트의 버튼 입력은 로컬 시험 장치이며 재시작 후 일반 결제 이력에서 원주문을 읽는다. 실행기는 소유한 시뮬레이터·원장·로컬 체인·빌드 캐시를 회수하고 판정과 앱 지문만 출력한다.
