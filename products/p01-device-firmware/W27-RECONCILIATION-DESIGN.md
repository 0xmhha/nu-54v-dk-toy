# W27 EVM reservation reconciliation: staged contract

Status: design, not enabled. `nu54_owner_limits` schema 1 remains byte-for-byte unchanged and no existing reservation is removed by this document. An unqualified board or unavailable evidence keeps the reservation and refuses unsafe day rollover, policy activation, and new signatures when the table or cap blocks them. The phone's RPC response is not a board authority.

## Existing boundary and why schema 1 cannot safely erase

The ordinary EVM gateway decodes the canonical unsigned EIP-1559 bytes and reserves against their Keccak digest before signing. The digest commits to the chain, account nonce, token call, recipient, amount and fee fields; the owner address is checked at the signing gateway. Schema 1 stores the digest, amount, request ID and expiry but neither signer nor nonce nor an authenticated on-chain finality cursor. Its 16 slots include both issued and possibly unissued signatures. A local request expiry does not invalidate an EVM transaction. The P01 payment-receipt reclaim command uses an enrolled settlement authority and a trusted expiry floor for the P06 quote domain; neither that floor nor P07's commerce-specific projection establishes finality for arbitrary owner EVM transactions. Reusing those claims as general-chain evidence would cross their scope.

A replayable authorization to remove `(request ID, digest)` is insufficient: after removal, the same tuple could be reintroduced and an old authorization could remove it again. A successful transaction must remain charged to the UTC day in which its finalized block executed, even after its pending slot is cleared. Native gas fees are not token amounts and cannot be subtracted from a token-denominated daily allowance. A replacement must be checked for its actual protected-asset effect, not assumed harmless from its different transaction hash.

## Required separate version and authority

A new versioned protected record must bind board, owner generation, signer address, network identity including genesis, asset, policy revision and a monotonic accepted nonce high-water mark for the one bound signer. Each pending entry retains the canonical unsigned digest, nonce, amount and request ID under that signer and generation. Reservation and high-water advance, and separately removal and accounting, each require one rollback-protected atomic state transition. A finalized account nonce can fence replay of all lower nonces, but it cannot alone establish which lower transaction consumed value: unresolved entries retain their full charge until each effect has separately verified evidence. Persisted evidence identifiers and a bounded replay strategy must survive slot reuse and reset. A scheme that cannot prove an idempotent result after an ambiguous write fails closed.

Enrollment must authorize a specifically scoped finality verifier for an exact chain/genesis and signer role, distinct from ordinary phone RPC and without assuming the existing installation-authority key is a chain oracle. The signed, versioned claim binds the board and generation, chain/genesis, signer, protected asset, exact canonical original unsigned digest and request, original nonce, canonical finalized block/hash, finalized account nonce and terminal disposition. The verifier must establish canonical finality and an unresolved reorganization/conflict must revoke issuance. The board must validate the signature under the enrolled scoped verifier, decode the original bytes itself, compare their digest and all policy bindings, and reject wrong chain, signer, generation, asset, nonce, transaction, block or authority. This new verifier enrollment and a real chain-finality adapter are not currently present.

* Original success: account nonce consumed, exact original included successfully. Charge the full protected-asset amount on the verified block UTC day; when reconciling after that day, its earlier charge has elapsed and the unresolved carry can be removed.
* Original finalized failure: exact original included with a final revert; token effect is zero, so its amount may be released. Native gas is outside this token-unit allowance.
* Finalized replacement: same chain, signer and nonce, different finalized transaction, with an independently verified protected-asset debit. Release only the portion proven not debited; absence of a complete effect proof leaves the whole amount charged. Other outgoing transactions and fee currencies cannot be silently treated as zero.
* Pre-sign failure: release only with an authenticated device-side durable state transition proving that this exact request never reached any signature-producing operation; neither local expiry nor a handset error proves this. An ambiguous call to the signer remains reserved.

Both the schema-1 interim path and schema-2 model may open a later UTC day before terminal proofs: every unresolved amount is first carried in full, and the trusted lower and upper time bounds must lie wholly in that day. In schema 2 a verified original success retains that carried amount if the block executed on the current UTC day; if its execution day is earlier, the carry is removed because that day has elapsed. A finalized revert removes its amount. Future block times, uncertain day boundaries and backwards time are rejected. Schema 1 has no finality removal. Policy activation requires no unresolved reservations; it must not lower today’s cap below today’s already charged amount, and it resets completed previous-day spend only on a certain later day. Concurrent reserve, reconciliation, policy change and rollover share the protected-store lock. Lost acknowledgements reread the committed state and return the existing terminal result only when the same authenticated claim is already recorded; an altered claim, stale generation, restored old snapshot, conflicting finality or unverified receipt cannot release anything.

## Verification gate

Before this can be offered, require red-to-green tests for actual P02 owner session and actual P01 management dispatcher, real cryptographic finality signatures, original-byte/digest/nonce/signer/asset/genesis mismatches, success/failure/replacement effect accounting, pre-sign proof versus ambiguous signing, two requests at one nonce, concurrent reconciliation and signing, day boundary and policy-delay transitions, stale restored state, response loss at every durable write, duplicate and altered proof replay, storage-full fail-closed behavior and qualified board anti-rollback. Test authorities and local chain fixtures must be explicitly synthetic. Existing schema-1 records require an explicit authenticated migration preserving every unresolved reservation; if the old original bytes, signer or nonce cannot be proven, do not migrate that reservation as cleared. No authoritative chain profile or device qualification is currently claimed.

## Interim schema-1 rollover

Until authoritative reconciliation exists, a trusted transition to a later UTC day carries the full amount of *each* unresolved reservation into the new day's spent amount before considering a new request. This pessimistically charges even transactions that may have settled on an earlier day, and it reserves space for every still-valid signed transaction that may settle today. It neither frees any slot nor treats expiry as finality. The next request is allowed only within the daily remainder and the existing per-transfer cap; an ambiguous clock boundary, backwards clock, invalid state, full 16-entry table or exhausted carried amount still blocks. The atomic reserve write persists the new day, carry and new reservation together. All older reservations and their original digest/ID remain unchanged. Therefore ordinary next-day use can continue where capacity remains, but this is not a reconciliation solution: repeated unresolved activity eventually fills the table and no pending policy change can activate. No historic record is automatically erased.

## Current experimental 8283 slice

`nu54_owner_finality` and the separate `device_owner_finality_ps` UID implement an experimental schema-2 original-transaction transition: only chain 8283, one bound signer, asset, genesis and independent P-256 finality key; canonical original bytes are decoded on the board side; nonce is taken from those bytes and must strictly exceed the accepted high-water mark. The signed `N54F` statement binds the board, generation, genesis, signer, asset, request, exact unsigned digest, nonce, block hash/height/time, finalized height and success/revert. Successful original transactions retain the token amount on their actual finalized block day; reverted originals release it. Identical latest evidence after a committed write returns `ALREADY`; a reused nonce, mismatched scope, altered original or invalid signature cannot release a slot. Earlier evidence whose acknowledgement was lost after a later evidence has replaced the one-entry replay receipt returns unknown rather than asserting success.

`test_owner_finality_anvil.py` runs only against a disposable Anvil 8283 chain and a test ERC-20. It finalizes a real original success and a real original revert, checks the canonical/finalized block and signer, signs evidence with an ephemeral independent P-256 key, and passes it to the actual C PS adapter with OpenSSL-backed synthetic PSA/PS. The fixture uses `issue_owner_finality_evidence.py` to construct the claim. The issuer CLI requires an operator-supplied HTTPS endpoint and the delegated P-256 private key outside the checkout, checks the configured chain/genesis/signer, exact unsigned transaction, original receipt, canonical finalized block twice and finalized account nonce. This is an explicitly trusted independent node/issuer, not an on-board consensus proof or a guarantee against a dishonest node; production operation requires qualified node trust and incident handling. The `make test` host suite exercises C transition and fake protected storage; CI separately executes the disposable chain test after the P06 build. Real secure boot, debug lockdown, TF-M rollback provisioning, independently authorized verifier enrollment, end-to-end management verification, signing-mode exclusion and trusted clock remain unqualified. OwnerSession and experimental board management op 27 forward a bound claim to the PS verifier; op 28 stages independent enrollment and op 29 resumes an already approved preparation. The settings screen accepts bounded typed JSON files for enrollment and finality evidence, and can resume an approved preparation; no qualified production board or production finality service is provisioned. The adapter qualification hook returns false by default. Experimental FINALITY_ONLY includes issuer-grant and independent-display/physical approval enrollment, a prepared V2 record, a mutually exclusive V1 fresh-key witness, and resume of a previously approved preparation. These routes are not production qualified. No V1 record is automatically migrated or removed. Replacement, pre-sign failure and V1 migration are unsupported. Other chains are rejected by this slice. The V2 code must not be enabled or treated as a user-facing reconciliation path until those boundaries and a scoped production finality authority have been qualified and independently reviewed.

## Replacement first slice

A replacement claim is a different signed `N54R` domain and binds both canonical unsigned transaction digests. It is accepted only when original and replacement decode to the same 8283 signer, nonce, enrolled token and allowed recipient, and the replacement amount is nonzero and no greater than the original reservation. The independent issuer must verify the finalized transaction is the exact replacement, its signer and nonce, original/replacement raw bytes and canonical receipt; the board re-decodes both inputs and verifies the separate scoped authority signature. No assumption is made that a successful ERC-20 receipt transferred the nominal amount: replacement success conservatively charges the *full original reservation* on the replacement's block day. A finalized replacement revert releases it because the nonce was consumed and all effects of that reverted execution were rolled back. A replacement on a different chain, asset, nonce, signer or recipient, a larger amount, native cancellation, arbitrary contract call, unknown receipt, missing original or missing trusted evidence remains blocked. This deliberately narrow rule is not general replacement reconciliation.

## V1 migration gate

A V1 active record is not a fresh-key marker and is never erased or reinterpreted in place. Its per-transfer/daily limits, asset, destination, revision, current UTC-day charge and every unresolved reservation must survive migration. Each reservation needs its exact original unsigned EVM bytes and verified signer/nonce; digest, amount, chain, asset and recipient must match the V1 record. A missing, duplicate, altered, non-EVM or out-of-scope original blocks migration and leaves V1 intact. An in-flight V1 policy change blocks migration until its original owner workflow resolves it.

Those records alone do not prove complete nonce history. In particular, V1's explicit allowance-revocation route can sign an EVM transaction without adding a limit reservation. A V1 record with zero or fully recovered reservations therefore does not prove that no other signed nonce exists. An independently authenticated chain finalized nonce only proves the consumed prefix, not absence of a higher signed transaction. Safe same-key migration must additionally have a rollback-protected, independently qualified signer-issued complete nonce journal that covers *all* prior signature routes and supplies its high-water mark. Existing V1 builds have no such witness, so ordinary deployed V1 is explicitly blocked rather than relying on the phone, an issuer's guess or local expiry. A separate user-approved fresh key and explicit transfer can be offered only as its own flow; no old signature is claimed revoked.

For a future qualified V1 lineage, prepare a V2 copy and exact snapshot digest first; never change V1 policy or clear reservations. Under the same V1 signing lock, recheck that snapshot and durable complete-nonce witness, then write a version-distinct immutable migration fence before activating the V2 copy. V1 reads/signing reject the fence. If a crash occurs before the fence, V1 remains authoritative; if it occurs after the fence, no V1 signature is allowed and the approved V2 preparation resumes. A changed V1 snapshot before the fence requires a new review, not reuse of stale preparation. Platform secure boot must exclude rollback to an image that ignores the fence. None of this qualifies a previously untracked V1 lineage by itself.

The V1 route inventory matters for that proof: ordinary direct ERC-20 EVM transfers reserve under this policy before EVM signing; owner-role P06 pilot approvals also reserve, but their quote/approval digest is not an EIP-1559 transaction and cannot be fabricated as a missing EVM raw transaction. Allowance revocation signs a same-account EVM transaction outside the limit reservation; its validated operation is an allowance reduction to zero, not an authorized asset transfer. A previously signed revoke can nevertheless consume a nonce first, make a pending transfer fail or wait, and leave reconciliation ambiguous. SIWE signs a scoped message rather than an on-chain transaction; the isolated market path uses its separate derived account; non-EVM account routes use separate derivation and are not covered by this 8283 EVM migration. Existing wallets created before this experimental fresh-key policy may additionally have untracked transfer signatures, so their risk includes actual unauthorized-by-the-new-policy spending, not merely revoke-related availability. Normal V1 remains usable in its original firmware/profile while no migration fence has been committed; it retains conservative carry/full-table limits. A new-generation setup must not mutate that V1 key, policy or pending records or claim old signatures invalidated.

### Independent display handoff

The public display characteristic returns only the pending attempt's 32-byte
random challenge or ATT read refusal. This applies to policy initialization,
policy changes and finality enrollment, as well as checkout and other display
prompts. Offset reads can return only the corresponding slice of the
challenge. The signed intent stays private.

The owner app gets the TLS exporter epoch from its pinned management session
and the request ID and expiry from the frame it sends. During that pending
request the owner can reveal a locally rendered QR with the ASCII form
`operation/session/request/expires` (decimal opcode, two 32-digit lowercase hex
values, then decimal Unix seconds). The QR opens only on an explicit tap.
It contains the session binding, never the TLS key, PIN, policy values, address
or signing key. The view clears when the request expires, the session closes,
or the app leaves the foreground. There is no share action, clipboard write
or saved QR.

On the registered independent display, run `recovery-accessory/confirm_board.py
policy ADDRESS DISPLAY_KEY --expect POLICY.json` or use
`finality-enroll ADDRESS DISPLAY_KEY --expect GRANT.json`. Scan the QR in
person with a USB scanner in keyboard mode into the display's hidden terminal
prompt, or enter the code there. The display combines the local code with the
BLE challenge and its independently prepared expected policy or issuer grant.
Policy dates are derived from the exact request expiry and the existing
24-hour delay. The finality grant retains its separate issuer expiry. The
display checks all values before signing with the registered display key. The
board verifies the exact canonical statement for that session, request and
challenge before enabling the matching physical prompt. An incomplete or
expired code, wrong public challenge, or different policy cannot result in a
valid proof. A previous accessory that consumes full characteristic data
must be updated for policy approvals. The signed statement bytes and
operations 24, 26 and 28 retain their existing meanings.
