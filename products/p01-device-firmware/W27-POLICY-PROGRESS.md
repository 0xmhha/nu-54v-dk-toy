# W27 owner-limit work in progress

The `nu54_owner_limits` transition and opt-in TF-M PSA Protected Storage adapter are **not an activated production board policy**. The adapter is enabled only by the experimental profile. That profile links authenticated management read/change/activation handling and reserves before personal pilot and ordinary EVM signing; absent protected state blocks those signing paths. This is not a qualified or provisioned production policy. It currently models conservative reservation bound to a caller-authenticated time interval, owner generation, chain, asset and the active recipient policy; an uncertain day boundary, backwards time, unknown generation, corrupt state or full reservation table is rejected. A repeated identifier is accepted only for the same generation, amount, expiry and digest. A caller must reload trusted state after any ambiguous storage error and durably reserve before producing a signature. On a new UTC day, the full value of every unresolved reservation is carried into that day before a new reservation is considered; the trusted interval must lie wholly within the new day. The slots are not released. A signed transaction's local expiry alone is not proof that it could not settle later.

Remaining device work before the settings change can be offered:

1. Qualify the first-EVM recipient-set migration and downgrade refusal on hardware. The host implementation and its adapter boundary are described below.
2. Carry the exact previous and proposed caps and allowlist, owner generation, revision, fresh challenge and deadline through the authenticated owner channel. Verify an independent display's signed statement and consume the matching physical button event; rejecting, disconnecting, wrong generation or an expired request must leave the active policy unchanged.
3. Persist a pending change before acknowledgement, keep the old policy in force through the mandatory delay, and activate only after trusted monotonic lower-bound time passes the delay. A restart without a trustworthy time source must block activation until a fresh authenticated time observation; an ambiguous write must force a durable reread.
4. Integrate reservation before **every in-scope** signing path and bind it to the same canonical operation and durable receipt. Failure after reservation remains charged until authoritative reconciliation; a retry must never generate a new uncharged signature. Handle pending operations across calendar boundaries without assuming that a local expiration proves chain finality.
5. Bind any released amount and day rollover to authoritative, replay-protected outcome evidence. Treat unavailable, ambiguous, tampered, rollback or full storage as blocked, never as zero spent. Test power loss at each durable boundary, duplicate requests, day-boundary uncertainty, owner replacement, downgrade and disconnect.
6. Expose verified current and pending policy through the existing owner-authenticated channel. Only then connect P02's limits, policy-wait and applied screens to the device. W27 can request device-bound policy readback and the experimental initialization/change flows; an unqualified board reports them unavailable.

`test_owner_limits.c` is a host regression for the partial transition; its caller-supplied clock values are test fixtures and do not prove trusted-time or physical-button integration.

The host strong-counter port and fixture verify that a stale record with a newer independent counter is rejected, as are missing callbacks, storage errors and ambiguous counter advance. The experimental TF-M adapter uses a separate Protected Storage UID, rejects absent or malformed state, serializes updates and treats a PSA write error as ambiguous. Its protection depends on actual TF-M PS rollback provisioning, verified secure boot and debug protection. A compilation proves none of those conditions on a device. The installed Nordic TF-M build selects its generic in-die flash NV-counter backend; its security depends on the in-die region and lifecycle/debug protections. The experimental `ns` overlay and test signing key are not a release or a flash authorization.

A compile-only custom `nu54v_dk/nrf54l15/cpuapp/ns` profile was built with MCUboot, a disposable Ed25519 test key, and a separate experimental combined secure/nonsecure partition overlay. `imgtool verify` accepted the resulting `zephyr.signed.bin` (version 0.3.0); the generated application configuration had TF-M PS rollback protection and the experimental adapter enabled. The Nordic build selected the template in-die flash NV-counter backend, with an 8 KiB OTP/NV region split between main and backup and a configured 2048-byte PS maximum asset. This is not a device qualification: the image was not flashed, the test key is not a trust root, the layout has not been checked against field migration or recovery, and secure boot, provisioned HUK, debug lockdown, rollback resistance and power-loss behavior have not been established on a board. The adapter is disabled in all normal profiles; in the experimental profile its manager and two scoped pre-sign gates are linked.

A further experimental host transition and PSA adapter exercise the 10/30-to-12 case with an injected test-only hash and independent-proof verifier. The canonical statement binds the board, session, request, challenge, owner generation, policy revision, chain, asset, old and proposed destination, old and proposed limits, request expiry and earliest activation. A matching `nu54_local_approval` physical-event token and independent statement verification are both required in that model; the proposal is written pending and the old cap stays active until the lower trusted-time bound reaches at least 24 hours after the approval request's expiry. An outstanding reservation blocks policy changes. The host PS fixture tests authenticated-board/generation readback, pre-delay refusal, activation after the delay, rejected button/proof, and a write that commits before reporting an error; pending request ID and statement digest support readback without repeating approval. The 24-hour delay is an experimental conservative choice, not an approved production policy. The verifier, hash, button event and strong counter in that unit fixture are simulated. The host integration below exercises the P02 owner session and C policy and signing paths. Qualified provisioning and evidence from a physical device clock remain outstanding. V1 supports one allowed address and has no finality reconciliation.

An existing owner must not be bootstrapped merely because the protected policy UID is absent. Previously signed EVM transactions may remain executable even after a local request expires, and the existing per-phone pending checkpoint does not prove that every historic nonce or signature is fenced. Safe activation requires a provably fresh key/generation before its first signature, or an authoritative finalized fencing/migration process that covers all prior authorizations. The experimental fresh-key bootstrap described below covers only a newly generated key with a durable fresh marker; existing keys without state fail closed. Existing market-account and read-only operations remain separate, and normal non-experimental profiles do not claim owner-limit enforcement.

The experimental management profile now has read (23), staged change (24), delayed activation (25), and fresh-key initialization (26) paths. A new HD seed may create a generation- and board-bound write-once fresh marker only while the existing seed and its hardware witness are absent; imported or existing keys do not get one. Initialization needs that marker, an independent `N54I` display signature and the device PIN/physical approval, and writes a separate initialized witness before the policy. Failure between those writes blocks recovery rather than treating a used key as fresh. The experimental PS port's platform-qualification hook defaults to false; no production implementation attesting the boot counter, debug/lifecycle and provisioned secure storage is supplied, so the profile cannot initialize or sign on an unqualified device. Prior signatures are never claimed revoked.

After a provisioned policy, the experimental profile reserves before personal pilot and ordinary EVM signatures. Other-chain personal signing requires policy presence; market signing remains a separate derived account. Duplicate reservation without an independently stored matching receipt cannot sign again. The reservation table is bounded at 16; unreconciled reservations can exhaust the daily remainder or the table and block further signing. Legacy management operations 23–26 expose the single-recipient policy view. Enrolled owners can use authenticated C1 operations 32–35 for the full recipient set. Physical qualification remains open.

`test_owner_limits_evm_ps` joins the actual ordinary EVM completion function to the actual PS policy adapter in one host process. With a synthetic PS strong counter, synthetic time and a pre-established simulated approval, it checks rejection above the cap, durable reservation before a subsequent signature/serialization failure, and refusal of both a repeated and a modified request without releasing that reservation. It does not exercise the real P02 session, device physical approval, qualified hardware storage or authoritative finality reconciliation.

The P02 `ownerSession.test.ts` host integration compiles `owner_limits_host_bridge`, uses the actual `OwnerSession` and V2 framing with a synthetic transport, and exchanges policy requests with the C parser and real PS adapter. The bridge drops the successful pending-change reply before reconnect, then the same synthetic persisted state is passed to actual `device_evm_complete`: a transfer above the old active cap is refused, an in-cap reservation survives a deliberately failed signature and an identical retry does not sign or add another reservation. OwnerSession reads that reservation and the still-pending change after reconnect. Activation rejects the stale candidate, missing time, a clock one second before the deadline and an unresolved reservation. With the separate unreserved fixture at the deadline, activation reads the new revision before returning and keeps it across restart. The bridge supplies its own test-only management dispatcher and substitutes the BLE/TLS peer, secure storage/counter, clock, independent display and physical button; it does not execute the full Zephyr `device_pilot` dispatcher or prove those device boundaries. The experimental `/ns` image was re-linked with the shared parser using the disposable test signing key; this remains compilation evidence only. Run the host scenario with `pnpm --dir products/p02-user-app exec jest --runInBand ownerSession.test.ts` (CMake and a host C compiler required), and the C transitions with `ctest --test-dir <host-build> -R '^owner_limit' --output-on-failure`.

## First-EVM recipient-set adapter

The opted-in PSA owner-limit path uses one policy for the enrolled board, owner generation, numeric EVM chain and ERC-20 test-token address. Schema 2 adds an active and a pending recipient set to the existing rollback-protected asset. It accepts up to eight nonzero 20-byte addresses, strictly ascending by unsigned byte value. Repeated addresses, unsorted addresses and nonzero bytes in unused slots are rejected. A set with count zero permits zero new recipients. The signed statement contains addresses only. The phone retains address names and contacts.

The adapter reads a schema 1 singleton as a set of one. `device_owner_limits_migrate_recipients_ps` can materialize that representation with one atomic write to the same UID. It keeps the revision, caps, accrued spend, reservations, pending request and original deadline. A new recipient proposal also materializes schema 2 when approved. After an interrupted write, the next read determines whether schema 1 or schema 2 survived. Repeating a completed migration adds no write. Firmware with the schema 1 reader rejects the new size/schema. The legacy management read can still project a singleton if both current and staged policies are representable. A multi-recipient or empty policy cannot be projected into an arbitrary single address. Legacy cap/destination proposals are refused after schema 2 is written. Previously staged v1 cap changes retain their original activation and outstanding-reservation rules.

Authenticated C1 operations 32–35 read the active and pending sets, stage a recipient-only or cap-only proposal, and activate the exact pending request after its deadline. The reply binds board, owner generation, revision, chain and asset. The independent verifier reconstructs the 498-byte `N54R` or 514-byte `N54M` statement using the private request binding and its own policy record. Public GATT reads expose only the 32-byte challenge. The board checks the registered display key and requires local approval before persisting a proposal. The wallet's W27 editor keeps contact names on the phone and passes only addresses selected from the verified network profile. The app checks committed state after a lost acknowledgement. [Wire and independent display](../../packages/protocol/v2/owner-management.md)

During the hold, only the active policy participates in signing. Recipient activation keeps the original caps. Cap-only activation keeps both original address lists and rejects a new daily cap below the recorded debit. Both preserve accrued spend and unresolved reservations in the same PS record. The next reservation carries unresolved amounts across UTC day rollover. A pending legacy change retains its original activation and outstanding-reservation rules. The same PS mutex serializes activation and reservation. The existing EVM gate checks the decoded token and recipient and durably reserves before signing. A repeated request cannot reserve or sign twice.

Host tests check interruption, stale revisions, old pending state, empty and full sets, wrong asset and real HD signing before and after activation. The P02 integration exercises the authenticated mobile wire, synthetic restart and C storage round trips with all eight recipients. The Python display encoder is tested against fixed statement bytes and the host display peer can verify its real P-256 proof against the C statement. These tests substitute secure storage, time, BLE and buttons. The PS record and management payload are constrained at compile time. Hardware qualification and power interruption remain open.

## Platform evidence required to enable W27 on hardware

The nRF54L15 silicon supports hardware-rooted boot and debug protection. The experimental W27 build exercises a TF-M application layout. Its generated MCUboot configuration has been observed with debug protection disabled and FPROTECT absent. That configuration does not qualify an installed board. The W27 adapter's production fallback remains false. [nRF54L15 immutable boot](https://docs.nordicsemi.com/r/bundle/ps_nrf54l15/page/chapters/security.html-immutable_boot) · [Nordic production debug protection](https://docs.nordicsemi.com/r/bundle/nan_047/page/app/nan_production_programming/nrf54l/nrf54l_device_protection.html)

The qualified profile needs a TF-M secure service with a versioned response bound to the current boot and installed board. The secure service should derive these results from the platform:

- **Provisioning and debug:** Require the secured OTP lifecycle, a provisioned board hardware root and attestation identity, and effective secure and nonsecure debug lockdown in this boot. The NCS 3.4.1 Nordic TF-M attestation HAL reads the lifecycle from bootloader OTP. Nordic's TF-M provisioning code checks the HUK, attestation key and UICR APPROTECT fields. Its UICR check describes the next reset. The service must also verify that the current boot applies protection using the approved SoC/boot configuration and hardware observations. The release manifest's generated Kconfig checks do not observe runtime lockdown.
- **Boot:** Require a verified, confirmed boot under the pinned immutable root, an approved secure and nonsecure measurement pair, hardware image rollback fencing, and the required protection for the boot chain and secure regions. The counted-update install proof in `device_install.c` already checks MCUboot confirmation and measures the active application slot. It provides a useful identity and image cross-check. The TF-M qualification result must also cover the bootloader and the secure image and read the provisioned rollback counter. An application measurement or confirmed image flag alone supplies only part of that evidence.
- **Storage:** Pin the secure layout, PS encryption and authentication backend, and rollback-counter implementation for the measured TF-M image. Verify counter availability and binding using the secure backend. A write/read probe can detect failed PS initialization. The probe alone cannot establish rollback resistance. Keep an independent counter floor outside any region that can be restored together with policy, and define the device recovery and reprovisioning behavior before qualifying the profile.
- **Runtime:** Bind qualification to this board identity and boot, invalidate it across reset or update, and fail closed on errors. Supply a verifier-backed installation time observation after boot through the existing device-install path. Check the source and maximum uncertainty and use the device lower bound for activation. Retain the current fresh/initialized witnesses and immutable migration boundary. Approval and signing must use the same qualification decision.

The experimental `owner-limits-tfm.conf` profile enables a TF-M IPC partition and NS client for W27. The default profile leaves the option off. V2 uses strict PSA service and wire version 2, a 68-byte request and a 36-byte response. The secure partition validates the exact request evidence mask and image-build tag. It rejects V1 requests and responses, including the old 112-byte response.

The partition reads the FICR factory ID and `UICR.BOOTCONF` internally. The reply carries a status indicating whether BOOTCONF equals the nRF54L15 reset value, and an opaque per-secure-boot identifier. PSA Crypto derives the identifier from a domain label, factory ID, paired build tag, BOOTCONF and secure random data. The partition keeps its initial boot configuration and identifier in secure RAM. A subsequent BOOTCONF change makes the service unavailable for that boot. Secure reset clears the state and the next successful request uses fresh random data. The factory ID, boot nonce and raw register stay within the secure partition. The tag pairs the service and client using their source, SDK release, effective app Kconfig and DTS. Verified measurements of executing flash remain required.

The snapshot is a local diagnostic. The TF-M manifest permits nonsecure clients on this platform. Any nonsecure caller with the build tag may request the same opaque value during that secure boot. The partition does not authenticate a wallet owner or individual NS client. The current firmware has no BLE, logging or external export for the snapshot. The client gets observations from a live PSA call and retains no observation across reset. The diagnostic carries no remote attestation proof and assumes a trustworthy TF-M kernel and secure platform.

The experimental L15 layout lacks the Nordic bootloader lifecycle-storage handoff and leaves Initial Attestation and provisioning off. The BOOTCONF status describes a stored configuration word. Provisioned HUK/IAK, verified boot, effective debug lockdown and rollback storage require independent evidence. V2 deliberately omits those proofs. The NS client rejects inconsistent version, size, malformed identifiers, unsupported evidence bits and unsuccessful PSA calls. Its available mask cannot satisfy the authorization mask. W27 management and policy-controlled personal transfers and pilot payments remain blocked. EVM login, allowance revocation and isolated market signing retain their separate authorization paths.

The NS client probes the partition at Zephyr APPLICATION initialization, after the SDK has initialized the NS interface. The existing limits gate uses the same reader.

The remaining work includes trustworthy boot measurements and counter handoff, the qualified storage layout, and a production commissioning root. Qualify the resulting signed profile on isolated nRF54L15 hardware with cold boots, an unprovisioned board, debug attachment attempts, signed-image rollback, protected-state rollback, power interruption around PS commits, restart with no trusted time, and the independent display plus physical SW1. Record measured locked state, counters, and policy revision after each case. Test the actual wait separately from the accelerated host run. Existing keys require the migration/fencing proof in the [reconciliation design](W27-RECONCILIATION-DESIGN.md).

### Compile-only checks

In an activated NCS 3.4.2 workspace, point `firmware` at P01 and use a private scratch directory. The pilot and HD fragments retain the existing policy call sites in the NS link. Prepare the pinned TLS module with `scripts/mbedtls_input.py` and set `tls_source` to the prepared module path. The workspace root must have the Nordic MCUboot checkout at `bootloader/mcuboot`. The counted experimental overlays give the pilot and HD configuration 192 KiB of nonsecure SRAM. MCUboot uses swap-move mode with a disposable key for this build.

```sh
mcuboot_source=$(PYTHONPATH="$firmware/scripts" python3 -B -c '
from pathlib import Path
import sys
from mcuboot_input import prepare
print(prepare(Path("bootloader/mcuboot"), Path(sys.argv[1])))
' "$scratch")
openssl genpkey -algorithm ED25519 -out "$scratch/compile-only.pem"
west build --sysbuild -b nu54v_dk/nrf54l15/cpuapp/ns "$firmware/app" -d "$scratch/build" -- \
  "-DBOARD_ROOT=$firmware" -DSB_CONFIG_BOOTLOADER_MCUBOOT=y \
  -DSB_CONFIG_MCUBOOT_MODE_SWAP_USING_MOVE=y -DSB_CONFIG_BOOT_SIGNATURE_TYPE_ED25519=y \
  "-DSB_CONFIG_BOOT_SIGNATURE_KEY_FILE=\"$scratch/compile-only.pem\"" \
  "-Dapp_EXTRA_CONF_FILE=$firmware/app/owner-limits-tfm.conf;$firmware/app/pilot-tls.conf;$firmware/app/hd-recovery.conf" \
  "-DEXTRA_ZEPHYR_MODULES=$mcuboot_source" \
  "-Dapp_EXTRA_ZEPHYR_MODULES=$tls_source;$mcuboot_source" \
  "-Dmcuboot_EXTRA_ZEPHYR_MODULES=$tls_source;$mcuboot_source" \
  "-Dapp_EXTRA_DTC_OVERLAY_FILE=$firmware/app/experimental/owner-limits-tfm-counted.overlay" \
  "-Dmcuboot_EXTRA_DTC_OVERLAY_FILE=$firmware/app/experimental/owner-limits-tfm-counted-mcuboot.overlay"
```

It leaves the VCOM1 management console on UARTE20 and the TF-M secure console on UARTE30. It disables the SPI00 instance that shares the UARTE00 registers. ### Owner idle lock

The W27 management link starts the 120-second monotonic idle timer after TLS authenticates the current owner on a qualified experimental personal board. The handshake still has the original first-connection deadline. Kiosk payment, recovery enrollment and unqualified sessions retain their connection limits. The idle timer advances only on accepted local SW1 or PIN input for the bound physical prompt. TLS or BLE traffic, status reads, capability checks and independent-display messages leave the timer untouched. Approval envelope expiry and local PIN entry timeout are evaluated separately.

At idle expiry or BLE disconnect, the link invalidates the prompt, wire2 and TLS state, PIN authority, and volatile approval and display bytes. The PIN loop checks the session and prompt before accepting an event or processing the completed PIN. A queued click from a retired prompt or disconnected link is refused. The loop polls cancellation at most every 100 ms while waiting for a button. Committed PS policy and reservations and recorded receipts remain governed by their own protocols. A fresh authenticated link is required to continue. No general production qualification is inferred from the idle feature.

Authenticated owner opcode `0x73` reports revision 1, idle and disconnect flags, and a 120-second rule. The phone verifies it separately from policy data and renders an unavailable rule on unsupported or unverified connections. This evidence confirms the reported rule at read time. The app does not maintain a board lock countdown or present a locally inferred lock status. The C regression uses virtual monotonic time. The production PIN loop runs in a native host test with simulated button, ITS and timing adapters. The iOS approval test uses the existing host TLS adapter and fixture capability. Hardware BLE disconnect timing and secure-world provisioning are separate field checks.
