# P03 시험 프로필

A, B, C는 각각 전용 참가자 프로세스와 전용 저장 디렉터리를 가진다. 조정 서비스는 라운드 메시지와 share를 받지 않는다. 업무 허가와 참가자 ACK만 교환한다. 운영 조직과 모바일 승인 증명이 계약된 조합만 공개한다.

| 동작 | 시험에서 관찰할 결과 |
| --- | --- |
| 가입·생성 | P03에 발행된 로그인 증명과 별도 사용자 증명을 검증한다. 동일 생성 요청에는 같은 세션을 반환한다. 독립 3개 share 저장 확인 및 같은 공개키를 받은 후 주소를 공개한다. |
| 참가자 통신 | 승인된 세션 전체의 지문을 peer·메시지 라운드·수신자에 결합한다. TLS에서 증명한 발신자와 명시 발신자가 다르면 거절한다. 브로드캐스트는 참여자 간 digest를 대조하고 원문 하나만 처리한다. |
| 재조회 | 각 참가자가 결과를 디스크에 커밋한 뒤 ACK를 반환한다. 프로세스가 중단됐고 결과가 없으면 같은 세션의 일회 자료 사용을 차단한다. 완료한 세션은 같은 결과를 재전송한다. |
| 서명 | 요청·체인·원문·세대·만료에 독립 A의 확인을 받는다. A/B가 저장한 결과를 같은 공개키로 검산하고, 서명 결과에서 체인 제출을 분리한다. |
| 복구 | 이전 세대의 일상 서명을 먼저 펜스하고 C의 별도 승인과 정책 대기를 확인한다. 구 B/C와 새 A/B/C에 서로 다른 참가 ID를 할당하고, 동일 공개키와 새 참여자 ACK 3개를 확인한다. |

## 참가자 제어와 저장

조정 서버와 참가자는 별도 TLS 인증서 지문으로 역할을 확인한다. 참가자끼리만 라운드를 전달한다. BNB Chain tss-lib v4의 고정 커밋 `f204718ae595`를 사용하고, 생성·서명에서는 A, 교체에서는 이전 C가 각 실행의 비밀 nonce 32바이트를 생성한다. 그 값을 세션 참가자에게만 상호 인증 TLS로 제공한다. 조정 서버와 클라이언트에는 세션 지문만 보인다. 증명은 엔진 기본 활성 설정을 사용한다. 재시작 후 완료 결과를 조회하고, 미완료 일회성 자료는 새 라운드로 이어지지 않는다.

참가자 API의 제어 경로는 `POST /v1/ceremony`, `GET /v1/ceremony/{id}`, `PUT /v1/fence`다. 발신자 인증서 핀과 세션에 속한 peer, 위원회, 메시지 종류를 대조한다. 각 참가자는 레코드를 암호화하고 디렉터리를 fsync한 후 결과를 공개한다. 같은 세션의 불일치 요청은 차단한다. 서명 세대 펜스 이후 구세대 서명 결과는 참가자 응답에서도 제거된다.

조정 서버는 생성의 A/B/C, 일상 서명의 A/B, 재공유의 이전 B/C와 새 A/B/C를 모두 확인한다. 준비만 끝난 참가자 일부의 보고는 공개 주소나 서명을 열지 않는다. 재공유에서 이전 B/C 양쪽 펜스를 확인한 후 두 구세대 참가자와 세 새 참가자의 같은 공개키 증거를 대조한다. PostgreSQL에서 이전 epoch 은퇴와 새 epoch 활성화를 한 번에 기록한다. 재공유 재시도가 필요한 경우 같은 지갑이 동결 상태로 남고 새 요청 번호와 새 승인, 새 일회 자료를 사용한다.

## P03 모바일·외부 권한 게이트웨이

HTTPS API는 `/v1/enrollment`, `/v1/session`, `/v1/wallet`, `/v1/operations`, `/v1/operations/{id}`, `/v1/operations/{id}/approval`, `/v1/credentials`, `/v1/credentials/{id}`, `/v1/close`를 제공한다. 신원 게이트웨이는 EdDSA JWT 헤더 `alg=EdDSA`, `typ=JWT`와 `iss`, `aud=nu54-p03-wallet`, UUID `sub`, UUID `credential_ref`, `scope`, `iat`, `exp`를 발급한다. 일반 요청은 `wallet`, 신규 연계는 `wallet:enroll` scope를 사용한다. JWT는 최대 5분 유효하다. provider의 원래 식별자와 계정 토큰은 권한 게이트웨이에 남긴다.

신원, 개별 승인, 복구는 서로 다른 서명 키와 HTTPS origin을 사용한다. P02는 브라우저의 사용자 확인과 기기에서의 결과 조회를 분리한다. 연동 게이트웨이는 아래 계약으로 교환한다.

시험 게이트웨이의 확인 양식은 같은 HTTPS origin으로 제출한다. 양식 문서는 `Referrer-Policy: same-origin`을 사용해 Safari에서 동일 origin 제출을 유지하고 외부로 referrer를 보내지 않는다. 서버는 설정한 origin과 일치하지 않는 양식 POST를 거절한다.

| 호출 | 본문 / 반환 |
| --- | --- |
| `POST /p03/device/start` | `request`, `codeChallenge`, `codeChallengeMethod: S256`을 받는다. `deviceCode`, 사용자 확인용 같은 origin의 `verificationURL`, 15–300초의 `expiresIn`을 반환한다. |
| `POST /p03/device/poll` | `deviceCode`와 `codeVerifier`를 받는다. `pending`, `denied` 또는 `ready`를 `state`에 반환한다. 로그인 성공에서는 `token`과 필요시 `enrollmentToken`, 독립 확인 성공에서는 Ed25519 증명의 base64 `proof`를 반환한다. |

로그인 요청의 `request`는 `action=login`과 `audience`다. 동작 승인은 `action`, `session`, `fingerprint`, 전송 시 `transfer`를 전달한다. 게이트웨이는 사용자가 해당 지갑을 관리한다는 독립 증명과 해당 요청 원문을 확인하고 `nu54/p03/ceremony-approval/v1/<kind>\x00` + 32바이트 세션 지문에 서명한다. 지갑 종료의 `action=close`는 `close:{Wallet,Epoch}`, 동일 객체 JSON의 SHA-256 `fingerprint`, `confirmAccessEnds:true`를 사용한다. 외부 게이트웨이는 결과를 다시 읽을 때에도 동일한 기기에 결합된 PKCE 확인과 만료를 검사해야 한다.

Sepolia 전송 프로필은 `chain=11155111`이고, EIP-1559 네이티브 자산 전송(가스 한도 21,000, calldata와 접근 목록 없음)만 파싱한다. 요청자·조정 서버·참가자 A/B의 역할은 승인·원문 확인·임계 서명의 순서로 연결된다. P02는 받는 주소·금액·최대 가스비·nonce·세대·만료를 표시하고, 원문과 서명 결과를 다시 계산한다. 동일 요청의 서명 결과는 활성 세대에서 24시간 동안 읽을 수 있다.

P02는 인증된 `/v1/session`의 pairwise subject와 지갑 번호를 확인한 뒤 해당 origin·subject·지갑에 대응하는 암호화 요청 기록만 연다. 지갑 번호 발급 전의 생성 요청은 별도 생성 범위에 보관하고, 서버가 같은 지갑 번호를 반환하면 지갑별 기록으로 이동한다.


## 기기 참가자 등록 경계

`POST /v1/mobile/roster`는 연결된 고객의 공개 PKCS#10 CSR만 받는다. 서명 검증된 CSR의 SPKI digest와 로그인 subject로 요청을 결합한다. 준비 결과는 `pending` 또는 독립 명부 발급자가 만든 `ready`다. 발급자는 모바일이 제출한 공개키에 TLS 인증서를 발급한다. 키와 서명 명부에 대한 권한은 별도 보관하며, 최종 위원회와 조정 서버는 두 TLS 핀을 미리 등록한다. 모바일은 앱의 서명된 구성에 고정된 Ed25519 서명 키로 `nu54/p03/device-roster/v1\x00` + 명부 payload를 확인하고, subject와 로컬 TLS 키가 일치해야 참가자를 시작한다.

네이티브 A는 iOS Keychain 또는 Android KeyStore로 보호된 AES 키를 사용한다. TLS 시드와 share는 네이티브 암호화 저장소에 기록하며, React 브리지에는 공개 CSR, 서명 명부 및 시작 결과만 전달한다. 최초 DKG와 재공유에는 서로 다른 참가자 ID와 TLS 키를 사용한다. 노출된 과거 정족수는 같은 공개키 재공유로 외부 서명 능력을 회수할 수 없다.

## 운영자 장애·사고 조회

`GET /v1/recovery/status`와 `POST /v1/recovery/incidents`는 독립 운영자 issuer, subject, 공개키 및 JWT scope `wallet:recovery-ops`를 사용한다. 운영자는 활성 세대, 미검증 대체 경로의 비활성 상태, 최소 감사 기록과 정족수 유출 동결 여부를 확인한다. `{"kind":"quorum_exposure"}`는 조정 DB에서 진행 중 작업과 신규 서명을 막고 해당 세대의 로컬 펜스 작업을 예약한다. 일반 재공유 또는 자동 자산 이동은 발생하지 않는다. 가용성·정족수 유출·체인상 자산 처리는 서로 다른 결과다.

등록 명부는 단말의 현재 좌석과 사용자에 귀속된다. 버전은 `(Epoch, Revision)` 순서로 증가한다. 같은 버전의 동일 서명 원문은 재조회할 수 있으며, 같은 버전의 변경이나 이전 버전 재설치는 거절한다. 명부 파일과 버전은 잠금 아래 한 파일로 교체한다. 변경 승인 후에는 이전 네이티브 리스너를 종료하고 새 명부로 다시 인증한다.

P02 네이티브 모듈은 지갑 서버의 유효한 로그인 응답에서 사용자와 만료를 다시 확인하고 그 범위의 저장소만 연다. 로그아웃, 자격 단절 확인, 로그인 만료 또는 화면 종료는 로컬 리스너와 진행 라운드를 종료한다. P02는 활성 중에 자격 상태를 다시 확인한다. 취소 당시 이미 발급된 결과의 재조회와 미완료 라운드의 폐기는 별도로 처리한다.

## 복수 사용자 등록과 요청 범위

등록은 로그인 issuer가 인증한 pairwise `Subject`와 별도 발급자가 서명한 해당 계정 프로필을 함께 확인한다. 첫 가입 시 사용자·issuer·독립 동작 승인/복구 키·위원회·참가자 HTTPS origin과 pin을 한 트랜잭션에서 등록한다. 등록 파일의 서명 입력은 `nu54/p03/account-profile/v1\x00`과 공개 프로필 JSON payload다. 한 계정은 고유한 참가자, 승인 키, 주소와 세대 이력을 갖는다. 이전 단일 등록은 시작 설정과 기존 영수증으로 계속 동작한다.

고객이 생성한 UUID는 응답 `requestId`로 되돌아오며 `(wallet_id, request_ref)`에서 유일하다. 참가자가 사용하고 증명하는 별도 `session.ID`는 조정 서버가 할당한다. P02는 `requestId`로 자신의 요청을 다시 조회하고, 별도로 내부 세션 지문과 전송 원문을 재계산한다. 기존 요청은 두 ID가 같다. 동작 승인·복구 브라우저 요청의 `owner`는 조회한 subject의 힌트다. 여러 계정을 처리하는 권한 게이트웨이는 사용자가 브라우저에서 증명한 subject와 일치하는 경우에만 해당 계정 키로 서명한다.

기기 등록을 먼저 해야 하는 새 고객에게 `/v1/session`은 `linked:false`와 확인된 pairwise subject 및 로그인 만료를 돌려준다. 이 범위에서는 공개 CSR 제출과 승인 대기 확인이 가능하다. 지갑 조회·DKG·서명·복구와 네이티브 리스너 시작은 프로필 승인 및 계정 연계 이후에 가능하다. 기존 연계가 해제된 자격은 신규 CSR 대기로 돌아가지 않는다. 배포 서비스가 반환하는 모바일 명부의 A 인증서와 SPKI, 승인 키, 세대 및 사용자도 계정 프로필과 일치해야 한다.

복수 계정의 사고 조회는 `GET /v1/recovery/status?wallet=<UUID>`를 사용한다. 사고 동결은 `POST /v1/recovery/incidents` 본문에 해당 지갑 UUID를 포함한다. 독립 issuer가 발급한 운영자 자격과 해당 계정에 등록된 정확한 `Operator`가 필요하다. 이전 단일 경로는 기존 명시적 운영자에게 계속 제공한다.

### 독립 서명 거절

브라우저의 `Deny`는 원소유자의 별도 자격을 확인한 뒤 `POST /v1/sign/refusals`로 제출한다. 요청 입구는 신뢰된 TLS 1.3 클라이언트 인증서를 검사한다. 이 인증서는 전달 채널에만 권한을 부여한다. 원요청에 대한 거절 권한은 귀속된 지갑의 독립 승인 Ed25519 키 서명으로 확인한다. 서명 도메인은 NUL로 끝나는 UTF-8 문자열 `nu54/p03/sign-refusal/v1`, `wallet:sign-refusal`, `sign`의 연결이다. 이어지는 공백 없는 JSON은 `subject`, `wallet`, `session`, `fingerprint`(32바이트 숫자 배열), `epoch` 순서다. 지문은 다이제스트와 전송 원문, 라운드 참여자, 만료와 세대를 결합한다. `session`은 사용자 요청 번호가 분리된 프로필에서도 조정 서버의 라운드 UUID다.

지갑 행과 작업 행을 차례로 잠근 뒤 만료되지 않은 활성 세대의 `reserved` 서명만 `refused`로 전이한다. 이전에 같은 작업의 거절이 기록됐다면 204를 다시 반환한다. 독립 승인이 먼저 `running`에 진입했거나 작업이 다른 상태에서 종결되면 409를 반환한다. 이때 브라우저에는 상태 변경을 안내하고 확인 결과는 `resolved`로 전달하여 앱이 원요청을 조회한다. 정상 거절은 DB 커밋 뒤에만 브라우저에서 `denied`로 확인된다. 기존 owner 인증으로 같은 `GET /v1/operations/{id}` 및 동일 원문의 예약 재시도에 `state: "refused"`를 반환한다. 신규 요청에는 신규 세션과 별도 승인이 필요하다. 기존 복구 거절은 별도 경로의 `denied` 상태와 서명 영수증을 사용한다.

### 독립 복구 거절 영수증

`POST /v1/recovery/refusals`는 전용 CA가 확인한 TLS 1.3 클라이언트와 지갑에 고정된 독립 복구 Ed25519 키의 서명을 둘 다 검사한다. 서명 입력은 각각 NUL 바이트로 끝나는 세 UTF-8 문자열 `nu54/p03/recovery-refusal/v1`, `wallet:recovery-refusal`, `refresh`와 순서대로 뒤따르는 JSON 문서다. JSON은 `subject`, `wallet`, `session`, `fingerprint`(32바이트 숫자 배열), `epoch`, `vote`, `issuedAt`(UTC Unix초) 순서의 공백 없는 객체다. 목적은 이 도메인과 서버의 `refresh` 상태 검사로 한정된다. 최초 접수는 90초 이내의 표만 허용하며, 이미 기록된 같은 서명과 표의 재조회는 원래 결과를 유지한다. 브라우저는 해당 요청이 DB에 기록되어 204를 받은 뒤 거절 결과를 확정한다.

기존 owner 인증이 필요한 `GET /v1/recovery/history`에는 자신의 최근 거절 요청과 시각만 포함된다. 원래 요청을 조회하면 서명 본문과 고정된 복구 공개키, 재심사 연결 여부를 받아 앱이 영수증을 검증한다. 운영자가 본인 전용 realm으로 인가받아 `POST /v1/recovery/reviews`에서 `wallet`과 `request`를 승인한 뒤, owner가 `POST /v1/operations/{request}/review`에 새 `successor` UUID를 제출한다. 한 허가는 단일 연결에 쓰이며 같은 번호를 재시도하면 그 요청을 돌려준다. 새 작업은 독립 복구 승인 전까지 예약 상태이며 구세대 차단을 유지한다. 허가한 재심사에서 증거가 부족해 보류되면 같은 요청과 거절 이력을 유지하고, 새 번호로 일반 복구를 시작해 별도 허가를 우회할 수 없다. 정족수 유출로 사용이 동결된 지갑에는 허가의 신규 기록과 신규 재심사 예약을 차단한다.

### 재개할 수 있는 종료 영수증

기존 `POST /v1/close`에서 `request`를 생략한 호출은 기존 응답을 유지한다. 영수증을 지원하는 호출에는 UUID `request`를 포함하고, 승인 realm에 전달하는 공백 없는 문서의 필드는 순서대로 `Wallet`, `Epoch`, `Request`다. SHA-256 지문을 기존 `close` 독립 승인 도메인으로 서명한다. 기존 증명은 새 번호에 재사용할 수 없다.

소유자가 같은 UUID를 조회하는 `GET /v1/close/{request}`와 자신의 마지막 영수증을 읽는 `GET /v1/close`는 `request`, `wallet`, `epoch`, `acceptedAt`, `assetMoves`(0)를 반환한다. 활성 세대의 펜스가 모두 기록되어 은퇴한 경우에만 `completedAt`을 포함한다. 접수 트랜잭션이 서명을 종료하고 영수증과 감사 사건을 함께 저장한다. 정상 등록 자격으로 다시 조회할 수 있으며 다른 사용자에게는 영수증을 공개하지 않는다.
